# FreeCAD Qt6 Shutdown Segfault

## Summary

All FreeCAD scripts that call `Gui.showMainWindow()` must end with `os._exit(0)` to
prevent a segfault during Qt6 cleanup. Scripts that never initialize the GUI (`FreeCADGui`
not imported) do not crash and do not need `os._exit(0)`.

## Stack Trace

Captured empirically from FreeCAD 1.1.0 under xvfb:


## Root Cause

`freecadcmd` does not run a Qt event loop. Internally it sets `RunMode = "Exit"` and
runs the script via `processCmdLineFiles()` without ever calling `QApplication::exec()`.
`Gui.showMainWindow()` creates the `QApplication` and `MainWindow` but does not start
the event loop.

The crash is in `QApplication`'s C++ destructor. During normal process exit, Python
begins unloading C extensions and triggering C++ static destructors. The `QApplication`
destructor destroys its child widgets, posting `DeferredDelete` events for each one.
Qt6 registers a thread-local storage (TLS) destructor that flushes the main thread's
event queue as part of thread teardown. By the time this hook fires, libc has already
begun freeing TLS slots — including the one Qt6 uses to track the current
`QOpenGLContext`. The widget destructor calls `QSurface::~QSurface()` →
`QOpenGLContext::currentContext()` → `QThreadStorageData::get()`, which reads a TLS
slot that has already been freed. Use-after-free → SIGSEGV.

Key point: the crashing `DeferredDelete` events are **generated by `QApplication`'s
own destructor** as it tears down its child widgets. They do not pre-exist in the event
queue during script execution — they appear only after Python begins the static
destructor phase. This is why draining the queue before exit does not help.

In contrast, the regular FreeCAD GUI binary calls `QApplication::exec()` and runs the
full event loop. When the user closes the window, `exec()` returns, all widgets are
destroyed cleanly inside the still-running event loop, and the process exits normally.
`freecadcmd` never reaches that state.

## Effect on Exit Code

FreeCAD installs a SIGSEGV handler that catches the crash, prints the backtrace, and
calls `exit()`. The exit code is not deterministic:

| Script                    | GUI type             | Crash? | Exit code without `os._exit(0)` | Test outcome             |
| ------------------------- | -------------------- | ------ | ------------------------------- | ------------------------ |
| `build_cube_with_hole.py` | None                 | No     | 0                               | Pass                     |
| `parametric_sketch.py`    | TechDraw             | Yes    | 0 (crash handler)               | Pass despite crash       |
| `build_compound.py`       | TechDraw             | Yes    | 0 (crash handler)               | Pass despite crash       |
| `export_page.py`          | TechDraw             | Yes    | 0 (crash handler)               | Pass despite crash       |
| `render_fcstd.py`         | 3D viewport + OpenGL | Yes    | 1                               | **Fail** without `_exit` |

`render_fcstd.py` exits 1 because a live OpenGL context is in a more entangled state
when the crash fires. The other scripts only set up OpenGL infrastructure for TechDraw's
offscreen HLR renderer, which leaves less state behind.

## Why There Is No Clean Fix

All obvious alternatives were tested empirically and fail:

**`FreeCADGui.exec_loop()` with `QTimer.singleShot(0, qapp.quit)`** — hangs. FreeCAD's
main window intercepts the quit event and shows a "save unsaved document?" dialog.
`exec_loop()` blocks waiting for user input that never comes in a headless environment.

**`qapp.sendPostedEvents(None, QEvent.DeferredDelete)` before exit** — does not
prevent the crash. The crashing `DeferredDelete` events don't exist yet at that point;
they are created by `QApplication::~QApplication()` during the C++ static destructor
phase, after Python has already started the shutdown sequence that will tear down TLS.

**`qapp.quit()` + `exec_loop()`** (quit before entering loop) — hangs. `qapp.quit()`
does nothing when the event loop is not running.

**`sys.exit(0)`** — same crash path as normal Python exit: triggers C extension cleanup
and C++ static destructors, including `QApplication::~QApplication()`.

**`del qapp`** — no-op. Python holds a reference to the C++ object; deleting the Python
wrapper does not destroy the underlying `QApplication`.

The root object — `QApplication` — is created and owned by FreeCAD's C++ side inside
`showMainWindow()`. Python cannot destroy it. No Python-level call sequence can prevent
`QApplication::~QApplication()` from running at static destructor time with TLS already
partially freed.

`os._exit(0)` is the correct workaround: it invokes the `_exit(2)` syscall directly,
which terminates the process without running any C++ destructors, atexit handlers, or
Python cleanup. All file writes are flushed before the call, so no output is lost.
