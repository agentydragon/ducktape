# Plaid Spend

The per-user CLI and daemon live in [`desktop/`](desktop/README.md), and the GNOME extension lives in `gnome/`.

`//finance/plaid/spend:server_image` serves the same backend-computed statement-cycle view to the Authentik-protected
browser UI and desktop clients. Card settings and the optional flexible allowance share one `spend-policy.yaml` in the
`plaid-spend-policy` Secret, generated by Finance Flux in the isolated `finance-spend-config` namespace and copied into
`plaid-mcp` by a Ducktape-owned ExternalSecret. Finance Flux has Secret-only permissions in its isolated namespace and
no write access in the app namespace. The canonical policy is `config/plaid-spend/spend-policy.yaml` in the private
finance-agent repository.

The browser at `/` signs in through the confidential Authentik `plaid-spend-web` client. Its tabs use hash URLs
(`/#/spending`, `/#/transactions`, `/#/sustainability`, and `/#/configuration`); the server only needs the root page route. The server keeps
OIDC tokens out of the browser and authenticates page, stylesheet, script, view, configuration, and event requests with
a signed session cookie. The GNOME panel and `plaid-spend` CLI use the separate public `plaid-spend-desktop` client and
Bearer-token API. Both desktop clients read the same global card view and notification-backed event stream.

## API

The response models in [`models.py`](models.py) and [`allowance.py`](allowance.py) define the wire contract. The running
service publishes their generated schema at `/openapi.json`; the browser generates its types from that schema. Money
values calculated by the service are integer currency minor units. Original Plaid transaction amounts in the
authenticated detail view remain decimal strings in major units.

- The shared spend configuration requires a root-level `time_zone` IANA zone.
  It determines local midnight for card, allowance, and sustainability reports,
  including when the allowance is disabled; `generated_at`, sync timestamps,
  and duration-based freshness stay UTC.
  Purchase days prefer Plaid's offset-bearing `authorized_datetime` converted
  to that zone, then `authorized_date`, then offset-bearing `datetime` (posting
  instant) converted to that zone, then `date`. Missing, malformed, naive, or
  exact-midnight timestamps fall back: Plaid documents default midnight times,
  which cannot reliably identify a purchase instant. Date-only values are used
  unchanged. This purchase day controls allowance activation, spend/pace windows,
  and transaction-list dates. Statement totals and classification `date_range`
  selectors still use the original Plaid `date`, exposed as `plaid_date` in the
  transaction row and its expandable details. A change to an existing policy
  shifts its next monthly credit instant; review that effect before rollout.
- `GET /api/v1/view` returns the card and allowance view. Optional `estimate_period_id=rolling_7d|rolling_30d`
  selects the allowance forecast and spending signal; omission uses the policy default.
- `GET /api/v1/transactions?period=rolling_30d` returns transaction explanations and a period summary. If a requested
  credit cycle is unavailable, the response identifies the actual `rolling_30d` period.
- `GET /api/v1/configuration` returns the loaded policy for the read-only Configuration tab without Plaid account IDs.
- Allowance views report unresolved full reversal pairs in their existing note field; transaction rows identify both matched legs. The
  Spending page shows unresolved pair issues even when the allowance is otherwise ready.
- `GET /api/v1/events` accepts the same optional estimate period and sends a complete `view` SSE event immediately and
  after `plaid_spend_changed` notifications; idle streams send heartbeat comments.

Each API route accepts the browser's signed session cookie or a Bearer token from the Authentik `plaid-spend-desktop`
OIDC client. The same handler serves both. Configuration is global to the service, so every authorized identity sees the
same view.

An unavailable statement period has no card total. A provisional period starts with the first recorded transaction and
is not a statement cycle. Minor units follow the currency's ISO precision (for example, USD cents and JPY whole yen).

The statement cycle starts the day after the latest credit-liability snapshot's `last_statement_issue_date`. A missing
date leaves cycle and spend values null and marks the card unavailable unless it can report a separately marked
provisional total since the first transaction; the service does not substitute calendar-month bounds. Posted and pending
amounts are summed separately, pending rows superseded by a posted transaction are dropped, removed rows and credit-card
payment transactions are excluded, and transactions with an explicit different currency are not included. Refunds retain
Plaid's negative sign. Spend percentage uses the configured limit; the alert becomes `warning` at its threshold and
`exceeded` at 100 percent. Card views identify both the Plaid account name and its institution when available.

## Shared card configuration

The private policy file follows `SpendConfiguration` in [`models.py`](models.py). Its `cards` list is required;
`allowance` is optional and can be omitted to disable the allowance.

Use `null` for an optional limit or threshold. The service validates this file at startup and reads it from
`/etc/plaid-spend/spend-policy.yaml`. Until the policy Secret exists, the pod cannot start; a missing or invalid file
fails application startup. Reloader restarts the Deployment after updating it; the process does not watch for mounted
Secret updates. The spend database role can only read the Plaid source tables needed to compute spending and portfolio values; it does
not store or write this configuration.

Each card's `label` is its short display name. For spending accounts that are not cards, an optional top-level
`account_labels` mapping in the same private policy supplies short names keyed by Plaid account ID. A missing mapping
falls back to the Plaid account name. Card IDs cannot also appear in `account_labels`, so each display name has one
configured source.

Allowance rules are evaluated in order; the first match determines the classification. A rule whose `scope` is
`one_off` corrects specific observed transactions and is validated as such — a bounded `date_range` plus a
name/category/amount condition, an `id`, and a note — but it is the same object matched in the same ordered list, not
a second tier, and it never addresses a transaction by Plaid transaction ID, which relinking rewrites. See
[one rule type, ordered](docs/allowance.md#one-rule-type-ordered-patterns-and-one-offs). `review` rules keep positive
purchases in provisional spending and the unmatched total, while unverified negative credits remain separate from
spending. Conditions can combine merchant or category matches, account type, merchant category code, counterparty type
and name, and amount sign. Private analyses use the same ordered matcher and policy file as the app. Required
`allowance.analysis_categories` entries map stable analysis-category codes to a display label and color; include
`unclassified` for purchases without a category. The Configuration API includes the catalog, and the Transactions
API includes each transaction's resolved category metadata. Display metadata does not affect rule matching or
allowance accounting.

For a confirmed full posted reversal, `allowance.reversal_pairs` can match the positive debit to its negative credit.
Both selectors must uniquely identify posted transactions with exactly opposite amounts in the allowance currency and
the same account; unresolved, ambiguous, pending, or overlapping pairs suppress neither leg. Partial refunds are outside
this feature. See [full reversal pair configuration](docs/allowance.md#explicit-full-reversal-pairs).

## Runtime settings

All service settings use the `PLAID_SPEND_` prefix except `DATABASE_URL`:

- `DATABASE_URL`
- `PLAID_SPEND_CONFIG_PATH` (default `/etc/plaid-spend/spend-policy.yaml`)
- `PLAID_SPEND_API_OIDC_ISSUER`, `PLAID_SPEND_API_OIDC_CLIENT_ID`, `PLAID_SPEND_API_OIDC_DISCOVERED_ISSUER`,
  `PLAID_SPEND_API_OIDC_JWKS_URI`, and optional comma-separated `PLAID_SPEND_API_OIDC_SIGNING_ALGORITHMS` (default
  `RS256`)
- `PLAID_SPEND_WEB_OIDC_ISSUER`, `PLAID_SPEND_WEB_OIDC_PUBLIC_BASE_URL`, `PLAID_SPEND_WEB_OIDC_CLIENT_ID`,
  `PLAID_SPEND_WEB_OIDC_CLIENT_SECRET`, and `PLAID_SPEND_WEB_OIDC_SESSION_SECRET`; optional
  `PLAID_SPEND_WEB_OIDC_SESSION_SECONDS` (default 28800)
- optional `PLAID_SPEND_HOST` and `PLAID_SPEND_PORT`
- optional paired `PLAID_SPEND_COINBASE__API_KEY` and `PLAID_SPEND_COINBASE__API_SECRET` settings. The
  deployed service receives these two properties from the existing view-only Coinbase credential Secret and signs
  Coinbase requests in memory.

The API resolver verifies Authentik RS256 access tokens against pinned issuer/JWKS metadata and requires the configured
audience and authorized party. The listener subscribes to committed `plaid_spend_changed` notifications from the
separate Plaid sync service.

## Experimental sustainability

`GET /api/v1/sustainability?window_days=90` and `/#/sustainability` show total mandatory, flexible and provisional
consumption annualized over complete days in the configured `time_zone`. Optional private `sustainability` configuration
selects the lookback windows, scenario reference rates, eligible asset/liability accounts, exact
`sources.plaid.holding_value_corrections` and `excluded_securities` selectors, Coinbase inclusion, documented effective
withdrawal-tax assumptions, and known coverage issues. Without this section
the page reports that the feature is unconfigured. Its classification rules and spending accounts come from the
existing allowance; history includes purchases before the allowance's activation date. Identified transfers, card
repayments and other excluded flows do not count as consumption. Explicit `include_excluded_categories` overrides
allow a separately reviewed exclusion to count here. Only negative transactions matching an explicitly listed
`confirmed_refund_rule_ids` rule offset consumption; other credits stay held outside spending.

Annualized spending is `net consumption × 365.2425 / covered days` and excludes withdrawal taxes. The optional
effective tax fraction is a share of gross withdrawals, so estimated annual funding is
`annualized spending / (1 - rate)`. A supplied rate requires a dated explanatory assumption. The displayed draw rate
is tax-inclusive funding divided by current eligible portfolio value, assuming no other income. Without a documented
tax assumption, funding and withdrawal percentages remain unavailable; consumption amounts are still available.
The reference markers are scenarios, not guarantees of lifetime sustainability.

`GET /api/v1/sustainability/windows` returns all configured windows from one transaction snapshot,
portfolio valuation and observation time. The page overlays their annualized trailing simple moving averages;
individual visibility checkboxes control curves independently of the spending-detail window selector below the graph.
That selector changes the headline gauge, scenario comparisons, spending breakdown and account-history coverage.
Portfolio valuation, tax assumptions and graph visibility remain shared. Detail selection is retained in the hash URL
and switches without fetching another snapshot.

The chart defaults to annual funding including withdrawal taxes. A local switch changes dollar labels to annual
spending excluding taxes. Withdrawal percentages remain tax-inclusive in both modes. Dollar and percentage axes
share the same canonical rate bounds and tick positions, fitted to visible curves and reference scenarios with
padding instead of anchoring at zero; the dollar conversion includes the tax fraction when showing consumption.
The switch cannot create a different apparent volatility or change the implied withdrawal percentage.
Tooltips compare a common endpoint with each curve's own inclusive dates including years, spending,
estimated withdrawal taxes, gross funding and required percentage. Curves retain independent startup dates and
coverage gaps; missing longer-window history does not truncate shorter-window curves.
Without a tax model, explicitly selecting spending shows dollars alone, with no reference-rate lines or percentage
axis. This linear conversion relies on the current fixed effective tax fraction and current portfolio denominator.

The headline annualizes the latest contiguous covered suffix ending yesterday when it is shorter than the selected
lookback, with a partial window label. It never averages disjoint known days across unknown history. Historical chart
points require the entire selected window: a 30-day point includes its endpoint and
the preceding 29 complete days. Startup windows are omitted to avoid annualizing one or two days of monthly bills.
Later windows crossing missing coverage are null, leaving visible gaps; earlier complete windows remain available
even when the current headline has no covered suffix.

By default, an account's first recorded transaction establishes an inferred history boundary, not its opening date.
Optional private `sustainability.account_history` entries separate account-opening evidence from documented complete
history. Keys must identify selected spending accounts. Both evidence types require a nonblank source and an `as_of`
date; neither Link creation nor requested Plaid history depth proves completeness. For example (synthetic only):

```yaml
account_history:
  example-new-card:
    opening:
      earliest: 2025-05-10
      latest: 2025-05-14
      source: User-reported approximate account opening, based on bank documents.
      as_of: 2025-07-01
    coverage:
      complete_from: 2025-05-10
      source: Independently verified complete history from account opening.
      as_of: 2025-07-01
```

Dates strictly before the earliest possible opening are known zero. Opening evidence alone leaves any interval from
that bound to the first recorded transaction unknown. A documented `complete_from` replaces the inferred boundary;
it is an explicit assertion of completeness, not a date derived automatically from successful sync. An unused account
can therefore have known coverage without transactions. A transaction predating the earliest opening bound is retained
and raises an evidence conflict that blocks funding estimates, including when observed on the current incomplete day.
The page identifies limiting accounts and expands their boundaries and evidence without exposing account IDs.
Plaid's Item-wide `HISTORICAL_UPDATE_COMPLETE` status confirms backfill completion, while `has_more=false` confirms
pagination drained; neither supplies an account's earliest available date.

Portfolio value is selected gross USD assets minus signed liabilities minus the current value of explicitly excluded
security positions. Holdings are not added to their account balances. Each Plaid holding-value correction selects an
exact account and one or more security IDs with a positive finite `value_multiplier`. Corrected holdings in that
account must reconcile to its balance. Exclusions contain selectors only; a matching correction is applied before an
excluded holding is subtracted, and corrections can also apply to included holdings. Enabled sources must be complete
and fresh for a percentage to appear. The Coinbase source covers returned brokerage
wallets and current USD spot quotes, including held quantities, not external wallets or every Coinbase product.
The backend signs view-only GET requests in memory, caches ready valuations for 60 seconds, and retries unavailable
reads on the next request.

Read-only analysis clients can reuse `plaid_valuation.value_plaid_rows` without importing the database or Coinbase
clients. The `portfolio_queries` SQLAlchemy Select builders select current active account balances and each account's latest complete holding capture
batch, with security metadata for allocation details. Convert transport timestamps to timezone-aware `datetime`
objects and pass holdings for the configured correction/exclusion accounts. The result contains the source status,
gross assets, signed liabilities and exclusions in USD cents; an unavailable source's zero totals must not be used.
`corrected_holding_value` applies the same exact-position policy corrections to allocation detail rows.

Every historical spending point uses **today's** eligible portfolio; historical asset values are not reconstructed.
Partial windows annualize only their contiguous covered days and are labeled. Inferred transaction boundaries are
not proof of complete linked spending. Asset
observations, transaction posting and transfer settlement can arrive at different times. Private `known_issues` notes
appear on the page alongside source errors. Historical asset-denominator charts and richer tax models remain
follow-ups. No financial-account writes are performed.
