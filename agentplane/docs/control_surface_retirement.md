# Agentplane control-surface retirement audit

Audit snapshot: 2026-10-15. This records confirmed callers and dispositions for overlapping
Session-control paths. It is evidence for the unfinished work in the [task DAG](../plans/task_dag.md#12-the-runner-gateway-serves-the-runners-own-service), not permission to remove a server API before its caller rollout gate.

## Caller-specific notes

Archive safety and Notification membership still rely on current live state and identity. Archive
refuses a live running harness and refuses when a present Pod cannot be checked; Notification checks
the current Sandbox UID and owner, then verifies the Session is in that incarnation. After #10619,
both callers send those expected identity values to `Runner.ListSessions`; `RunnerProxy` validates
them against the current Sandbox before forwarding. The checks are covered in the caller/proxy tests
and the migrated caller and receiver images are deployed in both environments. History's retained
namespace/name and last-observed harness state remain insufficient substitutes.

After #10622 the app has no `BatchGetSessionSandboxes` caller. `RunnerBridge.resume_thread` uses the
History-backed Sandbox name, lists live runner Sessions, then calls `SandboxRunner.resume`; the
Gateway's `ResumeSession` still requires a registry row for the current UID. Only Gateway
`CreateSession` writes that registry, so Dispatcher-opened Sessions fail at the final resume call.
App commands also use the Thread's History-backed Sandbox name and Dispatcher binds each command to
the current UID, without checking the Session's prior association. The latter remains an identity
contract to review; History's namespace/name is not an incarnation identity. Preserve the Gateway
UID/owner checks and do not infer a prior association from a same-name Sandbox.

## Reviewed surfaces with distinct semantics

- Dispatcher per-operation methods are sender-facing durable admission and delivery-state reads;
  runner per-operation methods execute the operation and journal its canonical admission. Similar
  method names are an intentional boundary, not duplicate queue APIs.
- Dispatcher `GetSessionOpening` reports the durable opening request; `GetDispatch` reports one
  command. `WatchDispatches`/`ListDispatches` expose commands, not session inventory.
- The inspected timeout settings are per-hop budgets: app and Notification caller deadlines,
  Dispatcher client and runner deadlines, Gateway admission and lifecycle deadlines, and runner
  stream/Quiesce bounds. They bound different work. The Gateway client command deadline is passed
  only to the unused `RunnerGatewayClient.command` helper; retire it with that wrapper after checking
  external and pinned callers.
- App and service Pydantic command-line options expose the same validated settings as environment
  and YAML inputs. No accepted-but-unused service flag was confirmed in this pass. Remove a setting
  only with its reader, deployment value and any pinned image gate together.

- The inspected destination fields are distinct: `SandboxDestination` carries owner, name and UID;
  `SessionDestination` adds the public Session ID. Dispatcher `Dispatch` and `SessionOpening` retain
  Sandbox name and UID separately to fence same-name recreation. History `SandboxRef` is only
  namespace/name and cannot replace that identity association.
- `RunnerGateway.SessionSandbox.sandbox_uid` is populated from the registry but is not read by the
  in-repository app caller. Keep its wire field until external/pinned reader usage is checked and
  the identity contract is resolved. `Command` remains shared by Dispatcher storage and the runner's
  `CommandAdmitted` event; retiring `DeliverCommand` does not retire the message. No other
  control-path field in the inspected `sandboxes`, `runner_gateway`, `session_dispatcher`,
  `history_service`, and `runner_control` schemas was confirmed safe to remove.

Before `CONTROL_SURFACE_RETIREMENT_AUDIT` is complete, trace field producers/readers and deployment
config for any newly identified candidate across generated clients, fixtures, guest wheels and stored
messages. A field with no current caller in one component is not dead on that evidence alone.
