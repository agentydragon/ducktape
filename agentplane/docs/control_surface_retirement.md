Audit snapshot: 2026-10-15. This records confirmed callers and dispositions for overlapping
Session-control paths. It is evidence for the unfinished work in the [task DAG](../plans/task_dag.md#12-the-runner-gateway-serves-the-runners-own-service), not permission to remove a server API before its caller rollout gate.

## Caller-specific notes

Archive safety and Notification membership still rely on current live state and identity. Archive
refuses a live running harness and refuses when a present Pod cannot be checked; Notification checks
the current Sandbox UID and owner, then verifies the Session is in that incarnation. After #10619,
both callers send those expected identity values to `Runner.ListSessions`; `RunnerProxy` validates
them against the current Sandbox before forwarding. The checks are covered in the caller/proxy tests
and the migrated caller and receiver images are deployed in both environments. History's retained
namespace/name and last-observed harness state remain insufficient substitutes.

After #10622 the app has no `BatchGetSessionSandboxes` caller. `RunnerBridge.resume_thread` uses the
History-backed Sandbox name, lists live runner Sessions, then calls `SandboxRunner.resume`; the
client invokes `Runner.ResumeSession` through the per-Sandbox proxy with current UID and owner
metadata. Dispatcher-opened Sessions can therefore use explicit resume without a Gateway registry
row. The legacy Gateway `ResumeSession` continues to require a row, and only Gateway `CreateSession`
writes it.
App commands also use the Thread's History-backed Sandbox name and Dispatcher binds each command to
the current UID, without checking the Session's prior association. The latter remains an identity
contract to review; History's namespace/name is not an incarnation identity. Preserve the Gateway
UID/owner checks and do not infer a prior association from a same-name Sandbox.

## `SessionOpening.attached`

`SessionOpening.attached` was copied from the runner's `OpenSession` response into the Dispatcher
row and echoed by `GetSessionOpening`. The app allowlist also includes Notifications, but no
Notification code calls this RPC; the app and frontend use opening state and reason, and the current
testing and staging app images (`devel-20261015233545-b8b2ba1`, Ready 1/1 and 2/2) have no production
read of `attached`. The frontend's optional field was unused. The only semantic reader was the
acceptance client's `wait_for_session_admission`; acceptance now reads the folded History Thread for
model, harness and cursor state. Runner `Attached` remains used by runner control and History and is
unrelated to this response snapshot.

#10675 reserved the `SessionOpening` response field and stopped writing or echoing the snapshot.
The nullable `session_opening.attached` ORM mapping remains until the writer-free Dispatcher image is
Ready in testing and staging. Then unmap it, wait for the unmapped-reader image in both environments,
and drop the physical column in a separate migration. #10699 allows the unused column to remain in
the database while absent from runtime metadata; a deferred ORM mapping is no longer required.
Migration starts before old pods drain in a rolling deployment. Opening identity, state, reason and
timestamps remain.

The HTTP/client paths likewise have distinct effects: app `POST /sandboxes/{name}/resume`
changes a Sandbox desired state, whereas `POST /threads/{thread_id}/resume` explicitly resumes
its native harness. The latter UI action stays when automatic resume-on-send is off; the suspended
indicator stays in both modes. `POST /threads/{thread_id}/commands` submits to Dispatcher, while
`GET /threads/{thread_id}/commands/{command_id}/dispatch` (`client.ts::commandDispatch`) reads
its status; `GET /sandboxes/{name}/sessions/{session_id}/opening`
(`client.ts::getSessionOpening`) polls a separate opening. None is a duplicate command sender.
The browser's old Sandbox session GET is already removed; retained Threads come from History.
