# Cold guest-root image import producer profile (2026-11-17)

## Finding

The largest observed VM-suite cold import, `agentplane-vm-guest-root:unset`, streams a 553,892,739-byte OCI layout through Python's `tarfile` into `k3s ctr images import`. A bounded one-image probe profiles the actual importer worker thread. Its baseline used 6.558 seconds of Python-thread CPU during a 26.104-second import call; `tarfile.copyfileobj` accounted for 6.541 cumulative CPU seconds, mostly `BufferedReader.read` (5.289) and `BufferedWriter.write` (0.949). The child-process CPU counters total 11.667 seconds across the `ctr` inventory and import calls, but do not identify client functions or distinguish the import client from the other `ctr` calls. The remainder of wall time cannot be assigned to pipe blocking, containerd, disk, or scheduling by subtracting overlapping process CPU counters.

Increasing `tarfile.open`'s stream and copy buffers from 10/16 KiB to 1 MiB cut read calls from 33,809 to 531 and write calls from 54,092 to 529, but changed importer-thread CPU only from 6.558 to 6.235 seconds. The candidate's import call took 29.977 versus 26.104 seconds in the control; the image span took 29.261 versus 25.472 seconds. Both are single observations on different RBE test workers, with different action input-fetch behavior. This rejects buffer sizing as a material optimization for the isolated guest-root import under the tested conditions; it does not establish that larger buffers cause a slowdown. The candidate code was removed.

The earlier [fresh 25-image VM profile](https://app.buildbuddy.io/invocation/1a8d57e8-08c4-44d8-8058-c97994132fbf) showed 212.769 seconds summed image spans and a 216.209-second serial import envelope. Its 420-second native containerd profile had 171.08 CPU seconds of samples, with 63.10 cumulative seconds under filesystem apply and 25.28 under import stream. Those overlapping daemon stacks and the long capture window cannot be assigned to this isolated image. Together with the new producer profile, the evidence puts the next cold-path investigation at the `ctr` client and containerd apply/content-write boundary, rather than at Python's per-block call count. It does not establish a storage-device bottleneck or a whole-suite speedup.

## Next decision boundary

`k3s ctr pprof` addresses containerd's debug socket; it profiles the daemon, not the short-lived `images import` client. No client profiler was declared in the probe's Bazel runfiles, and the repository's RBE Dockerfile does not install one; the base image was not inspected for extra tools. A prior [Bazel-supplied `linux-perf` attempt in RBE](../../../debug/2026_10_31_thread_browser_compute_profile.md) aborted with no samples; that was a different action context and does not prove `perf` cannot work in this Firecracker test. Before changing import policy or the image format, run a small capability check for a Bazel-declared process profiler in this exact Firecracker context, then capture the `ctr` client and a bounded native containerd window on the same cold image. Keep the current digest filtering, tag, CRI pin, and unpack/readiness checks. If sampling is unavailable, a declared syscall profiler can separate client reads/writes and pipe blocking, but its overhead must be measured and it cannot by itself identify device latency. The next optimization should be chosen from that stage attribution; neither the buffer experiment nor the prior aggregate Go profile justifies one now.
