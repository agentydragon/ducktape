# Cold guest-root image import producer profile (2026-11-17)

## Finding

The largest observed VM-suite cold import, `agentplane-vm-guest-root:unset`, streams a 553,892,739-byte OCI layout through Python's `tarfile` into `k3s ctr images import`. A bounded one-image probe profiles the actual importer worker thread. Its baseline used 6.558 seconds of Python-thread CPU during a 26.104-second import call; `tarfile.copyfileobj` accounted for 6.541 cumulative CPU seconds, mostly `BufferedReader.read` (5.289) and `BufferedWriter.write` (0.949). The child-process CPU counters total 11.667 seconds across the `ctr` inventory and import calls, but do not identify client functions or distinguish the import client from the other `ctr` calls. The remainder of wall time cannot be assigned to pipe blocking, containerd, disk, or scheduling by subtracting overlapping process CPU counters.

Increasing `tarfile.open`'s stream and copy buffers from 10/16 KiB to 1 MiB cut read calls from 33,809 to 531 and write calls from 54,092 to 529, but changed importer-thread CPU only from 6.558 to 6.235 seconds. The candidate's import call took 29.977 versus 26.104 seconds in the control; the image span took 29.261 versus 25.472 seconds. Both are single observations on different RBE test workers, with different action input-fetch behavior. This pair did not demonstrate a material improvement, so the candidate code was reverted. It does not establish that larger buffers cause a slowdown.

The earlier [fresh 25-image VM profile](https://app.buildbuddy.io/invocation/1a8d57e8-08c4-44d8-8058-c97994132fbf) showed 212.769 seconds summed image spans and a 216.209-second serial import envelope. Its 420-second native containerd profile had 171.08 CPU seconds of samples, with 63.10 cumulative seconds under filesystem apply and 25.28 under import stream. Those overlapping daemon stacks and the long capture window cannot be assigned to this isolated image. Together with the new producer profile, the evidence puts the next cold-path investigation at the `ctr` client and containerd apply/content-write boundary, rather than at Python's per-block call count. It does not establish a storage-device bottleneck or a whole-suite speedup.

## Controlled probe

Both runs used source base `c07d27d34de3c0dca3d0a0e5b13b9c220cc78933`, the same guest-root manifest digest `sha256:cfaffd76eeb7342e436e8dc60b4382c575963ad8035b873faca942b87ce2616a`, and the same layout-index SHA-256 `b927662deb62fa6f181feb5963b210156734f49ebf9e6cbb70fe1667ca6615bb`. The temporary Bazel test started one real K3s/containerd process in an isolated Firecracker action, asserted a distinct task-owned data directory and content store absent before start, then asserted all three OCI blobs present and the exact tag CRI-pinned and native-check usable after import. It ran the unchanged `K3s.import_images` from `ThreadPoolExecutor(max_workers=1)`, matching the suite's producer-thread placement. The probe did not install the rest of the VM stack or run guest workloads, so it omitted concurrent controller, service, and database load.

The profiler was stdlib `cProfile.Profile(timer=time.thread_time)` inside that worker. Its `pstats` output counts importer-thread CPU, including CPU spent inside its syscalls, with profiling overhead unmeasured. `time.monotonic_ns` brackets the entire `import_images` call; OpenTelemetry records the per-image UTC span separately. Linux `RUSAGE_CHILDREN` before/after is supporting CPU accounting, not a `ctr` profile. ## Native `ctr` client capture

`k3s ctr pprof` addresses containerd's debug socket, so a temporary Bazel target supplied the repository's existing `@trixie_vm_perf//:flat` closure and wrapped only the actual `k3s ctr images import` process with `perf record -e cpu-clock -F 49 -g`. It preserved the import command, stdin pipe, exit status, blob deduplication, tag and CRI pin checks. A separate [cheap capability action](https://app.buildbuddy.io/invocation/a19ffcb7-027e-4f7e-b0ab-0478ce90c36b) in the same Firecracker context first recorded 35 CPU samples with zero loss and resolved Python/OpenSSL symbols. The container had kernel 5.15.0, `perf_event_paranoid=2`, effective capabilities `000001ffffffffff`, and no `perf` or `strace` on its base PATH. Debian perf 6.12.73 worked when its ELF loader used the declared library closure without exporting that library path to the profiled child. An earlier probe leaked the Debian library path into `/bin/true` and aborted; that was a probe error, not evidence that `perf_event_open` was denied.

The [single cold client profile](https://app.buildbuddy.io/invocation/fec1c298-cecc-4e21-af92-a46c12a7965e) passed one physical remote TestRunner attempt with `doNotCache=true` and `--nocache_test_results` on worker `8860d3a6-c33b-4baf-9b01-6cc497da51dc`. The task-owned `/var/lib/k3s-import-client-profile-20261117-r3` and its content store were absent beforehand. The same 553,892,739-byte layout and manifest digest imported all three blobs, and the exact reference was CRI-pinned and native-check usable afterward. The importer call took 32.319 seconds by monotonic clock and its UTC image span 30.886 seconds. The TestRunner took 88.647 seconds and 192.377 CPU seconds, including the declared perf closure extraction, K3s startup and teardown; these are not comparable to the unprofiled pair as a speed estimate. Profiling overhead was not measured.

The 88,972-byte raw `test.outputs/ctr-import.perf.data` (SHA-256 `94a7ceb6f41a9b2b209f7cd13982e6743f832e077654f9120251eebb7eb41861`) contains 395 `cpu-clock` samples with zero lost. The in-action `perf report --stdio -n --no-children --sort comm,dso,symbol` output is 32,504 bytes (SHA-256 `b35876ac90b9d37f78a7baac909fed2d2b780cba58035ba0008439e6648cbc8c`). It attributes 310 sampled instruction pointers to `[kernel.kallsyms]` and 85 to the `k3s` DSO, all under `comm=ctr`. `finish_task_switch` has 152 samples and `_raw_spin_unlock_irqrestore` 88. These are sampled **CPU-clock instruction sites**, including scheduler boundaries; they are not blocked durations, disk-wait measurements, or fractions of import wall time. The `import-proof.json` SHA-256 is `55cbba129e6856d5d8d2dbdbb33b2f0643c3147993ad78be6024c0384598a750` and the matching `test-spans.jsonl` SHA-256 is `14ac82a1afea6c63c18196ccfc18bbd0dfa1b1a9ca70396cfbf29ab06eb1472b`.

The profiled `ctr` DSO was `/var/lib/rancher/k3s/data/df80f6eb827fe462e2eadc27897a605e8d1a97af7005d1dd9992eaa5d18eb1d4/bin/k3s`, with recorded build ID `dc2969762ccbee3e8c4ff22853b81a9db6d64f62`. The repository-pinned release asset has SHA-256 `ef1df26b26276c0f6d962391c94e12f9362d1f1e30ec7a7926e9ddb84b0d66ce` and GNU build ID `9a0eca4235ed510fe63e966b05affe17bb92d725`, so it is a different ELF. [K3s's pinned upstream `cmd/k3s/main.go`](https://github.com/k3s-io/k3s/blob/v1.34.12%2Bk3s1/cmd/k3s/main.go) stages its embedded asset before executing `ctr`. With the default K3s data directory absent on the analysis host, `K3S_DATA_DIR=<task-owned-absent-dir> <pinned-release> ctr --help` extracted the asset without starting a server or importing an image. The extracted directory name matched the capture's `df80f6eb...`; its `bin/k3s` has SHA-256 `8708d77af149a2715d02b0e5e1b05d96cec72298c04fdd3f3d3d947f93820157` and **the exact sampled DSO build ID** `dc2969762ccbee3e8c4ff22853b81a9db6d64f62`.

The repository's Bazel-managed `//devinfra/skills/reverse_engineer/examples:gosymtab` recovered 271,682 Go function symbols from that exact extracted ELF, preserving its build ID. A task-owned `PERF_BUILDID_DIR` then mapped the existing raw capture to the recovered ELF; host `perf report --stdio --no-children --sort symbol,dso -n` produced a symbolized report (SHA-256 `caaa3a607bee43c859e5d099bce5d10e45744841736a7984f93791226e6c0707`). Among the **85 directly sampled user instruction pointers**, 63 resolved to Go runtime/internal-runtime functions, 10 to gRPC/protobuf/HTTP2, two to containerd packages, and 10 to other functions. The largest individual user sites were `runtime.memclrNoHeapPointers` (10 samples) and `runtime.memmove` (four). These are direct IP counts, not inclusive call-tree costs. The 310 kernel IP samples remain best read from the in-action report, which used that action's kernel symbols; the later host report replaced their names with numeric addresses. Neither report measures off-CPU time. The symbolized report was parsed from the retained raw profile without a second import or a new profiling run.

## Reproduction source and next decision

The [control patch](cold_import_control.patch) and [1 MiB candidate patch](cold_import_buffer_candidate.patch) reproduce the two first probes on source `c07d27d34de3c0dca3d0a0e5b13b9c220cc78933`. The [client and capability patch](cold_import_client_profile.patch) reproduces the later probes on source `2351d263bcbec473b20f0cecafcaebc08cb2d892`. Each passed `git apply --check` on the stated base; their SHA-256 values are respectively `76682f1cfc3fdc8d3dc6a08ab6073f2abe237fa3155b84169b0ed91d5e386800`, `99be0dcf9a9044fca00ab08f97241ff6f124aa979929f048c425317c440a267a`, and `6025713992021f8681ecdbab72e9645d75397a5596e31b0ace226df6ebc86745`. The temporary targets, wrapper and buffer edit were not kept in production BUILD or importer code.

The client profile establishes that its sampled CPU is mostly in kernel instruction sites, while the decoded user sites are predominantly Go runtime work. It still does not distinguish off-CPU pipe backpressure, containerd apply/write wait, or physical device service. A short daemon capture aligned to the same import would narrow that boundary; a code optimization is not yet justified. Any future candidate must preserve the importer's missing-blob deduplication and digest/tag/CRI-pin/readiness contract.
