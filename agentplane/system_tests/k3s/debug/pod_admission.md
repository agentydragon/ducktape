# Pod suite admission budget

The completed [four-unit action](https://app.buildbuddy.io/invocation/bc8b6a85-f8f5-5fd8-93d9-9424c28a74e0) passed 19 of 20 cases. The messaging Codex sender was Unschedulable for insufficient memory and reached its 300-second readiness deadline. Services requested 1,734 MiB; every runner requested 1,568 MiB, including its isolated executor and running egress init sidecar. The Node had 9,724.5625 MiB and 7 CPUs allocatable: five runners fit, six do not. Retained runners remained alive while messaging requested four fresh runners. Native release/admission events agree with this arithmetic.

The case semaphore and protocol pair pool have independent limits. Two retained pairs, messaging and another fresh case can own ten runners, requesting 17,414 MiB and 8.24 CPUs including services. This bounds intended ownership with successful cleanup and suspend-before-resume; it does not bound leaks or actual RSS. Reducing CASE_LIMIT to one alone still permits an idle pair plus four messaging runners and cannot repair admission.

The [eight-unit trial](https://app.buildbuddy.io/invocation/8cf5c916-cbfe-4593-8e91-48fad41bbfb1) uses frozen source fb0ce2bfe8204287752f51e88bcd71c64ea1f235 with one rule-property edit. Native Action/Command decoding confirms identical input root, arguments and environment; EstimatedComputeUnits changes from four to eight. The completed failed control has the same input root. Native before-import and final snapshots agree on 19,543.824 MiB and 11 CPUs allocatable: 2,129.824 MiB and 2.76 CPUs above the request envelope. All 20 cases passed, with no failed scheduling events, and persistence cleanup completed. Physical action time was 555.348 s, pytest 532.183 s and input fetch 1.024 s. Setup took 221.126 s; the concurrent case window took about 257.398 s; stack cleanup took 38.497 s. The final source change applies the override only to test_pod; other targets keep their existing properties.

An earlier CLI-default attempt still emitted four units and was cancelled, so it is excluded. The first corrected rule attempt failed an external Go dependency download before tests; the identical retry produced the passing result above. Neither is a passing resource measurement.

This resource trial is separate from the negative Firecracker CPU experiment, which held RAM at 16 GiB and did not exhibit this Pod admission problem. The larger shape establishes capacity and execution at that boundary, not optimal sizing, fleet reliability or mean complete CI below four minutes. The passing 555-second action is about 194 s shorter than the failed 749-second control, with a doubled compute-unit reservation. Different cache/baseline histories and outcomes prevent a causal performance or cost estimate. Setup and scenario work still exceed the four-minute objective. The rollback is to revert the per-target override and macro passthrough; the known admission failure can then recur.

Exact public native artifact URIs, resource arithmetic, input identity and acceptance criteria are retained in [pod_admission.json](pod_admission.json).
