# VM early supervision scheduling finding

The simple separate-oneshot candidate changes the owner contract of the existing private real-systemd fixture. No Bazel, guest, or other execution test was attempted; this is a source and unit-ordering finding. It rules out this relocation arrangement rather than every possible way to overlap work.

`TestSystemdKernelFixture` reads the VM config and launch identity, then declares its owner as `agentplane-environment-runtime.service` with lifetime directory `/run/agentplane-environment-runtime-lifetime` and the production Runtime scope (`agentplane/env/runtime/supervision/systemd_kernel_test.go:44-70`). `SystemdLauncher` derives the lifetime marker from the caller's systemd `INVOCATION_ID` (`agentplane/env/runtime/supervision/systemd_launcher.go:167-174,256-266`); native child services bind to and order after that exact owner with `BindsTo` and `After` (`agentplane/env/runtime/supervision/systemd.go:164-170`, asserted at `systemd_kernel_test.go:664-672`). The Runtime unit creates that invocation's lifetime directory (`agentplane/env/images/systemd/agentplane-environment-runtime.service:7-17`). A new oneshot would have a different invocation and owner lifetime. Exporting or fabricating the Runtime invocation in another unit would no longer prove the production owner lifecycle.

The fixture's direct inputs are `/run/agentplane/config/environment-runtime.json`, `/run/agentplane/sandbox/launch.json`, the mounted `/state` filesystem (including its `/state/testing` receipt), and the system D-Bus manager (`systemd_kernel_test.go:44-70,809-825`; `systemd_launcher.go:116-123`). It does not read the harness home. However, the current Runtime start job is ordered after guest preparation, home preparation, D-Bus, and the cgroup observer (`agentplane/system_tests/vm/guest/environment-runtime-guest.conf:1-3`). Guest preparation also precedes `network.target`, while the shared Runtime unit is after `network.target`, creating a transitive barrier (`agentplane/system_tests/vm/guest/agentplane-guest-prepare.service:1-4`; `agentplane/env/images/systemd/agentplane-environment-runtime.service:1-5`). Home preparation is directly before Runtime (`agentplane/system_tests/vm/guest/agentplane-home-prepare.service:1-6`). Thus the current fixture starts only after those ordered preparations finish.

The existing wrapper runs the full Go test and requires the receipt before TLS-key isolation and `exec` of Environment Runtime (`agentplane/system_tests/vm/guest/environment_runtime_start:1-27`; `supervision_check:1-11`). This keeps Runtime protocol readiness behind successful proof and preserves missing-receipt failure. `test_vm.py` selects this private check only for Claude's guest, alongside a normal Codex guest (`agentplane/system_tests/suites/test_vm.py:40-59`).

A future overlap proposal must preserve the exact Runtime unit invocation and owner marker, keep the complete fixture and receipt gate before Runtime protocol readiness, retain the current preparation ordering and TLS-key isolation, and demonstrate missing/stale-receipt failure. It would need a systemd-supported way to begin the fixture while independent preparation proceeds without starting a separate owner or moving ordering into shell-side waits. Validate it on the manual boot-contract target with matched control/candidate invocations and a failure negative control, then confirm the live guest has no Runtime connection, Ready state, or session admission before proof. The measurements supplied with this task report all 11 Go children passing, with each taking about 1-2 seconds except the held-incarnation case at 4.75 seconds; total fixture time was 22.51 seconds. Those figures were not remeasured in this source-only pass.
