# What the synthetic slice arm exercises in cgroup v2

This note narrows what the [synthetic slice probe](standalone_kubevirt/synthetic_slice.md) establishes about the PID 1 stack seen in the separate pre-Ready failure. It does not attribute that failure to cgroup control updates or RCU.

## The conditional lock path in Linux 6.12.115

For a real change to `cgroup.subtree_control`, Linux 6.12.115's `cgroup_subtree_control_write()` updates the control mask and calls `cgroup_apply_control()`, which calls `cgroup_update_dfl_csses()`. That routine walks live descendants of the changed cgroup, skipping the changed cgroup itself, and adds each non-dead linked `css_set` to a preloaded source list. It sets `has_tasks` from whether that list is nonempty; the condition is not a direct check of `cgroup.procs`. The root cgroup is `cgroup_is_mixable()`, so enabling a controller at the root is allowed despite processes in the root cgroup. ([`cgroup.c`: root exception and write path](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/cgroup/cgroup.c?h=v6.12.115#n389), [`cgroup_update_dfl_csses()` and source-set collection](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/cgroup/cgroup.c?h=v6.12.115#n3093), [`cgroup_migrate_add_src()`](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/cgroup/cgroup.c?h=v6.12.115#n2802), [`cgroup_apply_control()`](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/cgroup/cgroup.c?h=v6.12.115#n3372), [`cgroup_subtree_control_write()`](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/cgroup/cgroup.c?h=v6.12.115#n3449).)

`cgroup_attach_lock()` always takes `cpus_read_lock()`, but calls `percpu_down_write(&cgroup_threadgroup_rwsem)` only when that preloaded list is nonempty. `percpu_down_write()` calls `rcu_sync_enter()`. When the `rcu_sync` state is idle, `rcu_sync_enter()` synchronously calls `synchronize_rcu()`; closely spaced entries can instead wait on a grace period already in progress. Thus, a trace containing `percpu_down_write()` within this update path proves that the conditional branch was taken. A controller state change alone does not. ([`cgroup_attach_lock()`](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/cgroup/cgroup.c?h=v6.12.115#n2490), [`percpu_down_write()`](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/locking/percpu-rwsem.c?h=v6.12.115#n224), [`rcu_sync_enter()`](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/rcu/sync.c?h=v6.12.115#n105).)

The guest reports Debian kernel `6.12.115-2`. Debian's [source package page](https://packages.debian.org/source/trixie/linux) identifies the upstream `6.12.115` source archive and Debian delta. The [`debian/6.12.115-2` source tag](https://salsa.debian.org/kernel-team/linux/-/tree/debian/6.12.115-2?ref_type=tags) lists one cgroup patch: a compatibility revert in `kernel/cgroup/cgroup-v1.c` for `/proc/cgroups`; the Debian delta does not modify the default-hierarchy path in `kernel/cgroup/cgroup.c`. Its common [kernel config](https://salsa.debian.org/kernel-team/linux/-/blob/debian/6.12.115-2/debian/config/config?ref_type=tags#L6563) enables `FTRACE`, `FUNCTION_TRACER`, `FUNCTION_GRAPH_TRACER`, `DYNAMIC_FTRACE`, and `KPROBE_EVENTS`. This is packaging configuration evidence; the proposed guest trace should first confirm that `function_graph` and the target functions are available at runtime.

## What the recorded synthetic transition proves

The successful synthetic arm sampled root `cgroup.subtree_control` as `memory,pids` before activation and `io,memory,pids` while its short service was active. The service's `agentplane.slice` appeared with `memory,pids` in its own `subtree_control`; the root's `io` setting remained after the service stopped. In v6.12.115, a successful root `subtree_control` change runs through `cgroup_subtree_control_write()` and `cgroup_update_dfl_csses()`, so this arm reached that update path. The captured state does not identify the writer or prove the conditional lock branch.

The records do not show whether a live descendant `css_set` was linked below root at the instant of the write, identify the writer, or capture a function stack. The later active-service sample does not establish that the service's `css_set` existed before the control write. Other guest descendants were not enumerated. Therefore this run does not establish that `has_tasks` was true, that `percpu_down_write()` or `rcu_sync_enter()` ran, or that an RCU grace period was slow. The approximately 1 Hz observer cannot recover a short call it did not sample.

## Small direct verification and repeat loop

Use a disposable, Runtime-masked direct guest. Start a bounded resident service in a descendant of the root cgroup and verify its PID's `/proc/<pid>/cgroup` path and membership in that descendant's `cgroup.procs`. Before each change, record `systemctl show -p IOAccounting` and root `cgroup.subtree_control`. Toggle a systemd slice's runtime `IOAccounting` off/on for two pairs, checking that the root `io` bit actually changes each time and that no child has `io` enabled in its own `cgroup.subtree_control`. A no-op property update is not an iteration; an `EBUSY` disable is a fixture/setup result.

For the first pair, enable tracefs function-graph tracing only around the controller writes. Check `available_tracers` and `available_filter_functions`, set `cgroup_subtree_control_write` in `set_graph_function`, cap `max_graph_depth` and the per-CPU trace buffer, and capture the PID/command shown for each call. Filter to PID 1 if the trace confirms systemd is the writer. Require the same call tree to contain `cgroup_update_dfl_csses`, `cgroup_attach_lock`, `percpu_down_write`, and `rcu_sync_enter`; retain the `synchronize_rcu` portion and durations as observed. If the tree stops before `percpu_down_write`, the source-set condition was not met and the test must not claim the RCU path.

Once the branch is proven, repeat actual on/off transitions (for example, 50 pairs under a fixed overall deadline) with the resident service held in place. Use bounded function-entry counters or a small filtered trace to count the relevant calls, and record root controller state after every operation. Rapid pairs can share an in-progress `rcu_sync` grace period, so vary spacing and report whether `synchronize_rcu()` was entered. Keep a separate uninstrumented repeat arm for stall-rate observations: function-graph tracing changes timing, and a clean finite batch would not rule out a rare stall.

This verification has not yet been run in the guest. It is a diagnostic proposal, not a repair or evidence that the original shutdown stall shares this cause.
