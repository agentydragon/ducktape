# Where Agentplane staging uses storage

The largest measured store on November 25 was the **166.55 GiB PostgreSQL backup bucket**. Its logical size rose **82.44 GiB (+98%) in 24 hours**. The backup directory inventory attributes **125.30 GiB to archived WAL (75%)** and **41.32 GiB to eight base backups (25%)**. In the live database, History events, sampler journal blocks and raw GitHub receipts together occupy **17.62 GiB, 74% of all database files**. The clearest duplication is inside History: 114 sampled JavaScript sends carried only a handful of distinct tool catalogs. Sharing that field projects to **~2.4 GiB** on one database instance. For raw webhooks, bounded blocks project to **~2.5 GiB**, with an additional **~0.14 GiB** available from grouping fields by column.

## Which bytes are worth changing?

**1. History: store the enabled tool catalog once per distinct value.** Of 29,018 ordinary kind-31 records in a follow-up count, 23,639 were larger than the [128 KiB decoded block limit](../history_service/internal/storage/blocks.go). They held **3.37 GiB, 96% of all ordinary boundary payload bytes**. Turning on the existing small-event packer more widely cannot reclaim those bytes. Nor is the new workload mostly repeated whole records: two sampled sets of standalone boundaries had no byte-identical bodies within either set.

In the two samples (179 and 118 records), **74% and 72% of stored bytes were JavaScript frames sent to the code host**. Provider events received and sampling results accounted for most of the rest. In the [code host execute request](../sampler/internal/codemode/wire.go), the nested field is `request.request.enabled_tools`. All 66 JavaScript sends in one sample had this field but only **six distinct canonical JSON values**; the other 48 sends had only **four**. Keeping a gzipped catalog once, a 32-byte reference per use and gzipped remaining frames cost **0.87 vs 15.94 MiB** and **0.58 vs 11.59 MiB** for the stored send records. Even against per-frame gzip, sharing saved **90–91%**. This models the JSON bodies; it excludes the outer protobuf envelope, table/index costs and exact-byte reconstruction metadata.

Weighting by the sampled share of boundary bytes gives **2.41–2.45 GiB per instance (~10% of all database bytes)** for a compact representation of the sends, if the samples generalize. Prototype this first. Intern the original serialized field in service-owned immutable storage and retain the surrounding bytes or a losslessly reconstructible frame. Verify hashes against the **original bytes**, since the probe compared canonical JSON. Keep cursors, call identity and authorization on the observation; a digest alone cannot authorize a read. Do not remove the catalog from the frame actually sent to the code host.

A lower-complexity alternative: compressing each complete protobuf independently with gzip level 6 took 13.16 MiB instead of 21.54 MiB and 9.76 MiB instead of 16.00 MiB: **39% less in both samples**. Applied to the 3.50 GiB ordinary boundary payload, that suggests **1.36 GiB per instance (5.7% of all database bytes)** before headers and page overhead. Use a versioned large-entry encoding with a bounded decode and the existing cursor index. Byte-compare decoded entries including unknown fields; measure CPU and point-read latency before changing ingress. Avoid a rewrite until WAL and free-space budgets allow it.

**2. Sampler: improve compression of blocks that already exist.** The 347,775 blocks held 11.12 million frames in **4.82 GiB of stored payload**. In two samples of 209 and 178 blocks, boundaries occupied 96% of decoded frame bytes. Recompressing the **same framed bytes**, keeping the current [block layout](../sampler/internal/eventcodec/event_block.go), reduced stored size by **13.2% and 14.2%** with level-6 gzip. That projects to **0.64–0.68 GiB (2.7–2.9% of all database bytes)**. This needs no new decoder; test compression CPU and p95 append latency against the current Go best-speed writer. Compare Zstandard on the same frames before adopting a second decoder. Deleting the exported sampler journal would have a much larger apparent payoff, but export acknowledgement alone does not preserve sampler continuation or independent restore.

**3. Notifications: decide how long the body must remain replayable.** A full scan counted 760,484 deliveries and **2.95 GiB of stored JSONB**. Bodies over three days old accounted for **1.90 GiB (64.3% of payload, 8.0% of database bytes)**. Prefer a shorter body lifetime for high-volume CI events after their normalizers have committed. Keep the delivery ID, digest, subject links, normalized facts and active inbox entries for their existing lifetimes. This requires an explicit compact receipt representation and tests for late subscription matching, retry deduplication and replay after raw expiry; changing the [single retention setting](../notification_service/README.md#github-event-retention) also shortens other guarantees. The 1.90 GiB is for **all** old bodies. Restricting the policy to workflow runs/jobs and check runs/suites accounts for **1.77 GiB** of that budget.

If seven days of raw replay matters, compression is a separate option. In two samples of 476 and 314 receipts, minified JSON gzipped per receipt used **45% less** than stored JSONB. Storing each distinct `repository` and `sender` subobject once, with 32-byte references and individually gzipped remainders, used **58% less** including the sample dictionary. Applied to seven days of payload: **1.33 GiB** for per-row gzip or **1.72 GiB** with the dictionary. The incremental opportunity for sharing is only **~0.39 GiB** before reference tables/indexes. The consecutive-window test below found a larger benefit from ordinary blocks without a shared dictionary. These ratios compare encodings of parsed JSON values, not original signed HTTP bytes. Verify numeric fidelity, missing versus null fields, and replay against the stored JSONB contract.

**4. Backups: change cadence only after a timed restore.** The eight bases averaged **5.17 GiB**. Six fewer bases at that average avoid **31.0 GiB (18.6% of the bucket)** before extra WAL retained to reach the oldest recovery point. The [chart supports weekly cadence](../../cluster/cdk8s/cnpg/backup.py); test restoration to both ends of the seven-day window and measure replay time. Most backup bytes are WAL: a **10% reduction in archived WAL volume** at fixed retention and workload saves **12.53 GiB (7.5% of the bucket)**. Attribute WAL growth to ingestion versus packing, pruning and full rewrites over a complete cycle before changing the archive policy. Do not extrapolate the 82 GiB jump as a daily rate.

**5. Sandbox reservations:** four reporting state claims together used 1.05 GiB against 40 GiB capacity. If peaks permit provisioning comparable future directory-state claims at 5 rather than 10 GiB, reserve **20 GiB less (50% of those claims; 8.5% of namespace capacity)**. A template change saves zero bytes on existing volumes. Check usage across builds, restarts and suspension, separate VM disk/checkpoint layouts and keep expansion headroom.

## What about columnar storage?

**Run the first block pilot on webhook receipts.** Sixteen windows spread through the live receipt position range each held 64 consecutive deliveries. Each cohort contained eight windows (512 receipts). The same parsed JSON objects were encoded three ways with gzip level 6. The column prototype grouped each top-level field into a list of (row ordinal, value) pairs, preserving absent versus null; all objects reconstructed equal in memory. This tests layout on real receipts, not a particular columnar engine.

| Representation                                  | Bytes in cohort A | Bytes in cohort B | Saving vs current | Projected saving on 2.95 GiB of payload |
| ----------------------------------------------- | ----------------: | ----------------: | ----------------: | --------------------------------------: |
| Stored JSONB datums                             |         2,111,585 |         2,120,654 |                 — |                                       — |
| One gzip member per receipt                     |         1,158,838 |         1,162,716 |               45% |                                1.33 GiB |
| One row-oriented gzip block per 64 receipts     |           314,747 |           345,508 |            84–85% |                           2.47–2.51 GiB |
| Same 64 receipts grouped by field, then gzipped |           213,618 |           243,868 |            89–90% |                           2.61–2.66 GiB |

Most of the measured benefit comes from sharing a compression window. Grouping fields adds **~0.14 GiB**, or 4.8% of current payload bytes, on top. Keep new receipts individually addressable until matched/normalized; seal by age with both a count and decoded-byte limit. Keep a position-to-block locator, membership checks and expiry timestamps outside the compressed body. Test a late delivery replay, single-position lookup and expiry of the oldest block. If shorter raw retention is acceptable, use it first and size compression on the remaining bodies; the 1.90 and 2.5 GiB savings cannot be added.

History's native-link, evidence, entity and manifest relations spend **1.91 GiB on main indexes**. These are good candidates to benchmark a sorted immutable segment keyed by session, kind and cursor, with delta-encoded offsets and a sparse block index. A 25% reduction in these indexes would save **0.48 GiB (2.0% of database bytes)**; this is a break-even budget for the experiment, not a measured engine result. Keep the live projection, inbox, deduplication keys, leases and transactionally committed outbox in PostgreSQL. Copying the same data into ClickHouse or Parquet for analytics without retiring the source increases retained bytes.

For a cold tier, compare bounded PostgreSQL blocks with Parquet/Zstandard row groups on object storage or a ClickHouse MergeTree sorted by the same access keys. Measure the whole retained set, including the locator index, tombstones, replicas, temporary parts and any still-required source copy. Replay by cursor, fetch one old tool result, scan by kind, expire one session, then restore both stores to the same watermark. A columnar move is justified only if it beats the simpler block representation at these reads and preserves byte-exact evidence and independent authorization. Existing checks for exact duplicate outputs [found one tool result](../plans/storage_representations.md#measured-targets) occupying 1.71 MiB across native, semantic and projected forms: sharing it could avoid **1.11 MiB (65%)** before references. That is a reason to share large bodies within an owner, not a fleet-wide deduplication ratio.

Savings here have different denominators. Retention and compression compete for the same receipt bytes. Ordinary vacuum lets PostgreSQL reuse pages; it does not generally return space to the filesystem. A rewrite needs room for both copies and generates WAL on the replica and in the archive. Validate a canary with physical relation bytes per million events, WAL per event, replay correctness, p95 read/write latency and CPU at matched load. Measure backup impact after a full retention cycle.

## Repeating the census

Read PVC capacity with `kubectl get pvc -n agentplane-staging`. For mounted filesystem usage use the maximum `kubelet_volume_stats_used_bytes` by claim, scoped to that namespace, so repeated scrapes do not add copies. Mark absent claims as unmeasured. Use the backup bucket's `SeaweedFS_s3_bucket_size_bytes` gauge for off-volume logical object bytes.

On a read replica, use a read-only connection with a statement timeout. Count each database once with `pg_database_size`. Inside each service database rank `pg_stat_user_tables` by `pg_total_relation_size(relid)`; heap, indexes and TOAST are components of that total. On the same replica compare the sum across databases and `pg_ls_waldir()` with filesystem used bytes. For representation estimates, sum `pg_column_size` of the stored column before extracting fields; do not add those sums to relation sizes. Aggregate probes need no transcript, webhook body or session identifier in their output.

The encoding probes ran on the replica in memory and returned totals only. For seeds 25 and 26, use PostgreSQL SYSTEM page samples of 0.5% for ordinary boundaries (kind 31, ≤2 MiB, limit 240), 0.05% for sampler blocks (limit 240) and 0.06% for receipts (<1 MiB stored, limit 650). Compare the sum of stored column bytes with the sum of candidate encodings for those same rows. Page sampling can cluster related events; the two estimates are sensitivity checks, not confidence intervals. Repeat across days before sizing a rollout.
