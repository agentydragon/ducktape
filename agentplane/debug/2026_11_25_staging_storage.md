# Where Agentplane staging uses storage

The largest measured store on November 25 was the **166.55 GiB PostgreSQL backup bucket**. Its logical size rose **82.44 GiB (+98%) in 24 hours**. Start by separating retained base backups from archived WAL. For the live database, focus on History and the sampler: together they accounted for **99.4% of database growth** in the measured November 24 interval.

The 16 bound claims comprise seven 10 GiB state/workspace pairs and two 48 GiB database instances. Six sandbox claims lacked filesystem gauges; their usage is unknown. The reporting workspace maximum was 4.16 GiB; the largest reporting state claim used 0.75 GiB. Of the sandbox capacity, 120 GiB used the local HDD class and 20 GiB the replicated SSD class. Both database instances used local SSD. The standby holds a second copy for failover and reads.

The two database filesystems and eight reporting sandbox filesystems used **61.59 GiB** combined. The backup bucket alone was **2.7×** that size. The [backup policy](../../cluster/generated/agentplane-staging/db-backups/db-backups.k8s.yaml) takes daily base backups and archives continuous WAL, both gzip-compressed, with a seven-day recovery window. One day's net bucket change includes arrivals and expiry; it does not measure WAL generation. The bucket and PVC figures exclude backend replication, node images, ephemeral storage and shared monitoring. GiB means 2³⁰ bytes.

## What the existing measurements establish

The [November 24 census](../plans/storage_representations.md#november-24-recurrence-and-storage-decision) attributed 4.37 GiB/day (54.7%) to History and 3.57 GiB/day (44.7%) to the sampler. At that snapshot, their ordinary event tables occupied 6.57 and 4.63 GiB respectively, including indexes and TOAST. A day's growth is neither a steady-state forecast nor a count of duplicate bytes.

There is evidence of duplication, beyond similarly sized tables. The [November 13 comparison](../plans/storage_representations.md#measured-targets) found the same tool output in a native event, its semantic completion and the rendered projection: **1,792,111 stored bytes** across the three. Keeping the largest representation once would avoid about **1.11 MiB (64.7%)** for that example before references and framing. Conversely, deduplicating whole projection chunks within their own table would have addressed only about 7 MB out of 476 MB (1.5% of that table). Neither sample estimates whole-database savings. The old full-request snapshots and redundant successful audit arrays have already been addressed; do not book those savings again.

## Options and expected benefit

**Backups first:** get compressed bytes by completed base backup and by WAL day from the backup catalog. Verify that expiry runs and that the oldest retained base supports the recovery window. Before changing cadence, restore to the end of the window and time WAL replay. Moving from seven daily bases to one weekly base would avoid about six base copies per week while retaining continuous WAL. For example, at **5 GiB per base**, six fewer bases would mean **30 GiB (18% of today’s bucket)** before extra WAL needed for the older recovery anchor. This is a sensitivity estimate, not a measured base size or a forecast; cutting cadence has little benefit if WAL dominates. The [CNPG backup chart](../../cluster/cdk8s/cnpg/backup.py) already supports weekly cadence.

These benefits have different denominators. Packing and content sharing may compete for the same bytes; shorter retention reduces the data available to deduplicate. Deleting rows ordinarily makes pages reusable inside PostgreSQL. Returning bytes to the filesystem requires a separately planned rewrite with room for both copies, WAL, and replica lag; it does not lower the PVC size. Compare `pg_total_relation_size` before and after maintenance, and measure backup bytes over a full retention cycle before counting a backup benefit.

## Repeating the census

Read PVC capacity with `kubectl get pvc -n agentplane-staging`. For mounted filesystem usage use the maximum `kubelet_volume_stats_used_bytes` by claim, scoped to that namespace, so repeated scrapes do not add copies. Mark absent claims as unmeasured. Use the backup bucket's `SeaweedFS_s3_bucket_size_bytes` gauge for off-volume logical object bytes.

On a read replica, use a read-only connection with a statement timeout. Count each database once with `pg_database_size`. Inside each service database rank `pg_stat_user_tables` by `pg_total_relation_size(relid)`; heap, indexes and TOAST are components of that total. On the same replica compare the sum across databases and `pg_ls_waldir()` with filesystem used bytes. For representation estimates, sum `pg_column_size` of the stored column before extracting fields; do not add those sums to relation sizes. Aggregate probes need no transcript, webhook body or session identifier in their output.
