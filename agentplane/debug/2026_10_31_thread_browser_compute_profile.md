# Thread browser test compute profile

## Finding

The current `//agentplane/app:test_thread_browser` run spent most of its test-case time in pytest fixture setup. The slowest individual cases were expensive because they were the first case in their shard and therefore carried that shard's session-scoped fixture initialization. Each shard starts the shared app database and a logical-WAL history database/template; each test also starts a fresh Electric service and browser/app fixture stack. This is evidence of repeated setup work, but the available profiles do not attribute its CPU to Python, PostgreSQL, or Electric, so no code optimization or savings estimate is justified yet.

## Evidence

The successful baseline invocation [`f0c59d85-d192-5dfd-8140-ef12fb71cb16`](https://app.buildbuddy.io/invocation/f0c59d85-d192-5dfd-8140-ef12fb71cb16) had 16 fresh `TestRunner` shards: 1,572.159 process-seconds, 3,131.374 CPU-seconds, and a 137.581-second longest shard.

I ran the complete target on the current `origin/devel` checkout at `7bedf6a9c03d8e827747ad5b77a8dc6aed111d49`, with all 50 browser cases enabled and `--nocache_test_results`. All 16 RBE shards passed. The BuildBuddy invocation is [`6ca19414-fe78-4b9e-a0cd-9e5641e95ec1`](https://app.buildbuddy.io/invocation/6ca19414-fe78-4b9e-a0cd-9e5641e95ec1). Its `TestRunner` executions sum to 1,572.709 process-seconds and 3,153.509 CPU-seconds; the slowest shard took 122.065 seconds. The Bazel profile reports a 124.84-second critical path. The near-equality of aggregate process time to baseline is not a before/after claim: the runs use different commits, and this run added diagnostic output and sampled browser profiling.

JUnit durations sum to 1,249.406 seconds. Pytest's `--durations=0` phase totals are 957.22 seconds of setup, 141.50 seconds of test calls, and 150.67 seconds of teardown, summed across all cases and shards. Setup is about 77% of that summed test-case duration. The first case on each shard has 33.32–66.82 seconds of setup; those 16 setup charges sum to 781.78 seconds. The other 34 cases sum to 175.44 seconds of setup, about 5.16 seconds per case. These are overlapping per-test durations, not wall-clock savings.

The underlying fixture graph explains where that setup is charged. `postgres_container` and `app_database_template` are session-scoped per Bazel shard. `thread_browser_postgres` also starts a shard-local PostgreSQL server configured for logical WAL and migrates a history template. `electric` is function-scoped and starts a new Electric process against a database clone for every test. The page and `thread_browser` fixtures are function-scoped as well. The RBE `container_setup.log` artifacts show one `postgres:18` image load per shard taking 8.8–18.7 seconds (228.8 seconds summed) and readiness taking 2.0–7.5 seconds (46.0 seconds summed). Those durations overlap across shards and are not CPU measurements. The custom logical-WAL PostgreSQL startup is not timed in that artifact.

Four Chromium CDP CPU profiles were collected for the hottest baseline cases. They cover only 2.17–6.04 seconds each. The hook started inside the `thread_browser` fixture, after pytest resolved its dependencies, so it excludes the large first-case setup phase that dominates the durations above. The renderer profiles therefore do not explain the full case cost. I reviewed the phone-raw `following`, `reading`, and `resumed` screenshots; they show the expected tail-following, detached-reader affordance, and resumed-tail states.

A temporary, environment-gated Go `runtime/pprof` capture was added only for one bounded diagnostic rerun. The selected `test_thread_follows_bottom_until_reader_scrolls_up[phone-raw]` case passed on shard 1, and its Go app profile covers 5.45 seconds from app startup through shutdown. It contains 160 ms of CPU samples (16 samples at 100 Hz); that is too little data for a reliable hotspot ranking. The app process starts after the expensive fixture dependencies, so this profile also excludes their CPU. The wrapper invocation [`4257c40d-85db-47d0-9afc-1e7f79bdb250`](https://app.buildbuddy.io/invocation/4257c40d-85db-47d0-9afc-1e7f79bdb250) failed overall because the pytest `-k` filter left 15 fixed shards with no matching items, which this repository's sharding plugin treats as an error. The selected shard itself passed and uploaded the profile. Use `--test_sharding_strategy=disabled` for a one-case profiled rerun.

I then captured stdlib `cProfile` with `time.process_time` around `pytest_bazel.main()` for that one selected case, with sharding disabled. The case passed in invocation [`3f67d630-33bf-4783-b6ad-4541d183f4a6`](https://app.buildbuddy.io/invocation/3f67d630-33bf-4783-b6ad-4541d183f4a6), which retained `test.outputs/thread-browser-fixtures.cprofile`. The profile reports 7.131 seconds of pytest-worker CPU across 3.26 million calls. Its largest self-time entries are buffered reads (2.184 seconds), `compile` (0.722), buffered writes (0.573), and garbage collection (0.324). The fixture implementation itself has very little Python self CPU in this capture: `thread_browser` is 0.0007 seconds, `electric` 0.0002, `http2_proxy` 0.0003, and PostgreSQL connection setup (`psycopg._connect_gen`) 0.036. This points away from Python work in the test worker as the source of the long setup wall time, but it does not measure Dockerized PostgreSQL or Electric CPU. Profiling began after test-module imports, includes pytest collection and fixture setup/call/teardown, and adds profiler overhead. Async cumulative timings are overlapping and were not used for attribution. The temporary wrapper was removed after collecting the artifact.

I also supplied Debian `linux-perf` through a temporary Bazel apt closure and tried a system-wide `perf record -a -F 99 -g -e cpu-clock` around that same real RBE browser case. The selected test passed in invocation [`2fdb7944-2ea1-4c73-a400-056572d65557`](https://app.buildbuddy.io/invocation/2fdb7944-2ea1-4c73-a400-056572d65557) through the wrapper's unprofiled fallback. Its `perf-capability.txt` artifact shows that even a `/bin/true` preflight made `perf record` abort with `SIGABRT` (`*** stack smashing detected ***`) after writing a file. A subsequent real recording attempt, invocation [`f09a5241-63b4-4b4d-9c6f-10c53ebb79b0`](https://app.buildbuddy.io/invocation/f09a5241-63b4-4b4d-9c6f-10c53ebb79b0), ended with profiler exit `-6` and no recorded child exit. Its 54,980-byte `thread-browser.perf.data` file is readable by `perf report`, but `perf report --stdio` says it has no samples. The header records perf 6.12.73 on the RBE host's 5.15.0 kernel, the requested `cpu-clock` event, and zero first/last sample times. The remote command launched perf through the loader and library path extracted from the same Debian package closure. This is a profiler failure, not evidence that system-wide sampling succeeded or that the test passed under profiling.

## Scope and next measurement

The Bazel profile and BuildBuddy execution statistics establish aggregate RBE time and CPU but do not provide Python or container-process stacks. The CDP profile covers only the Chromium page's V8 isolate, while the Go pprof profile covers only the Agentplane app process. Both omit Dockerized PostgreSQL and Electric CPU. The Bazel-supplied host profiler produced no usable samples because it aborted during recording; a separate guest test also showed `perf_event_paranoid=3` and denied CPU-clock access to the restricted Runner service (invocation [`a394fe63-0e05-4287-8748-08edfbc2228a`](https://app.buildbuddy.io/invocation/a394fe63-0e05-4287-8748-08edfbc2228a)). These are distinct execution contexts. No change to tests, fixture scopes, shard count, or production code is proposed from this evidence. A working CPU profiler with usable samples is still needed before attributing the setup cost to a specific backend component. The existing eight-shard comparison was not repeated; its previously recorded compute saving and longer maximum shard duration remain the relevant trade-off.
