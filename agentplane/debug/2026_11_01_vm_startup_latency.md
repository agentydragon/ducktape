# VM startup latency prior-work audit (2026-11-01)

This audit separates production `environment-vm` startup from the Debian/QEMU
VM fixture used by `test_vm`. Existing product boot and image work has already
removed several known costs. The remaining product question is which phase,
if any, still dominates a fresh NixOS VM start. CI fixture timings do not answer
that question.

## Latest CI observation

The [1 November CI latency report](https://github.com/agentydragon/ducktape/blob/gh-pages/latency/index.html), its [evidence](https://github.com/agentydragon/ducktape/blob/gh-pages/latency/evidence.json), and [manifest](https://github.com/agentydragon/ducktape/blob/gh-pages/latency/manifest.json) cover 02:30–21:45 UTC and source `de5f671002f516e952c3dfafcbf06659a4bc731b`. The report-only [#13550](https://github.com/agentydragon/ducktape/pull/13550) verifies that the preceding implementation merges are ancestors of both selected test sources. The earlier [#13487 snapshot](https://github.com/agentydragon/ducktape/blob/a7aba03c0c745de172872fda1393303cbd55dd70/latency/index.html) is retained as historical context; its chronology was inconsistent, so merge ancestry is used for intervention presence.

Two ordinary devel VM test actions took 425.0 s and 343.9 s. Their computed Bazel critical paths were 444.4 s and 361.2 s. VM setup spans were 167.1 s and 103.1 s; case envelopes were 229.1 s and 204.2 s. The VM action ran a Debian 6.12 EROFS guest under QEMU TCG with one vCPU on RBE, not the production NixOS guest on a KVM-schedulable node. The case envelope includes scenario provisioning, guest execution, and cleanup. It is not VM startup. Cache, source, and worker conditions differ, so the pair has no matched treatment effect.

Within those test runs, guest Ready took 77–110 s, native Codex start 36–41 s, and final guest cleanup 25–35 s. These spans identify fixture activity, not removable waits or production bottlenecks. The report's 371/696 s green-head p50/p90 is a PR feedback proxy; its conditional gate-headroom calculations are not measured savings.

## Bounded product measurement still needed

The staging [fresh VM acceptance](../docs/vm_sandboxes.md#fresh-vm-trial-readiness) records claims binding, launcher Ready, Runner connection/bootstrap, and readback markers, but no durations. There is no current end-to-end production NixOS/KVM start trace. Therefore no remaining production optimization is demonstrated yet.

Measure one ordinary fresh production `environment-vm` Sandbox start on a KVM-schedulable node, recording the exact guest image digest, node, storage class, and whether the image/cache state is naturally cold or warm. If naturally available, capture a warm follow-up on the same node and image. Do not evict caches, delete nodes, or discard guest/user state to manufacture a cold run. Correlate existing Kubernetes object timestamps/events and launcher/guest/Runner evidence across Sandbox request, PVC binding, VM/VMI scheduling and start, guest boot, Runner Ready/bootstrap, and the first safe useful Session action. Reuse `vm-phases`/K3s traces only to understand their fields; they do not substitute for this production run. If an essential phase is not observable, add only its smallest timestamp at the owning boundary.

The measurement should say which phase is on the critical path and whether a product bottleneck is actually present. If image pull dominates, inspect current NixOS root-image bytes and node-cache state before considering further closure trimming. If guest boot dominates, identify the owning NixOS unit or CPU/I/O wait before proposing a guest change. If native-session startup dominates, compare the current overlap path while preserving the executor-readiness gate. If no phase dominates or the needed cold state was not observed, record that limit and stop without selecting an image/layout redesign. Any implementation proposal should name one mechanism and owner, preserve KVM scheduling, storage/state ownership, and Runner/bootstrap/readiness behavior, and include a same-image matched validation plan.

CI has a separate possible mechanism: a versioned prepared K3s baseline could reuse immutable K3s/KubeVirt/Kyverno/certificate-controller setup and validated image state while keeping namespaces, databases, credentials, certificates, PVCs, and Sandboxes fresh. The latest 103–167 s setup spans are only ceilings on repeatable work, not savings. Any experiment needs digest and unpacked-state guards, cleanup ownership, a cold-install target for baseline-input changes, and periodic cold validation. This is a CI-fixture opportunity, not production VM startup work or a prerequisite in the product DAG.
