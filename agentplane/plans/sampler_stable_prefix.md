# Stable provider prefixes for sampler conversations

**Status:** design for operator review; no implementation is authorized by this plan.

The goal is that a sampler rollout cannot invalidate reasoning already sent for a Thread. The operator has accepted that Threads already broken by #15591 stay broken; this design adds no repair or migration for them.

## Current requests and stored state

The route is pinned to one provider API per conversation. At each turn boundary, the sampler builds a native request from route configuration and durable conversation state, then sends the complete projected input. It does not use Anthropic Message Threads, OpenAI `previous_response_id`, or the Conversations API today.

- **Responses:** [`prepareProviderRequest`](../central_sampler/internal/sessionstore/provider_request.go) builds `instructions` from the shared `protocol.BaseInstructions`, a leading developer input from the conversation's stored instructions, and tools from the current `toolcontract.ModelSurface`. Standard routes put tools in `tools`; Lite routes put them in a leading `additional_tools` item. The rest of `input` is projected from the stored native Responses context, including opaque reasoning, tool calls and results. Requests use `store: false` and a Session-scoped prompt-cache key.
- **Anthropic Messages:** the same preparation path builds top-level `system` from `protocol.BaseInstructions` plus stored conversation instructions, one `exec` tool from the current tool surface, and `messages` from stored native Messages records. Signed thinking and other provider blocks remain opaque.
- **Persistence:** each prepared call has a `sampler_model_request` row with a profile reference, native context references, and ordered prefix/suffix item references. `sampler_content` holds deduplicated request profiles, instructions, tool definitions and native records. `sampler_context` retains the ordered conversation chain. This is Agentplane-owned continuation state; retries reconstruct the frozen prepared request from it.

There is already partial prefix freezing in current `devel`: `previousRequest` selects the latest profile, `FreezeRequest` restores its top-level instructions/system and tools, and Responses Lite also reuses the first stored `additional_tools` item. Prior native history is extended rather than rebuilt. A changed tool surface is therefore held at the old value in an existing conversation; it reaches new conversations only. The freeze is implicit in repeated request profiles, not an explicit conversation baseline, and it does not freeze every route field. Model, reasoning/output options, and other provider settings are rebuilt from the current route configuration. The Anthropic live test asserts empty `input_transformations` during compaction and restart, but does not change a tool description; no Responses test asserts that field. The Anthropic adapter retains a TODO describing the older unfrozen path; remove it with the eventual implementation. Static inspection is not behavioral proof.

Staging sets Anthropic `thinking.block_binding.prefix_mismatch_behavior` to `error`. Official docs were unavailable during this pass. The prefix break modes below are copied from the dated survey formerly in [`task_dag.md`](task_dag.md#unblocked) and are not revalidated live:

| Route              | Prefix mutation and provider result in the checked-in 2026-11-14 survey                                                                                                                                                                     | Current guard                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Anthropic Messages | The survey says changing top-level `system`, any tool definition, or an earlier `messages` item invalidates signed thinking; `error` returns 400 and `drop_block` discards that block and later blocks. It reports tool-list order is safe. | Current code freezes `system` and `tools`; persisted message projection appends history. New messages appended after the old input are the safe shape to investigate. Rewriting or reordering already-sent content is never the update strategy. A rollout that changes an unfrozen field must preserve the old value or start a new provider conversation.

## Designs

1. **Freeze the first request for the life of the conversation.** This is the simplest portable rule and largely matches current code. Reuse the first request profile as the immutable baseline; every code rollout applies only to new conversations. No new table is needed if the first `sampler_model_request.profile_id` remains the baseline. Existing Threads continue with their old prompt surface. The cost is stale tool/instruction text in long-lived Threads.
2. **Frozen baseline plus append-only updates.** Keep the initial rendered profile immutable, then apply a changed tool or instruction surface only at the next settled turn boundary and only through a provider form verified for that route. This is the recommended target: it preserves old reasoning while allowing supported changes to reach existing Threads. A new `sampler_conversation_prompt` row could hold `baseline_profile_id`, baseline hash, and the applied surface revision/hash; it would reference existing `sampler_content`, not duplicate prompt bodies. Persist provider update items in the same native context/request journal and commit the revision with the prepared request. Added tokens, provider betas and per-route adapters are the cost.
3. **Provider-managed Threads/Conversations plus native updates.** Let each provider own more of the Thread state and use its update forms when available. This could reduce repeated input transfer, but it adds remote lifecycle, retention and outage dependencies, and still needs Agentplane's local canonical history for recovery. Message Threads are identified as beta; OpenAI state guarantees and both providers' costs remain unverified. Do not make provider state the only copy.

### Recommendation

Use design 2 with design 1 as its safety fallback. Make the rendered first-request profile an explicit immutable baseline; compare the current surface at a settled turn boundary; append only a documented update; otherwise keep the current surface for that Thread and apply the new surface when a new provider conversation is created. Never mutate an earlier message, change a bound top-level field, use `drop_block`, or treat provider-held state as the only transcript. The current profile/content store should be reused; add only the small baseline/revision row if operator review confirms it is needed. Provider-side state remains an optional transport optimization after live verification.

A tool or instruction update is staged with the next new sampling intent, after all earlier tool effects settle. The transaction records the exact appended update and request before dispatch, so retries and restarts send the same bytes. An unsupported update remains pending for a new provider conversation; compaction is not a boundary unless provider documentation explicitly guarantees that it resets the prefix binding.

## Acceptance test

Use a Store/request test for byte-for-byte prefix and retry/restart persistence, plus an opt-in live provider acceptance test for each API. Start with tool description v1 and preserve reasoning; after a simulated rollout renders v2, send v2 only through a provider-documented append-only form. The provider must accept continuation, the previous reasoning item (including Anthropic's signature) must remain byte-identical in stored native context, and `input_transformations` must be empty on both APIs. Restart between turns and verify the exact update is replayed. If a provider has no verified update form for the difference, assert that v2 stays deferred, the old prefix is unchanged, and a new provider conversation starts with v2. The live test is what demonstrates provider semantics; a fixture alone cannot.
