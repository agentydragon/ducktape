# Service SVID authentication inventory

This is the stage-one inventory for `PRIVILEGED_BACKEND_AUTH_DESIGN` (operator decision,
2026-11-14). The approved direction is one first-party service authentication mode: service SVID
client authentication over mutual TLS, with verified server TLS on every service hop. The inventory
records the current deployment so receiver admission and caller migrations can be dispatched as
small roll-safe changes. It does not imply that the target API or credentials are implemented.

## Target authorization contract

A backend component presents a certificate naming its exact service SPIFFE URI. The receiver
authenticates that peer as a distinct service principal and applies the method's explicit service
caller allowlist. A service URI is not an agent `Identity`, a Kubernetes ServiceAccount, or a
`WorkloadCredential`; it carries no ServiceAccount UID or Pod proof. Do not synthesize either to
reuse today's `auth.Account` or `auth.Principal` allowlists.

For an operation on behalf of an Identity, retain three values independently: the authenticated
service principal, the effective Identity (including its live UID), and typed provenance. A
delegation grant is explicit and method-scoped. A direct service call uses only the service
principal. The proposal uses `auth.ServicePrincipal{SPIFFEID}`, `ServiceAdmission`,
`DelegatedServiceIdentityAdmission`, `Rule.AllowServiceCallers`, and
`AllowServiceDelegationFrom`; these names describe the intended contract and are not current APIs.
The existing workload SVID path continues to resolve Sandbox and standing workloads as
`IdentityPrincipal`s, and operator or durable MCP Connection authorization remains at its existing
boundary.

proxy-to-Runtime hop; they are separate from the Kubernetes ServiceAccounts currently admitted at
the shared Gateway listener. The exact SPIFFE IDs are `spiffe://agentplane/sessions`,
`spiffe://agentplane/runtime-proxy`, and `spiffe://agentplane/environments`. They are method-scoped
service identities, not Kubernetes ServiceAccounts, and must not become one Gateway-wide allowlist.
Today the Dispatcher calls the per-Sandbox Runtime proxy with its projected Gateway-audience bearer,
and the proxy calls the native Runtime over the existing `spiffe://agentplane/runner-gateway` mTLS
connection. That control connection remains until its separate cutover. These roles describe the
planned authentication boundaries; this inventory does not claim that the callers currently present
these certificates or that Runtime currently admits them.

## Transport and issuer facts

The deployed certificate helper `cluster/cdk8s/agentplane/workload_tls.py` issues service serving
certificates with `serverAuth` only. Its separate `client_certificate` helper issues `clientAuth`
only and currently serves Sandbox Controller/runner paths. Neither helper yet provides the general
service caller credential and lifecycle required by the target. The workload CA already admits
one-segment service URIs, but a certificate being issuable does not mean a receiver trusts it as a
caller.

Transport holes that must be explicit in receiver/caller staging are:

- App → Policy Service is plaintext in staging.
- The MCP edge's native ConnectionService gRPC listener is plaintext.
- The Central Sampler's primary gRPC listener is plaintext and authenticates Gateway TokenReview
  bearers. Its optional TLS is server-authentication only.
- Policy Controller and Central Sampler have optional server-auth-only TLS settings; these do not
  establish client identity.
- Public app traffic terminates TLS at the Gateway, so an external client certificate cannot reach
  the app as mTLS. The app's `agentplane-agent` TokenReview path needs its separately approved
  issuer-backed test/operator token transition and must not be replaced by a backend service SVID.

Before changing a receiver, pin its existing server URI, add client certificate verification and
exact service-principal admission, and keep current bearer admission temporarily. The caller switches
only after the receiver image with that admission is pinned. Remove bearer admission and TokenReview
only after every corresponding caller image is pinned. A failed or missing certificate must never
fall back to a bearer. Rollback before bearer removal may restore the previous caller image; after
bearer removal, rollback requires restoring a receiver image that still contains the compatible
service-SVID admission, not reviving TokenReview as a hidden alternate mode. Remove token audiences
and `tokenreviews` RBAC last, after all in-cluster callers and images have moved.

Certificates and trust mounts must exist before code relies on them. Code accepting new TLS settings
must be pinned before manifests set those settings. Verify actual Deployment image IDs and trust
bundle mounts, not only source revisions. These checks are distinct from the caller/receiver image
gates: cert-manager can issue a usable cert while an older receiver image still rejects its client
certificate.

## Sequencing and boundaries

1. This inventory and the current-versus-approved authentication guidance reconcile the old
   bearer/transport descriptions.
2. Issue and mount service certificates with both client and server usage, and make issuer/trust
   rotation and renewal visible to workloads, before receiver code depends on them.
3. Add exact service SPIFFE IDs to receiver method allowlists while existing bearer callers remain
   valid. Test both actor verification and method denial. This is the stage-three receiver work;
   History JournalIngress must preserve its existing Identity and Session provenance independently.
4. Move each caller only once every receiver image it needs is pinned with SVID admission. Each
   target's authentication settings land in source before deployment manifests enable them.
   For LLM ingress, this includes switching the Central Sampler connection from `auth.mode: bearer`
   to `auth.mode: agentplane_ingress` and enabling `central_sampler_identity_callers` for the exact
   `spiffe://agentplane/central-sampler` service actor only after that receiver image is pinned. The
   sampler's existing
   `providerAuthorization` builds a typed envelope from the Session's recorded execution Identity
   and Session ID; it removes `x-agentplane-session-id` in that mode, and LLM ingress checks the
   Identity UID live. Missing Identity name/UID fails the delegated request before dispatch and
   must not fall back to a bearer. The staging Sessions must therefore continue to have a recorded
   execution Identity with a UID for this provider path; verify that invariant against live staging
   before switching the caller image.
5. Remove bearer listener modes, TokenReview code, projected token audiences and TokenReview RBAC
   after the last caller image is pinned; RBAC deletion is last.

PRs #16333 (Policy Controller and sampler server TLS), #16334 (verified client TLS), and #16324
(Sandbox Controller client SVID reuse) are separate in-flight work to build on. This inventory does
not duplicate those changes. The next implementation dispatch stops after stage 3 and the
independently approved app-agent-token step (a) are open and green; stages 4–5 wait for explicit
image-pin review. The end-state acceptance is: no Agentplane receiver admits a Kubernetes bearer;
tests cover exact peer and method admission, wrong/rotated/expired credentials, caller denial, and
delegation without a bearer fallback.
