# Thread browser startup proxy boundary

## Observed setup failure

[Invocation `5699ac4c`](https://app.buildbuddy.io/invocation/5699ac4c-baa3-5d54-a7b0-8ea9ad0f7136), shard 16 of `//agentplane/app:test_thread_browser`, passed `test_thread_follows_bottom_until_reader_scrolls_up[phone-raw]` and then errored while setting up `test_streamed_admission_survives_a_lost_http_reply_and_reload`. The latter never reached its lost-reply scenario. `open_browser` canceled `page.goto` through the 30-second timeout shared with `thread_source.opened.get()`. Teardown connection resets and runner unavailability came afterward.

The scripted source's `ingesting()` task queues `Opened` before waiting for replay; it performs no history copy until the test releases that replay. The failed Playwright trace records the document and both static assets as HTTP 200. Its Node-side `Frame.goto` call ran from trace time 8.843 to 13.901 seconds and recorded a successful response, although the Python await eventually canceled. Browser API requests for thread metadata, frontend config and summary began around 11:21:21 UTC and all spent about 23 seconds waiting for response headers, arriving together around 11:21:45. The ingress log corroborates that interval. In the passing case in the same shard, `Frame.goto` took 0.95 seconds, the frontend-config request 21 ms and thread metadata 148 ms.

All those API requests pass through the test's Python ASGI `BrowserProxy` before the Go app. The old trace shows only browser-to-ingress timing, not when the Python proxy admitted each request or received Go headers. The concurrent wait and the successful Node-side navigation rule out a late scripted `Opened` as an explanation, but do not locate the stall between Python event-loop scheduling, proxy forwarding and Go/backend response. No timeout increase or application repair follows from this sample. The added per-open phases and per-proxy-request admission/upstream-header phases are written to undeclared test outputs so a recurrence can be joined to the retained Playwright trace and ingress log.

The focused [fresh RBE run](https://app.buildbuddy.io/invocation/f09eb530-244e-45d3-87bf-fa1672850768) passed the streamed-admission case and emitted both phase artifacts. In that pass, `opened_wait_start` and `opened_wait_done` are 20 microseconds apart, and `navigation_start` to `navigation_done` is 400 ms. The pass validates artifact plumbing; it does not reproduce or resolve the old stall.

## Playwright response boundary

The failed invocation ran commit `c52a46c69db0bba0e026fa3d012e8631fac4a710`, whose `pyproject.toml` pins Playwright 1.62.0. Its trace action `call@13` records `Frame.goto` ending successfully at 13.901 seconds with a response. The `after@call@13` frame snapshot appears at 40.934 seconds, 27.033 seconds later. The snapshot's own JavaScript collection time is 208.5 ms. In the passing test immediately before it in the same shard, `call@13` ended at 20.105 seconds and its after snapshot appeared at 20.850 seconds, with 12 ms collection time.

In the pinned Playwright driver (`playwright/driver/package/lib/coreBundle.js`), the dispatcher awaits `instrumentation.onAfterCall` before sending the call response to Python (lines 18796–18805). Tracing's `onAfterCall` awaits `_captureSnapshot` (25397–25408), which evaluates the snapshot script in the existing frame main context (15005–15019, 22998–23005). The instrumentation proxy awaits each listener in order (12735–12763); the other `onAfterCall` implementation is the optional Recorder, which this fixture does not enable. The trace therefore puts Python's pending await in the post-action tracing path, after navigation succeeded. It does **not** establish whether the delay was in Chromium's main thread, Node's event loop, or execution scheduling before snapshot collection began. The trace also cannot show whether the three slow API responses had reached the Python proxy or the browser's network stack during that interval.

## Bounded RBE controls

One [physical RBE test](https://app.buildbuddy.io/invocation/1585db6a-8bb1-4aee-9056-10650ca8a7c9) ran the same case with Chromium CPU throttled 8× and passed in 65.7 seconds. Navigation took 5.754 seconds; the action-end to after-snapshot gap was 1.392 seconds. Proxy `received` to `upstream_headers` was at most 99 ms. General browser CPU slowdown at that setting did not reproduce the failure.

A second [physical RBE control](https://app.buildbuddy.io/invocation/18f973d1-e647-4b1a-9964-c4ef4d6cd027) used a temporary, uncommitted init script that scheduled a 32-second renderer main-thread block immediately after the thread route loaded. The control's source was commit `5c6cc2ebeaa53c1e8ea3e0a1cc6c6335776119ed` plus a one-file patch to `thread_browser.py` (patch SHA-256 `0f57c303efbb7e21eb7fbaec6922d76e9a4c19f0b0b58079da813449b5632d91`); the patch was reverted after the run. It failed as intended: `Frame.goto` ended successfully at trace time 14.447 seconds, the block ran from 14.860 to 46.800 seconds, and the after snapshot appeared at 46.825 seconds with 6 ms collection time. Python recorded `navigation_failed: CancelledError` 33.059 seconds after navigation started. This shows a renderer block can produce the same post-action snapshot and Python timeout signature. In this control, the frontend-config, thread metadata and summary requests had HAR durations of 24, 24 and 77 ms, while proxy `received` to `upstream_headers` took 6, 11 and 69 ms. It did not reproduce the historical 23-second API wait. These deliberately induced conditions do not identify the natural trigger.

The historical Go and Python `Date` headers differ by about 23 seconds, but Go may assign `Date` before flushing headers. They are not a measurement of when the proxy received upstream headers. The existing proxy phase artifact will locate that boundary on a fresh failure: late `received` points before ASGI admission; early `received` with late `upstream_headers` points into forwarding or Go/backend response; early `upstream_headers` with late `finished` points into body forwarding or ASGI send. A concurrent snapshot gap would still require native browser/Node/Python stacks or scheduler evidence during the gap to identify its trigger. The historical run has neither those stacks nor proxy phase artifacts, so it supports no runtime repair or timeout change.
