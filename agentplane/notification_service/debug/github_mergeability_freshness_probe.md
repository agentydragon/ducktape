# GitHub mergeability freshness probe

On 2026-10-28 UTC, a draft synthetic PR (#12341) in `agentydragon/ducktape` tested how REST `mergeable` changes when only its base branch moves. Its orphan trees contained two text files and no `.github` directory. The head ref stayed at `488988aed37a5b11e0a17a40c3826ecb9eacf763`; the base started at `b24544f2c5a248fd7a16a3ce01db70b95ebac221`.

The first PR GET returned `mergeable=null` / `mergeable_state=unknown` at 00:09:15.145Z. At 00:09:20.664Z it returned `true` / `clean`, with test merge commit `c952e8ccb521918cef51cffe3e34d61f60699c61` and parents `[b24544f2c5a248fd7a16a3ce01db70b95ebac221, 488988aed37a5b11e0a17a40c3826ecb9eacf763]`.

The base ref advanced to a commit with a conflicting edit at 00:09:23.610Z. Direct ref GETs showed that new base SHA and the unchanged head throughout the polls. The PR endpoint continued returning `true` / `clean` through 00:11:17.835Z; its first `false` / `dirty` response completed at 00:11:22.829Z. That response had `merge_commit_sha=null`. The PR response's `base.sha` still named the initial base throughout, including with the `false` result. Thus this probe observed a 119-second gap between the base-ref update and the first negative response, but cannot establish which exact commit pair GitHub evaluated.

The base ref then advanced to a commit restoring its original file content at 00:11:25.540Z; the head ref did not move. The first PR response afterward, at 00:11:25.865Z, was still `false` / `dirty`. At 00:11:31.859Z it became `null` / `unknown`, then at 00:11:37.894Z it became `true` / `clean`. The resolved test merge commit `b720578f6b0dac1c84eef2c753eb82ed51e27ca2` had parents `[4ab1f68b7ee0861a6222eaace9bc6b25e340b2d9, 488988aed37a5b11e0a17a40c3826ecb9eacf763]`. The PR `base.sha` still named the initial base in all three responses. This is one bounded observation, not a general GitHub timing guarantee.

REST responses were HTTP 200 and carried `Cache-Control: private, max-age=60, s-maxage=60`. The first conflict response and stale post-restore conflict response had the same ETag; the unknown and resolved responses had different ETags. Responses carried advancing Date headers and distinct request IDs. This does not distinguish HTTP caching from mergeability-computation lag.

A negative result is reported as “GitHub reported CONFLICTING at `observedAt`,” alongside the refs read, without claiming proof of the evaluated pair. Parent validation rejects the stale positive seen here. For negatives, the implementation chooses three early rechecks with successive delays of 5, 15 and 45 seconds, then the ordinary source freshness interval. Unverified results retry after 5, 15 and 45 seconds, then every 60 seconds. Counters and deadlines persist; a changed observed ref/state tuple resets the counter. This is a cost/latency policy informed by the probe, not a freshness proof or a GitHub timing guarantee. Existing shared refresh leases coalesce reads across subscriptions. Each refresh needs the PR and current base ref, plus the test commit when GitHub reports mergeable.

The probe made 107 REST API calls, including 29 PR GETs and 60 ref GETs, with 5-second target intervals and a 120-second cap per transition. It did not query GraphQL. The PR was closed. Both branches were freshly read at their expected SHAs, deleted through the GitHub API after the local SSH lease-delete failed on `.ssh/config` permissions, and verified absent.

Raw JSON, response headers, poll samples, fixture SHAs, and cleanup evidence are in `/tmp/gh-mergeability-freshness-20261028-Djr8Gz/` (`api_calls.jsonl`, `samples.jsonl`, per-call `.json` / `.http`, `state.json`, and `cleanup.json`). No authorization headers or tokens were recorded.
