Findings and acceptance criteria

1 · Visual false pass

Haku screenshot fixtures are type-checked but not uniformly parsed

Source and risk. RegisteredToolPreviewFixture ties fixture values to each tool’s Zod output type. The runtime renderer still safeParses, and a mismatch returns no preview; the visual test only asserts the card shell is attached. Thus a runtime refinement mismatch can leave a raw/fallback card that still captures. Grocy has narrow explicit parse examples, not a preflight over every registered fixture/result.

Acceptance. Before capture, parse every catalog entry’s arguments and any registered result with the runtime registry schema; fail with fixture slug, tool and validation issues. Assert the intended specialized preview is present. Keep explicit malformed-input tests and the Grocy negative regression.

2 · Derived fixture values

Spend card totals are still authored beside ledger transactions

Source and risk. scenario() hard-codes card spend, posted, pending and percentage fields (including both the established and provisional card), then separately builds statement decisions from synthetic transactions. The current parity test catches disagreement, but the fixture still maintains both representations and can become stale or require synchronized edits.

Acceptance. Derive statement amounts and percentage from the synthetic rows using the production statement rules. Retain independent fixed expected outputs for normal, pending, provisional and unavailable cases so the derivation is not tested against itself.

2 · Cross-language configuration coverage

Sidecar config has a real Python-to-Go path, but only partial shared vectors

Source and current coverage. Python Settings defines authoring defaults and validation. SidecarProcess serializes that model to YAML and starts the actual Go binary, so valid end-to-end configuration is already exercised. Separately, Go loader tests use hand-written YAML to exercise defaults, unknown fields, null and malformed nested values.

Remaining gap and acceptance. The positive Python-emitted path and Go negative/default matrix do not share input cases. Add focused contract vectors consumed by both Python validation/serialization and the Go loader, covering omitted defaults, nested routes, unknown fields, explicit null, required values and secret-file paths. Keep the real-process E2E as runtime evidence; a common schema is optional if vectors stay reliable.

2 · Python generated client gap

Python model-catalog client still translates App ProtoJSON by hand

Source and risk. The App owns generated ListModelsResponse, but models() indexes raw response dictionaries and maps camelCase fields into the domain ModelCatalog. This is a residual after the separate status and preset clients moved to generated parsing.

Acceptance. Parse the endpoint with generated ListModelsResponse, then adapt into ModelCatalog. Preserve its duplicate-model and harness-reference checks and test ProtoJSON casing, missing fields and invalid catalog relations.

3 · Test-only composed model

Python ThreadView helper manually joins two generated response shapes

Source and risk. The browser now keeps generated ThreadMetadata and SessionSummary nested; the Go metadata API no longer returns the former flattened view. Python still composes both JSON objects with thread_view_from_proto_json(), which has a manual feed-status table whose unknown values map to None. The App instructions put HTTP response models in testing/models.py; this is a test helper, not a production wire owner.

Acceptance. Parse each response using its generated Python message before projecting the test convenience view. Make unknown enum handling explicit; retain historical-harness cases, omitted attachments, uint64 cursor coverage and the helper’s test-only role.

3 · Presentation projection

App config decodes generated messages, then defines parallel view interfaces

Source and risk. The client declares its own Harness, model, defaults and preset view types, then decodes generated messages and maps each field into them. These may be useful UI projections, but they repeat field names, enum vocabulary and optional/default behavior across a boundary.

Acceptance. Derive the projection type from generated message types or establish a single typed adapter contract. Keep only transformations the UI needs, and test default/optional behavior plus exhaustive enum handling before dropping any view fields.

3 · Local schema/type duplication

GitHub Action arguments declare a type and Zod schema separately

Source and risk. SearchPullRequestsArguments and its strict Zod schema repeat the same local fields, so an edit must keep both declarations aligned. The upstream MCP tool catalog is external and dynamic; local equality does not prove upstream compatibility.

Acceptance. Infer the local TypeScript type from the Zod schema, preserve strict unknown-key rejection and negative vectors, and treat any upstream comparison as a versioned external compatibility check rather than claiming the local schema owns it.

What to preserve

Keep independent expected values and malformed inputs; deriving both sides from one implementation can make a test tautological. The current Spend parity test is useful as an independent guard even while the fixture duplication remains. Keep Haku malformed-schema fallback tests and Go config rejection cases. Preserve landed historical compatibility evidence: the journal v3 adoption test proves existing EventEntry and native-request data survive migration; do not regenerate it from the current writer.
