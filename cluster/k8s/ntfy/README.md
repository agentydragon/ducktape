# ntfy

This package runs one ntfy server at <https://ntfy.allegedly.works> for
Alertmanager and Flux notifications.

## Storage and configuration

- ntfy-db is a two-instance CloudNativePG PostgreSQL cluster on
  local-path-ovh-hdd in hil-ovh. CNPG generates the `ntfy-db-app` connection
  Secret; ntfy stores its message cache and authentication/authorization state
  in PostgreSQL. Attachments and web-push are not enabled.
- cdk8s deploys one ntfy pod. ntfy is not horizontally scaled yet; the two
  PostgreSQL instances provide database failover, not two ntfy writers.
- Static server configuration and the alerts ACL are generated by
  `cluster/cdk8s/ntfy_constructs.py` into `ntfy.k8s.yaml`.
- Passwords and tokens are encrypted in credentials.sops.yaml.
  ESO renders bcrypt auth-users and declarative auth-tokens into the
  ntfy-auth Secret. No bcrypt hashes are committed to Git.
- Alertmanager and Flux receive separate ESO-managed bearer-token Secrets in
  their own namespaces. Both can publish only to alerts; the Android token
  can subscribe to alerts but cannot publish.

## Credential rotation

When rotating a password or token:

1. Edit credentials.sops.yaml with sops.
2. Bump `ntfy.ducktape.io/auth-generation` in
   `cluster/cdk8s/ntfy_constructs.py`,
   `cluster/k8s/flux-webhook/ntfy-webhook-eso.yaml`, and
   `cluster/k8s/monitoring/stack/alertmanager-ntfy-webhook-eso.yaml`.
3. Regenerate manifests with `bb run //cluster/cdk8s:generate_manifests`.
4. Verify the three ExternalSecrets are Ready, ntfy restarted after its
   derived Secret changed, and Alertmanager/Flux delivered a test notification.

The generation bump is deliberate: bcrypt uses a random salt, so a periodic
ESO render would otherwise change the derived hash and restart ntfy without a
credential change.

GNOME client integration is intentionally not part of this package yet.
