# CDviz CI analytics

GitHub sends `workflow_run`, `workflow_job`, and `pull_request` events to the signed HTTPS receiver at `https://cdviz-webhook.allegedly.works/webhook/github`. The Crossplane OpenTofu workspace in `tf/gitops/cdviz-github-webhook/` owns the repository webhook and its signing secret. Flux deploys the collector, CNPG database with the TimescaleDB extension, and the CI workflow dashboard in Grafana's **CI** folder. No GitHub Actions workflow changes are required.

The collector uses a dedicated ingestion role; Grafana uses a separate read-only role. CNPG backs up the database to the existing SeaweedFS object store. The daily retention job keeps 90 days of events. The namespace, database, collector PVC, and OpenTofu state are retained when their Flux resources are removed.

Three Flux Kustomizations cover the database (including namespace, roles, extension and backups), the Crossplane OpenTofu webhook workspace, and the application (collector and dashboards). Only the database and application add source artifacts; the workspace reuses the existing `github-tf` artifact. The application waits for the database extension and signing Secret to be ready. The workspace waits for the database group to create the namespace.

The **Commit to CI feedback** dashboard (`ducktape-ci-feedback`) measures each exact PR head occurrence from GitHub's PR `opened`/`synchronize` timestamp to its first required failure and first simultaneous required-checks-green observation. It retains both clocks when a failed attempt later passes. A queued rerun invalidates its previous result. Cancellation, missing checks, supersession, and unknown conclusions cannot produce green. Repeated heads such as A → B → A remain separate occurrences.

These start clocks are proxies for commit arrival: opening a PR can happen long after the commit was pushed. Heads without an observed PR head event, including `devel` commits, use the earliest workflow `created_at` instead. The default selects PR head events; use the **Scope** and **Clock** filters to inspect other populations. Completion timestamps describe GitHub jobs, not when their results became API-queryable or reached an agent. Successful-only percentiles include sample counts; the 5/10/20-minute rates include every sufficiently old arrival in their denominators, including censored heads. Recent arrivals remain still observing.

An unauthenticated poll records the active `devel` required-check names every 15 minutes. The dashboard replays the latest observed policy at its selected end time; it does not assert historical policy applicability or full merge eligibility. The observation timestamp is visible. Missing/unsupported policy is unknown. The current integration supports GitHub Actions required jobs; a policy pinned to another integration is unsupported. The analytics function is installed by the numbered SQL migrations, applied in order before reader grants in a single transaction by the existing init container. Future schema changes require a new migration file.

Exact push-arrival clocks, durable transition recovery, historical policy applicability, and BuildBuddy phase drilldowns remain tracked by [#14122](https://github.com/agentydragon/ducktape/issues/14122). The existing collector cannot prove complete transition history: missed job events can leave heads pending or omit a transient result. This dashboard is an observed-history replay, not a replacement for GitHub's branch protection decision.

The collector image is `ghcr.io/cdviz-dev/cdviz-collector:0.53.1`; schema setup uses `ghcr.io/cdviz-dev/cdviz-db-migration:1.5.0`. Both are pinned to OCI index digests in `collector.py` so Kubernetes can resolve the node architecture. The migration image entrypoint is `migrate`, so its init container supplies `-database … -path /migrations/ up` as arguments.

The RBE integration test uses the digest-pinned upstream `timescale/timescaledb:2.31.0-pg18-oss` image through Testcontainers. It matches production's PostgreSQL major and TimescaleDB version; CNPG's Debian image and `ImageVolume` extension mounting are deployment concerns outside this test.

The database sink is named `postgres`: the bundled `database` sink in this collector version has a default `url` that takes precedence over `url_file`. A separate name lets the mounted secret supply the connection string.

The `CI workflow and job timings` dashboard (`ducktape-ci`) refreshes every minute and filters by workflow, branch, and pull request. It shows workflow attempts, failure rate, P50 and P95 workflow runtime, runtime and outcome trends, recent workflow attempts, and recent jobs. The recent tables link to the GitHub attempt or job; original names and URLs remain in the stored events.

The dashboard JSON is maintained in this component at `dashboard.json`. Its PostgreSQL queries use the collector's `cdviz.pipelinerun` and `cdviz.taskrun` views. Pull request numbers come from the `customData.github.workflow_run.pull_requests` array; they are not inferred from a branch or commit SHA.

The upstream `transformers-community` archive is licensed under Apache License 2.0. Bazel includes its `LICENSE` in the generated application artifact alongside the transformer source embedded in the ConfigMap. The license is an unreferenced artifact file, not a Kubernetes resource or a mounted file.

The `.vrl` scripts use [Vector Remap Language](https://vector.dev/docs/reference/vrl/), which CDviz embeds to transform GitHub JSON into CDEvents. Bazel fetches them unchanged from the SHA256-pinned `cdviz-dev/transformers-community` commit [`754a167ed781f52ba5cab5bf94a9144918ce0afb`](https://github.com/cdviz-dev/transformers-community/commit/754a167ed781f52ba5cab5bf94a9144918ce0afb): `github_events/to_v0_5.vrl` handles signed webhook payloads, and `github_rest_api/workflow_runs_to_v0_5.vrl` converts the REST workflow-runs response. `collector.toml` reads both secrets through the collector's `_file` configuration adapter; values are mounted from Kubernetes secret files and are not interpolated into TOML or the process environment.

The 15-minute unauthenticated REST poll follows GitHub's pagination links, with 100 runs per page, until it reaches runs created more than one hour ago or exhausts the response. It processes the boundary page too. A 12-request/depth guard bounds each poll; hitting a guard logs a warning and leaves that poll incomplete. Including the four policy requests, the guards permit at most 52 requests per hour before retries, within GitHub's [60 unauthenticated requests/hour/IP limit](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). Other consumers of the same public IP share that quota; 403/429 responses hold the poll for retry. This is best-effort recent-run repair, not a historical backfill guarantee. The sizing evidence is in [debug/poll-sizing.md](debug/poll-sizing.md).

Larger recovery windows need authenticated API access and a separate backfill strategy. The endpoint has no `updated_at` time filter, so a missed completion for a run created before the overlap is not repaired, even if it only just finished. An outage longer than the overlap can also leave gaps. Polling does not fetch per-run jobs, so task-level detail depends on `workflow_job` webhooks. The upstream REST transformer emits queued, started, and finished pipeline events from each returned run; its REST custom data does not retain `pull_requests`, so PR numbers can be empty for poll-only observations. The upstream transformers also use collector time if an expected timestamp is absent.

Queue-to-start duration uses the upstream normalized transition timestamps. The webhook transformer uses `workflow_run.updated_at` for each phase; REST reconciliation uses `created_at` for queued and `run_started_at` for started. These are recorded transition clocks, not runner assignment measurements. GitHub may retain the original `created_at` on a rerun, so reconciled queue intervals can overstate queue time for later attempts.

Outcome trends label unfinished workflow attempts as `queued` until `started_at` is present, then `running`. Cancellation is labeled only when the stored terminal outcome is `cancel`, `cancelled`, or `canceled`; a missing `finished_at` alone does not mean cancellation.

The PostgreSQL batch spool is persistent on the collector PVC, and the DB sink replays it after restart. A successful webhook response means the collector's in-memory event queue accepted the payload; it is not a durable database acknowledgement. Events still waiting in the collector queue or batcher may be lost on a hard process/node failure before the batcher fsyncs them. A DB outage longer than the finite PVC capacity also requires operator recovery. Polling can repair only pipeline summaries returned within its bounded recent-run scan; it cannot restore missed task transitions or prove exact event history.
