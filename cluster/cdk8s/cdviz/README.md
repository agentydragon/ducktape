# CDviz CI analytics

GitHub sends `workflow_run`, `workflow_job`, and `pull_request` events to the signed HTTPS receiver at `https://cdviz-webhook.allegedly.works/webhook/github`. The Crossplane OpenTofu workspace in `tf/gitops/cdviz-github-webhook/` owns the repository webhook and its signing secret. Flux deploys the collector, CNPG database with the TimescaleDB extension, and the two dashboards in Grafana's **CI** folder. No GitHub Actions workflow changes are required.

The collector uses a dedicated ingestion role; Grafana uses a separate read-only role. CNPG backs up the database to the existing SeaweedFS object store. The daily retention job keeps 90 days of events. The namespace, database, collector PVC, and OpenTofu state are retained when their Flux resources are removed.

This provides workflow and job timings and outcomes. Exact PR-head arrival-to-required-checks-green cohorts, required-check policy history, supersession, and BuildBuddy phase drilldowns remain tracked by [#14122](https://github.com/agentydragon/ducktape/issues/14122).

The collector image is `ghcr.io/cdviz-dev/cdviz-collector:0.53.1`; schema setup uses `ghcr.io/cdviz-dev/cdviz-db-migration:1.5.0`. Both are pinned to OCI index digests in `collector.py` so Kubernetes can resolve the node architecture. The migration image entrypoint is `migrate`, so its init container supplies `-database … -path /migrations/ up` as arguments.

The database sink is named `postgres`: the bundled `database` sink in this collector version has a default `url` that takes precedence over `url_file`. A separate name lets the mounted secret supply the connection string.

The dashboards refresh every minute. Table names omit the fixed repository prefix and link to the GitHub workflow attempt or job; the original names and URLs remain in the stored events.

The two dashboards derive from CDviz repository commit [`44e3250dad1c6aaebaa5f0d02a8bfb885fb3f63f`](https://github.com/cdviz-dev/cdviz/commit/44e3250dad1c6aaebaa5f0d02a8bfb885fb3f63f): `cdviz-grafana/dashboards/pipelinerun_executions.json` and `taskrun_executions.json`. They retain the upstream statistics, trends, and selection variables. The unsigned `cdviz-executiontable-panel` was replaced with Grafana's built-in table panel, dashboard datasource references use UID `cdviz`, and panel IDs are made unique. The table SQL reads the upstream `cdviz.pipelinerun` and `cdviz.taskrun` views. Pipeline PR numbers come from the retained `customData.github.workflow_run.pull_requests` array; no branch/SHA-to-PR inference is performed.

Both upstream repositories license these assets under Apache License 2.0 and contain no `NOTICE` file. The full upstream license texts are preserved in `LICENSE.cdviz` and `LICENSE.transformers-community`; they are byte-identical. Each dashboard's description records its local modification.

The VRL files are vendored unchanged from `cdviz-dev/transformers-community` commit [`754a167ed781f52ba5cab5bf94a9144918ce0afb`](https://github.com/cdviz-dev/transformers-community/commit/754a167ed781f52ba5cab5bf94a9144918ce0afb): `github_events/to_v0_5.vrl` handles signed webhook payloads, and `github_rest_api/workflow_runs_to_v0_5.vrl` converts the REST workflow-runs response. `collector.toml` reads both secrets through the collector's `_file` configuration adapter; values are mounted from Kubernetes secret files and are not interpolated into TOML or the process environment.

The 15-minute unauthenticated REST poll follows GitHub's pagination links, with 100 runs per page, until it reaches runs created more than one hour ago or exhausts the response. It processes the boundary page too. A 12-request/depth guard bounds each poll; hitting a guard logs a warning and leaves that poll incomplete. The guard permits at most 48 page requests per hour before retries, within GitHub's [60 unauthenticated requests/hour/IP limit](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). Other consumers of the same public IP share that quota; 403/429 responses hold the poll for retry. This is best-effort recent-run repair, not a historical backfill guarantee. The sizing evidence is in [debug/poll-sizing.md](debug/poll-sizing.md).

Larger recovery windows need authenticated API access and a separate backfill strategy. The endpoint has no `updated_at` time filter, so a missed completion for a run created before the overlap is not repaired, even if it only just finished. An outage longer than the overlap can also leave gaps. Polling does not fetch per-run jobs, so task-level detail depends on `workflow_job` webhooks. The upstream REST transformer emits queued, started, and finished pipeline events from each returned run; its REST custom data does not retain `pull_requests`, so PR numbers can be empty for poll-only observations. The upstream transformers also use collector time if an expected timestamp is absent.

Queue-to-start duration uses the upstream normalized transition timestamps. The webhook transformer uses `workflow_run.updated_at` for each phase; REST reconciliation uses `created_at` for queued and `run_started_at` for started. These are recorded transition clocks, not runner assignment measurements. GitHub may retain the original `created_at` on a rerun, so reconciled queue intervals can overstate queue time for later attempts.

Outcome trends label unfinished attempts as `queued` until `started_at` is present, then `running`. The pipeline view exposes `queued_at`; the task view does not, so its queued label means “not started” and has no measured queue interval. The trends label cancellation only when the stored terminal outcome says `cancel`, `cancelled`, or `canceled`; the database rollup sets `finished_at` only from a finished event, so its absence does not mean cancellation.

The PostgreSQL batch spool is persistent on the collector PVC, and the DB sink replays it after restart. A successful webhook response means the collector's in-memory event queue accepted the payload; it is not a durable database acknowledgement. Events still waiting in the collector queue or batcher may be lost on a hard process/node failure before the batcher fsyncs them. A DB outage longer than the finite PVC capacity also requires operator recovery. Polling can repair only pipeline summaries returned within its bounded recent-run scan; it cannot restore missed task transitions or prove exact event history.
