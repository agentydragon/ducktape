# Agent RBAC

The `agent-rbac-base` directory (Flux Kustomization `claude-rbac`, generated by
<../cdk8s/agent_rbac_base.py>) is the **lightweight base** for agent RBAC. It contains only
cluster-scoped resources (ClusterRoles) and sandbox-internal resources
(namespace + RoleBindings within `claude-sandbox`). It must **never** depend on
service or database kustomizations.

Namespace-scoped RoleBindings targeting other namespaces live in per-service `agent-rbac/`
directories or generated `agents/namespace-rbac/<namespace>/` directories (see Architecture below).

**Cross-references**: `cluster/AGENTS.md` (Agent RBAC Architecture) and the root
`AGENTS.md` (Kubernetes MCP Server section) keep brief summaries that point here. Update this file as the single source when changing permissions or the quota.

## Architecture

Agent RBAC is split across four layers:

### 1. `agent-rbac-base` — lightweight base

Depends on: `kyverno-policies` only. No service or database dependencies.

Contains:

- `claude-sandbox` namespace, ResourceQuota, LimitRange
- Sandbox-internal Role + RoleBinding (`admin`)
- Sandbox-internal `claude-ollama-consumer` RoleBinding (binds ClusterRole in claude-sandbox ns)
- ClusterRoles: `cluster-diagnostics-reader`, `logs-configmaps-reader`,
  `namespace-diagnostics-reader`, `secrets-reader`

### 2. `shared-rbac` — cluster-scoped bindings

Depends on: `agent-rbac-base`.

Contains:

- ClusterRoleBinding for `cluster-diagnostics-reader` (cluster-wide)

### 3. Per-service `<service>/agent-rbac/` — exceptional namespace-scoped RBAC

Service-specific or sensitive agent access has its own `agent-rbac/` directory with an
independent Flux kustomization.

### 4. `agents/namespace-rbac/<namespace>/` — common diagnostics

`namespace_access.py` is the single reviewed namespace classification.
`agent_namespace_rbac.py` generates namespaced RoleBindings to the metadata and log
ClusterRoles. Each namespace has an independent Flux Kustomization depending only on
`claude-rbac`, which supplies the shared Roles. Application health and namespace-owner
Kustomization readiness do not gate diagnostic access. Agentplane consumes the same
classification for managed grants; Kyverno does not generate agent bindings.

These Kustomizations emit only RoleBindings, never Namespaces. Existing namespace owners
retain creation, labels and deletion. On a fresh bootstrap, the Kubernetes API rejects
bindings to a namespace that does not exist yet; Flux retries every minute until it exists.
No namespace is created merely to grant diagnostics, and a missing/suspended namespace does
not block bindings in other namespaces. An unhealthy application in an existing namespace
does not block its diagnostic bindings either.

This does not change Agentplane's separate binding-delegation dependencies or exceptional
per-service RBAC.

## Permissions Granted

### 1. claude-sandbox namespace — full CRUD

The `admin` Role, its RoleBinding, and the ResourceQuota and LimitRange are
generated by <../cdk8s/agent_rbac_base.py>.

### 2. Cluster-wide read — diagnostics

`cluster-diagnostics-reader` ClusterRole (<../cdk8s/agent_rbac_base.py>),
bound in <../cdk8s/agent_shared_rbac.py>, grants cluster-wide `get`/`list`/`watch` on
diagnostic resources, including RedisReplication, legacy Flux Terraform, OpenTofu Workspace,
GrafanaDashboard, and all objects in the Crossplane API groups `apiextensions.crossplane.io`,
`ops.crossplane.io`, `pkg.crossplane.io`, `protection.crossplane.io`, `opentofu.upbound.io`,
`opentofu.m.upbound.io`, and `litellm.m.crossplane.io`. This includes compositions, XRDs,
operations, packages, runtime configs, OpenTofu provider configs, provider config usages and
Workspaces, and LiteLLM provider configs, keys, teams, and organizations. It also reads `keys` and
`teams` in the legacy cluster-scoped `litellm.crossplane.io` API group. All object
fields are readable, including `EnvironmentConfig.data` and OpenTofu Workspace outputs, so secret
values must stay out of inline fields. The role does not grant reads on Kubernetes Secrets or direct
access to an OpenTofu state backend. It also excludes ConfigMaps, Pod logs, Pod exec, and `nodes/proxy`;
the apiserver authorization review subresources allow `create` only to query permissions and persist
no object.
Static agent identities on the shared binding receive it directly. Managed public-coder,
finance-agent, and Haku sandboxes select it through their presets. The generator is the
resource-list source of truth.

### 3. Cross-namespace read

Service-specific and sensitive namespaced RoleBindings live in per-service `agent-rbac/`
directories. Each is an independent Flux kustomization that depends only on the target
namespace + the agent RBAC base. The common diagnostics readers are generated by
`agent_namespace_rbac.py` from the shared namespace policy, then applied by Flux.

The `secrets-reader` ClusterRole (get/list/watch `secrets`) is bound **only** where a
service explicitly opts in (currently `study-casino`), and only for
`oidc-ksbx-groups:kubectl-sandbox-users` — never co-subjected to Haku, whose reader
grants stay deliberately secret-free.

### 4. Haku background agent — diagnostics subset

Haku's durable Console Agent profile is represented to SubjectAccessReview as the synthetic,
non-login group `haku:access-profile:haku`. The existing OIDC group
`oidc-ksbx-groups:haku` and in-cluster `haku` ServiceAccount remain the direct login/runtime
identities for callers that carry Kubernetes credentials. All three are co-subjected onto the same
roles: full CRUD in `haku-sandbox`, plus general cluster diagnostics and safe log reading. The
transport or runtime that authenticated Haku therefore does not select a different permission set;
Console-launched CLI runners carry no ServiceAccount token and use the synthetic group through the
authorization proxy:

- **`cluster-diagnostics-reader`, cluster-wide** (added as a subject on the shared-rbac
  ClusterRoleBinding). It has no `secrets`/`pods/log`/`configmaps` permission and no write or
  exec permission. OpenTofu Workspace specs and statuses are readable, so sensitive inputs must
  stay in referenced Secrets rather than inline Workspace fields; the role cannot read those
  Secret objects.
- **Metadata and logs in explicitly classified namespaces**. `namespace_access.py`
  is the source of truth. Its static projection generates
  namespaced RoleBindings for both Haku groups, the direct Haku ServiceAccount,
  `kubectl-sandbox-users`, and `claude-ai` (section 6).

The labels describe the shared policy; changing a live Namespace label **does not**
grant or revoke access. RoleBindings grant access, and ClusterRoles define the
resource permissions. Adding an agent identity means updating the shared subjects
once, rather than changing every namespace.

There are exactly two generated namespace classifications:

- `rbac.ducktape.io/agent-readable-metadata: "true"` describes the common metadata baseline:
  workload/controller state, Events, PVCs, Jobs/CronJobs, and explicitly classified ConfigMaps.
  It excludes Secrets and pod logs.
- `rbac.ducktape.io/agent-readable-logs: "true"` means the same metadata is readable **and**
  pod logs are readable. A LOGS classification generates both bindings and the logs
  label; the namespace does not need both labels. The additive logs role grants only `get` on `pods/log`.

Both labels use the same agent subject set. This keeps Haku's synthetic SAR identity structurally
at least as capable as public-coder and makes the label a statement about the namespace's data
sensitivity, not about a particular authentication transport.

The separate `oidc-ksbx-groups:kubectl-sandbox-users` group belongs to the interactive Claude
Code Web/kubectl sandbox environment. It is not a parent group of Haku, but it participates in
the same explicit namespace classifications.

This widens the original `haku-sandbox`-only perimeter (<../../haku/PLAN.md>) to read-only
diagnostics; the structural fences (read-only verbs, no secret material, mitmproxy egress) are
unchanged. Haku's full enforcement inventory: <../../haku/docs/security.md>.

### 5. claude-ai (OAuth Connections in agentplane-staging) — diagnostics, Coinbase key

The `claude-ai` ServiceAccount in `agentplane-staging` is the principal for Connections
enrolled from the Claude.ai MCP connector (`cluster/cdk8s/agentplane/actions_staging_policies.py`);
every sandbox it stamps through the sandbox Action group runs as it
(`agentplane/action_service/sandbox/README.md`). Its Kubernetes access includes:

- The secret-free `cluster-diagnostics-reader` binding and metadata/pod-log readers of
  the `agent-readable-*` namespaces (section 4).
- The same narrow console metadata, ClickHouse diagnostics, public-coder diagnostics,
  and public-coder VolSync status Roles used by public coder and Haku.
- `get`/`list` on Agentplane `sandboxes`, `sandboxtemplates`, `policysets` and `policybindings` and read-only KubeVirt VM/VMI views, plus the VMI
  `console` subresource, in **agentplane-staging** (`claude-ai-sandbox-reader`), so a read-only
  check needs no approval.
- `get` on one explicitly named Secret: `agentplane-staging/coinbase-api-credentials`
  (the view-only Coinbase CDP key).
  No general Secret enumeration or staging login access.

The `coinbase` PolicySet combines GET egress to `api.coinbase.com` with the `get` grant on
the named Coinbase Secret. The static `claude-ai` and `haku-agent` PolicyBindings both select it;
the Haku and finance-agent presets select it for managed sandboxes. Static Haku identities keep
their explicit RoleBinding to the same named Secret. These grants do not make `claude-ai` an alias
for Haku: it has no Haku sandbox write authority or staging operator access, and `haku-agent`
has no Haku profile grants.

The `kubernetes-inspection-reads` PolicySet auto-approves `kubernetes_admin`'s resource-usage reads
(`nodes_stats_summary`, `nodes_top`, `pods_top`) for the static `claude-ai` and `haku-agent`
bindings and the Haku preset. They run as the operator's cluster-admin passthrough identity but
return only metrics; every other `kubernetes_admin` Action stays manual.

Agentplane-managed Haku runner Pods use per-Sandbox ServiceAccounts and their own
preset selections, which an operator may replace. Kubernetes access is also distinct
from Forgejo credentials, egress policies, and Actions approvals; this profile does not
change those authorities.

### Agentplane-managed Sandbox grants

Agentplane creates a distinct ServiceAccount for each managed Sandbox, and the Sandbox
Controller binds it to the `PolicySet`s its `spec.policySets` names with one `PolicyBinding`
the Sandbox owns ([model](../../agentplane/docs/adr_policy_sets.md)). The sets are
Flux-rendered from the grant catalog in `cluster/cdk8s/agentplane/staging_config.py`
and `cluster/cdk8s/agent_access_profiles.py`; presets supply the default set names for a launch,
and the operator can replace them, including with none. The Policy Controller keeps the native
RoleBindings and ClusterRoleBindings of the bound sets' Kubernetes rules
([contract](../../agentplane/policy_controller/SPEC.md)). A set edit therefore reaches every
bound Sandbox, and deleting a Sandbox deletes its binding and the native bindings it granted.

Each environment chart separately materializes the Policy Controller workload, its assignable
PolicySets, and the controller's RBAC. The same assignable grant references produce both the
PolicySet Kubernetes rules and the controller's exact `resourceNames`-scoped `bind` permissions;
the controller workload construct itself has no Role or binding wiring. The controller cannot
edit the referenced roles' rules. Its own Flux Kustomization owns delegation in `agentplane-staging`
and at cluster scope. Each external target namespace has a separate, GitRepository-sourced Flux
Kustomization for the Policy Controller's RoleBinding management Role and RoleBinding
(`cluster/cdk8s/agentplane/binding_delegation.py`). The `haku-sandbox` delegation depends on
`haku-rbac`, which depends on the namespace owner. A failure in this delegation Kustomization
does not block the Agentplane app Kustomization. Keep an external delegation while its
namespace is in the retained cleanup scopes, even if its catalog entry is removed.

The Policy Controller's exact-name `bind` rules limit which assignable ClusterRoles it can grant,
but not their subjects. Kubernetes RBAC cannot scope top-level ClusterRoleBinding creation by
`resourceNames`; the controller's ClusterRoleBinding `create`, `patch`, and `delete` permissions
are unscoped. A compromised controller identity could therefore bind an assignable ClusterRole to
any subject and delete any ClusterRoleBinding. Generated names and labels guide normal
reconciliation; they do not limit this ServiceAccount's authority. This cluster-wide binding
authority is part of the current trusted-controller boundary.

Putting ClusterRoleBinding writes in a separate controller would isolate the Policy Controller's
credential, but would not contain compromise of the new writer: it would need the same unscoped
cluster-wide ClusterRoleBinding `create`, `patch`, and `delete` permissions and the same `bind`
authority for assignable ClusterRoles. Without an admission guard, a compromised writer could still
grant those roles to any subject and delete any ClusterRoleBinding. Static bindings avoid a runtime
writer but give up PolicyBindings' runtime ServiceAccount subjects.

Containment after writer compromise would require admission to check each ClusterRoleBinding's
subject and role against its PolicyBinding and PolicySets. Expiry deletes the PolicyBinding first;
the subsequent NotFound reconciliation deletes its native bindings. The cleanup check must therefore
authorize deletion from ownership data on the old ClusterRoleBinding after its source PolicyBinding
has disappeared. A `ValidatingAdmissionPolicy` evaluates the admission object and its old object, plus
an explicitly selected parameter resource; it does not fetch arbitrary related objects. This dynamic
cross-object check needs a validating webhook or another authoritative server-side source. See
Kubernetes' [RBAC resource-name and bind rules](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)
and [ValidatingAdmissionPolicy CEL inputs](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/).

### Shared deployment definitions and parity contract

`cluster/cdk8s/agent_access_profiles.py` holds existing Kubernetes grant references,
static identity references, and deployment-side profile selections. Service charts
still own their Roles and bindings; Agentplane consumes the same references for its
catalog and presets, from which delegation is already generated. This does not add
an Agentplane API or combine namespace-scoped readers into a cluster-wide binding.
Service-specific Role names and ownership remain unchanged. The common namespace
readers migrate to Flux-owned bindings as described below.

The logical profiles are distinct from the transport identities:

| Access path                        | Logical profile / contract                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------------- |
| `oidc-ksbx-groups:haku` group      | Static Haku; checked independently                                                                  |
| `haku:access-profile:haku` group   | Static Haku Console; checked independently                                                          |
| `haku-sandbox/haku` ServiceAccount | Static Haku compute; checked independently                                                          |
| Managed `haku` preset              | Includes public coder; matches each static Haku path, including the exact Coinbase grant below      |
| Managed `finance-agent` preset     | Public coder permissions plus the exact Coinbase grant below; no static finance identity is implied |

| `agentplane-staging/claude-ai` ServiceAccount | Separate legacy OAuth/Actions account: broad cluster diagnostics, labeled namespace readers, and Coinbase read |
| `agentplane-staging/haku-agent` ServiceAccount | Separate Actions account, not the managed Haku preset |
| `public-coder-agent/openclaw` ServiceAccount | Static OpenClaw Action caller; Action Service reads labeled ServiceAccount metadata here, while its policy binding and sets stay in `agentplane-staging` |

The managed finance and Haku presets and the static `claude-ai` and `haku-agent` PolicyBindings
select the `plaid-diagnostics` PolicySet. It combines the pgweb `plaid_ro` read-only egress path
with a namespaced `plaid-mcp` RoleBinding for read-only control-plane metadata (Pods, Services,
EndpointSlices, workloads, events, PVCs, and CNPG Cluster status). The Role excludes Secrets,
ConfigMaps, Pod logs/exec and every mutation. This grant diagnoses sync and Postgres health without
treating the sensitive `plaid-mcp` namespace as globally agent-readable. It is a new-sandbox preset
grant for managed callers and a PolicyBinding grant for the static callers, not proof of current
RBAC in an already-running sandbox.

**Intended relationship between the Haku and finance-agent presets.** Haku is the executive
agent that directs the finance agent (Rai's finances are the finance agent's, and Haku
orchestrates over it), so the finance preset is meant to hold a **weaker subset** of Haku's
privileges, not a peer set. What is deliberately different is the identity: the finance agent has
its own Forgejo user, which owns `finance-agent/finance-agent` with Haku as a write collaborator
(`tf/gitops/finance-agent`). Any permission the finance preset has that Haku lacks is a gap to
close or a named exception, not a design choice. Open work: [`haku/TODO.md`](../../haku/TODO.md).

The `coinbase` PolicySet combines GET egress and **`get` on
`agentplane-staging/coinbase-api-credentials`**. Managed Haku and finance-agent presets and the
static `claude-ai` and `haku-agent` PolicyBindings select it; static Haku identities retain their
direct RoleBinding. Public coder does not receive this access. Tests name the Secret scope,
resource, verb, and object literally, not by a Role whose rules could grow.
Static Haku retains redundant narrow inventory bindings; managed Haku's broader
cluster reader covers those rules without selecting the same Role names.

`test_cluster_integration` compares the rendered, active RBAC rule coverage for
each identity separately, using the Flux-owned namespace readers. It rejects the
retired Kyverno policy, dedicated background-controller ClusterRole, and old binding
names in rendered manifests, and checks binding scope against namespace classification
labels (including the rendered Flux bootstrap overlay).
It checks static/managed parity, finance's exact Coinbase addition, and
explicit denials for staging operator/login and node proxy (every profile).
The separate legacy accounts have their own contracts; their permissions are not
unioned with Haku's to mask missing access on a particular path.

`cluster/validation/agent_rbac.py` compares binding scopes, API groups, resources
and subresources, verbs, resource names, and non-resource URL prefixes. Unsupported
Role aggregation fails closed. The retired Kyverno expansion evaluator is removed. This is a declarative
RBAC contract, **not** proof of live deployment or complete agent capability parity:
built-in authorization, external identity group membership, admission constraints,
egress, Actions policies, and authority reachable through exec/node proxy need
separate verification. The broad Haku diagnostics Role is deliberately unchanged;
narrowing its Flux capabilities is a follow-up policy decision.

### Namespace reader migration: Kyverno to GitOps

`cluster/cdk8s/namespace_access.py` declares namespace diagnostics once.
`namespaces.py` derives labels from it; service charts no longer choose a second
classification. `agent_namespace_rbac.py` emits static bindings referencing the
same ClusterRoles as the managed catalog. Agentplane still owns the lifecycle of
each sandbox ServiceAccount's bindings. No group grants blanket sandbox access,
and no namespaced reader is bound cluster-wide.

Each namespace has its own Flux Kustomization, dependent on its namespace owner
and the shared Roles. An unavailable namespace cannot block readers elsewhere.
The bootstrap `flux-system` label remains in its hand-written overlay during the
migration; the integration test checks it against both projections.

**Stage 1 ([#8731](https://github.com/agentydragon/ducktape/pull/8731)):** adds
`agent-diagnostics-metadata` / `agent-diagnostics-logs` RoleBindings while retaining
Kyverno's old `agent-readable-*` bindings. The names are distinct, so Flux never
adopts Kyverno's synchronized objects. Stage 1 tests proved exact equivalence and
static/managed parity without counting the old bindings.

**Stage 2 (this follow-up; deployment-gated):** removes
`generate-agent-diagnostics-readers` and the dedicated
`kyverno-background-controller-rolebindings` ClusterRole. Other Kyverno policies,
controllers, Helm settings, and cleanup-controller grants are unchanged. Reader
ClusterRoles, Flux-owned bindings, managed presets/delegation, and Coinbase access
are unchanged from stage 1.

**Do not merge stage 2 merely because stage 1 has merged or CI is green.** An
operator must first record deployment evidence:

1. All 31 `agent-namespace-rbac-*` Flux Kustomizations are Ready at a revision
   containing stage 1, with no suspension or reconciliation failure.
2. All 58 replacement RoleBindings exist with the expected namespace, subjects,
   and roleRef from the stage-1 generated manifests. Their names are
   `agent-diagnostics-metadata` / `agent-diagnostics-logs`, not `agent-readable-*`.
3. Check representative allowed reads and denials through each static access path
   and a fresh managed public-coder/Haku/finance sandbox. Use each identity's own
   credentials and `kubectl auth can-i`, not the deployment catalog as proof.

After stage 2 reconciles:

- Verify the retired ClusterPolicy and dedicated ClusterRole are absent.
- Verify the old `agent-readable-metadata` / `agent-readable-logs` bindings owned
  by this Kyverno generator are gone, while all 58 replacements remain. Do not
  assume synchronized cleanup completed or that Helm/Flux reconcile order is
  guaranteed. If old objects remain, have an operator review their exact
  namespace, name, Kyverno ownership metadata, subjects and roleRef, then delete
  only those legacy generated bindings through an approved cleanup operation.
  Do not delete by broad name prefix or touch the reader ClusterRoles.
- Recheck static and fresh managed access. Residual legacy grants are a migration
  failure even if access works, since they could defeat later revocations.

If stage 1 fails, leave Kyverno in place. To roll back stage 2, restore the retired
policy and its dedicated ClusterRole together; leave the new bindings in place.
Verify the old generator has reconciled before ever rolling back stage 1. This
follow-up's green tests prove declarative parity, **not** live deployment or cleanup.

### Shared managed-agent diagnostics

The staging `public-coder`, `finance-agent`, and `haku` presets compose the same
namespace-scoped diagnostics bundle in `cluster/cdk8s/agentplane/staging_config.py`:

- Metadata in every active `agent-readable-*` namespace; pod logs only in the
  log-approved namespaces, including `agentplane-staging`.
- Cluster-wide read-only inspection through `cluster-diagnostics-reader`, including
  RedisReplication, legacy Flux Terraform, and OpenTofu Workspace resources.
- The existing Ducktape Flux, Haku Console metadata, ClickHouse diagnostics,
  public-coder VolSync status, and public-coder reader Roles. The last Role is an
  explicit service-specific exception allowing logs in `public-coder-agent`, whose
  common namespace classification is metadata-only.

Public coder and finance agent share diagnostics grants. Finance also
selects the explicit Coinbase credential grant; public coder does not. Both
also select the existing `public-coder-agent-node-reader` and
`public-coder-agent-cluster-metadata-reader` ClusterRoles, bound cluster-wide:
node inventory, CRD schemas, and node metrics. Both now select Haku's same
secret-free `cluster-diagnostics-reader`, but neither receives Haku's `haku-sandbox`
writes.
Action policies remain separate from these Kubernetes grants.

These bundles are plain deployment-side grant lists, not a new API. The broad
cluster reader is an explicit `cluster-diagnostics` PolicySet selection. Metadata
and log readers retain their separate namespaced RoleBindings; service-specific
Roles retain their existing rules and ownership.
Haku composes the shared reads with its existing additional authority below.
The testing environment's public-coder preset does not select these staging grants.

Preset changes affect **new Sandboxes only**. After deployment, launch a new Sandbox
(or explicitly migrate through the operator workflow), then check its effective
access with `kubectl auth can-i` and exercise the intended reads. In particular,
verify Ducktape Flux access and approved logs. Verify
that staging operator login and staging Sandbox lifecycle/exec remain denied; every profile
must also remain denied node proxy access, and public coder and finance Secrets/exec outside
their explicit permissions. Namespace diagnostic reads in staging are distinct from operator access. Do not treat
a configured catalog or preset as proof that existing Sandboxes received bindings.

The initial `sandbox-tool-config` catalog entry separately proves narrow ConfigMap
read selection. `namespace_access.py` is the single reviewed namespace classification.
It generates namespace labels, static RoleBindings, and managed catalog entries.
Log-approved namespaces receive metadata and pod-log grants; metadata-only
namespaces receive metadata alone. An absent namespace grants nothing. Props stays
excluded because its Namespace is absent and its Flux source is parked.
The `flux-system` and `ducktape-flux` delegation Kustomizations have no `dependsOn`:
they are bootstrap roots without generated owner Kustomizations. The cluster integration
test derives active label opt-ins and checks their catalog grants, all three preset defaults, and
target-owned delegation dependencies together.

### Managed Haku additional authority

The Haku preset currently selects `cluster-diagnostics-reader` cluster-wide,
`haku-sandbox-admin` within `haku-sandbox`, the common metadata and pod-log readers
within `agentplane-staging`, and the combined `coinbase` PolicySet, which grants GET egress and
`get` on exactly `agentplane-staging/coinbase-api-credentials` via the existing
`claude-ai-coinbase-reader` Role. The latter Role's name predates managed grants; its rules are
shared while its static RoleBinding (legacy `claude-ai` plus all three Haku identities) remains
Flux-owned. The static `claude-ai` and `haku-agent` PolicyBindings also select the combined set.
The preset also selects the existing Haku Console metadata and ClickHouse
diagnostics Roles in their respective namespaces. Their managed binding
delegation lives in separate Flux Kustomizations dependent on those services.
It also selects the `ducktape-flux` reader Role and the public-coder VolSync
status Role. The former namespace and Role are owned by the bootstrap Flux
source, so its independent delegation Kustomization has no generated predecessor;
the latter depends on the public-coder app Kustomization. Public-coder's wider
reader observes Pods, logs, ConfigMaps, service and workload metadata, RBAC/Flux
metadata, and Pod metrics. It grants no Secret read or Pod exec. Managed Haku's
broader cluster reader already covers public coder's two narrow cluster readers.

### Staging acceptance for managed Haku grants

After the stacked grant PRs deploy, use the staging operator UI to create two Sandboxes
from the Haku preset and one from public-coder with an explicitly empty Kubernetes
grant list. Record their Sandbox names as `HAKU_A`,
`HAKU_B`, and `OTHER`; wait for each Sandbox's `PolicyBinding` to report `KubernetesReady` before opening sessions.
Run these commands with the operator kubeconfig. Each inner `kubectl` runs **inside**
the Sandbox workload and uses its sidecar's substituted token:

```sh
for box in "$HAKU_A" "$HAKU_B" "$OTHER"; do
  kubectl -n agentplane-staging exec "$box" -c runner -- kubectl auth whoami
done
for box in "$HAKU_A" "$HAKU_B"; do
  kubectl -n agentplane-staging exec "$box" -c runner -- kubectl get nodes -o name
  kubectl -n agentplane-staging exec "$box" -c runner -- kubectl -n agentplane-staging get pods -o name
  kubectl -n agentplane-staging exec "$box" -c runner -- kubectl -n agentplane-staging auth can-i get pods/log
  kubectl -n agentplane-staging exec "$box" -c runner -- kubectl -n haku-sandbox auth can-i create jobs
  kubectl -n agentplane-staging exec "$box" -c runner -- kubectl -n agentplane-staging auth can-i create jobs
  kubectl -n agentplane-staging exec "$box" -c runner -- kubectl -n agentplane-staging get secret coinbase-api-credentials -o 'jsonpath={.metadata.name}'
done
kubectl -n agentplane-staging exec "$OTHER" -c runner -- kubectl get nodes -o name
kubectl -n agentplane-staging exec "$OTHER" -c runner -- kubectl -n agentplane-staging get secret coinbase-api-credentials -o name
```

The three `whoami` results must name three distinct
`system:serviceaccount:agentplane-staging:<sandbox-name>` principals. Both Haku boxes
must read Nodes and staging Pod metadata, answer `yes` for staging `pods/log`
reads and `haku-sandbox` Job creation, answer `no` for staging Job creation,
and return only `coinbase-api-credentials` from the Secret read. The last two
commands must return `Forbidden`. Never use `-o yaml`, `-o json`, `describe`, shell
tracing, or an agent transcript for the Secret: those can expose the key. The
metadata-only output above still performs a real Secret `get` without printing
its data.

For shared Role propagation, create a dummy `agentplane-grant-probe` Secret in
staging with a harmless literal value, then verify both Haku boxes are denied `get`
on it (`kubectl get secret agentplane-grant-probe -o name` prints only its name).
In a small Flux change to <../cdk8s/agentplane/actions_staging_policies.py>, add
the dummy Secret name to the existing `claude-ai-coinbase-reader` Role's `get`
resource names. After Flux applies the Role change, repeat the metadata-only `get`
from both **existing** boxes and verify both succeed without changing their binding
UIDs; `OTHER` remains denied. Revert the Flux change and delete the dummy Secret.
This tests shared Role updates, not preset re-resolution; the static `claude-ai`
identity temporarily gains access to only the dummy value too.

Finally, through the connected Agentplane MCP client, call `sandbox__create`, poll
`sandbox__get` until Ready, then call `sandbox__exec` with `kubectl auth whoami` and the same
metadata-only Coinbase read. Approve the Action if Agentplane requests approval. The expected
principal is the Agentplane sandbox's static
`system:serviceaccount:agentplane-staging:claude-ai`, not either managed Sandbox SA.
Dispose of the sandbox with `sandbox__dispose`. Check that deleting the suspended
managed Sandboxes removes their cross-namespace RoleBindings and ClusterRoleBindings;
verify by the Sandbox UID annotation, without dumping Secret contents.

### Grant inventory

This doc intentionally avoids a hand-maintained namespace matrix. Service-specific and
sensitive grants are sourced from the set of `*rolebinding-*.yaml` files under:

- `cluster/k8s/**/agent-rbac/`
- `cluster/k8s/**/gateway-agent-rbac/`
- `cluster/generated/agents/shared-rbac/`
- `cluster/generated/agents/namespace-rbac/`

Use `roleRef.name` in those files to determine which permission class is bound:
`namespace-diagnostics-reader`, `agent-readable-namespace-metadata`,
`agent-readable-namespace-logs`,
`logs-configmaps-reader`, or `secrets-reader`
(`secrets-reader` is an explicit per-service opt-in for
`kubectl-sandbox-users` only — never Haku), or a
service-specific reader Role/ClusterRole such as `reader` in `ollama`,
`log-reader` in `langfuse`, or `claude-props-reader`.

The common generated grants live in `agents/namespace-rbac/`. The shared policy
projects one of two descriptive labels onto each classified Namespace:

- `rbac.ducktape.io/agent-readable-metadata: "true"` describes the secret-free, log-free
  `agent-readable-namespace-metadata` baseline. Alongside core workload state, it covers
  safe operational metadata for autoscaling, disruption, standard/Gateway API networking, and
  Flux image automation. It deliberately excludes Secrets, ExternalSecret/SecretStore resources,
  Terraform controller objects, Helm/source/Kustomization values, Prometheus rules, pod logs,
  exec-like subresources, and all writes. The namespace must be explicitly classified in `namespace_access.py`. The existing
  `flux-system` Namespace has its descriptive label in the bootstrap patch at
  `cluster/k8s/flux/flux-system/kustomization.yaml`; its Flux-owned reader bindings
  grant access without a cluster-wide grant.
- `rbac.ducktape.io/agent-readable-logs: "true"` describes that metadata baseline plus the additive
  `agent-readable-namespace-logs` role, which grants only `get` on `pods/log`.

Both classifications grant the same subjects: Haku's OIDC and synthetic access-profile groups,
its in-cluster ServiceAccounts, `kubectl-sandbox-users`, and
agentplane-staging's `claude-ai` ServiceAccount. The Flux-owned bindings come from
`agent_namespace_rbac.py`; the Kyverno generator is retired. Sensitive or
identity-specific access remains explicit service RBAC.

Augur is parked in `gaffer-private` and has no namespace in the cluster. Its agent RBAC
is parked with it at `gaffer-private/k8s/parked/augur/agent-rbac/`, including an
in-namespace Role granting `pods/exec`, `pods/attach`, and `pods/portforward` for
debugging the single-replica augur deployment.

## Adding Agent RBAC for a New Service

1. For service-specific or sensitive access, create `<service>/agent-rbac/` with:
   - `kustomization.yaml` — lists the RoleBinding YAML(s)
   - RoleBinding YAML(s) referencing the appropriate ClusterRole from `agent-rbac-base`
2. Add the service's Flux Kustomization generator under `cluster/cdk8s/`; wire its
   namespace and agent RBAC dependencies in `generate_manifests.py`.
3. The service namespace kustomization has **zero coupling** to agent infrastructure.

## Authentication

Claude Code web sessions authenticate via an **Authentik-issued OIDC JWT**
that carries `groups: ["kubectl-sandbox-users"]`; kube-apiserver's
`AuthenticationConfiguration` maps that claim to
`oidc-ksbx-groups:kubectl-sandbox-users`, the Group every binding below
subjects on. JWTs are minted biweekly by the `authentik-jwt-rotation`
CronJob in the `agents-infra` namespace — see <../cdk8s/authentik_jwt_rotation.py>.

Machine JWTs from the `kubectl-sandbox-client-credentials` provider use a
separate explicit Authentik allowlist for effective groups. The normal provider
client-credentials principal maps to `kubectl-sandbox-users`; the `haku-k8s`
service account maps to `haku`; unknown machine principals receive no Kubernetes
RBAC group.

Laptops run their own admin kubeconfig (deployed by home-manager from
`secrets/shared/kubeconfig.yaml`) with cluster-admin-level access; it's
not governed by this sandbox RBAC. See
<lessons_learned/2026_04_24_k8s_auth_through_mitm_proxy.md>
for why Claude Code web can't use the laptop's path (L7 TLS-terminating
egress proxy eats client certs).

## Kubeconfig Provisioning

The Claude web JWT is minted by the `authentik-jwt-rotation` CronJob via
Authentik's `kubectl-sandbox-client-credentials` OAuth2 provider and committed
SOPS-encrypted to `secrets/claude-web-k8s-jwt.yaml`. At session start,
<../../devinfra/k8s/kubeconfig.py> decrypts it and builds a kubeconfig
with `user.token` auth pointing at `https://kubeapi.allegedly.works`
(the `HTTPRoute` in <../cdk8s/kube_api_proxy.py>).

The session start hook (background command in the web profile) writes
`~/.kube/config` to a real file for interactive `kubectl` use. MCP clients should
use connected Agentplane MCP Actions when configured for Kubernetes operations.
Discover the available Actions and current policy, then verify the Action's execution
identity against this RBAC source of truth; an MCP connection alone grants no Kubernetes
permissions. See <agentplane_mcp_staging.md> for the staging MCP setup and boundary.

## Security Considerations

- **Write isolation**: Full CRUD only in `claude-sandbox` namespace
- **Broad read**: Cluster-wide diagnostics read; see <../cdk8s/agent_rbac_base.py>
- **Resource quotas**: see <../cdk8s/agent_rbac_base.py>
- **Flux reconciliation**: Diagnostics grant only read access to Kustomizations, not
  patch access. The former annotation-only Kyverno policy is removed with that grant.
