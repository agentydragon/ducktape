# Plan: cdk8s adoption for cluster manifests

**Status: phase 1 landed for its first Kustomization.** `cluster/k8s/litellm/app` (minus
`deployment.yaml`, see § "The other real catch") is now fully cdk8s-generated and
committed, pinned by `//cluster:test_generate_manifests`, which passes against Bazel's
real hermetic `cdk8s`/`jsii` toolchain. Carried forward from the original spike
(<https://github.com/agentydragon/ducktape/pull/6840>). `litellm/servicemonitor` no
longer exists as a separate Kustomization — human PR #7103, landed independently on
`devel` while this was in flight, folded it (and six other monitor-only Kustomizations
across the cluster) into their owning components; rebasing onto it meant regenerating
into the merged `litellm/app` shape instead of fighting it (see § First cutover). Nothing
else has converted yet.

## Goal

Let some Flux Kustomizations' manifests be generated by Python cdk8s instead of
hand-written, without changing how Flux discovers or applies them, and without a
big-bang rewrite of the cluster tree.

## Phase 1 (this phase)

- Generated and hand-written manifests **coexist directly in `cluster/k8s`** — no
  side output directory, no separate publish branch. Flux keeps reading `devel` exactly
  as it does today; a cdk8s-generated file is just another committed file under a
  Kustomization's directory.
- **Convert one whole Flux Kustomization at a time.** A directory either is fully
  hand-written or has its application manifests fully generated, with two named
  exceptions that stay hand-written even in an otherwise-generated directory: SOPS
  secrets (cdk8s has no key material) and any resource carrying Flux's `$imagepolicy`
  marker (a YAML emitter can't reproduce the comment it depends on — see § "The other
  real catch"). Not a general per-resource escape hatch — just these two.
- **CI pins generated output to committed output**: a Bazel test regenerates the
  manifests in-memory and asserts the result equals the committed file, exactly the
  "generated-output snapshot" pattern STYLE.md already codifies for
  `cluster/k8s/litellm/app/proxy-config.yaml` (STYLE.md § Testing, "the LiteLLM config
  pattern"). This is a `gazelle -mode=diff`-shaped check, not a new idea — cdk8s adoption
  reuses it rather than inventing a parallel mechanism.
- Because that check is an ordinary `py_test`, it runs for free inside the existing
  `bazel-ci` job in `.github/workflows/ci.yml` — **no bespoke GitHub Actions workflow
  needed.** Recommend dropping PR #6840's `cdk8s-manifests-experiment.yml`, including its
  opt-in publish-to-`cluster-manifests`-branch job: that mechanism solves a problem
  ("where does generated output live before it's trusted") that phase 1 avoids by
  committing output directly.
- First concrete target: finish converting `cluster/k8s/litellm/app/` (see § First
  cutover). Nothing else converts until that one is merged and has run in production for
  a while.

## Does this mix well with hand-written Flux manifests?

Yes — the mechanisms that wire Flux Kustomizations together don't know or care how a
directory's manifests were produced:

- The root `cluster/k8s/kustomization.yaml` includes each Kustomization as a flat
  `<dir>/flux-kustomization.yaml` line. Adding a converted directory is exactly the same
  one-line change as adding a new hand-written one.
- `dependsOn` addresses other `Kustomization` objects by `name`/`namespace`, not by
  file. `litellm/app/flux-kustomization.yaml` already depends on ten other
  Kustomizations (`litellm-secrets`, `litellm-db`, `gateway`, `external-secrets-config`,
  `monitoring-crds`, ...) this way today, entirely independent of how `litellm/app`'s own
  manifests are authored. A cdk8s-owned Kustomization depending on hand-written ones, or
  vice versa, is the same graph edge either way.
- `cluster/validation`'s structural checks (`test_crd_layering`, `test_flux_build`)
  operate on **rendered** `kustomize build` output (`KustomizeBuildResult`), never on
  source text. They're provenance-blind by construction — a generated Deployment and a
  hand-written one are indistinguishable to them.
- kubeconform validates everything under `cluster/k8s/**/*.yaml` unconditionally
  (`.pre-commit-config.yaml`'s `kubeconform (cluster)` hook has exactly one exclusion:
  Flux's own auto-generated `gotk-components.yaml`). A committed generated file gets the
  same schema validation as a hand-written one for free.

So: yes, it works, and no new cross-Kustomization wiring mechanism is needed. The one
real constraint is **secrets**. SOPS-encrypted `*.sops.yaml` files must stay
hand-maintained forever — cdk8s has no key material and has no business synthesizing
ciphertext. This is already satisfied by the existing convention of splitting secrets
into their own `<service>-secrets/` Kustomization (the CRD-layering rule already forces
this split for unrelated reasons — see `cluster/AGENTS.md` § Flux Kustomization Wiring).
A cdk8s-owned directory should simply never be the one holding a `.sops.yaml`.
`ExternalSecret` objects are fine to generate — they carry no ciphertext, only a
pointer at a `SecretStore` key.

## Granularity: one Flux Kustomization at a time

Converting at Kustomization-directory granularity is the right unit because it's the
unit every other structural rule already uses — the CRD-layering split (operators /
secrets / app), the flat-vs-grouped directory examples in `cluster/AGENTS.md`
(`k8s/aiquota/` vs `k8s/langfuse/{namespace,secrets,db,app}/`), and the root
kustomization's one-line-per-Kustomization inclusion list. cdk8s adoption doesn't need a
new organizing principle; it just adds, per existing Kustomization directory, a yes/no
answer to "is this one generated."

**A fully-converted directory generates all three files, not just the app manifests.**
Earlier drafts of this plan kept `flux-kustomization.yaml` hand-written on the theory
that it's "small and important." That's not a real argument — nothing about the Flux CR
is mechanically different from any other resource cdk8s emits: it's YAML built from
string data (name, namespace, `sourceRef`, `dependsOn` entries), and § "Does this mix
well" already established that Flux's dependency graph doesn't care who produced a
`Kustomization` CR. So per converted directory:

- `flux-kustomization.yaml` — generated. Use one shared cdk8s construct (e.g.
  `FluxKustomization` in a `cluster/flux_constructs.py` every converted directory's
  generator calls) for the boilerplate that's genuinely constant across the fleet
  (`apiVersion`, `kind`, `sourceRef.kind: ExternalArtifact` with `sourceRef.name`
  defaulting to the Kustomization's own `name`, `namespace: ducktape-flux`,
  `prune: true`), parameterized for the fields that vary per service today
  (`interval`/`timeout`/`retryInterval`, `wait`, `healthChecks`, `decryption.provider:
sops`, `dependsOn`, `annotations.description`). Centralizing the boilerplate is a real
  win — right now every one of the ~150 `flux-kustomization.yaml` files repeats it by
  hand.
- `kustomization.yaml` — generated too; it's just `resources: [<name>.k8s.yaml]` plus
  whatever `namespace:` the directory sets, no reason to hand-maintain that either.
- `<name>.k8s.yaml` — generated, committed, one file per cdk8s `Chart`. The spike's own
  CI workflow already used this suffix (`litellm.k8s.yaml`,
  `litellm-servicemonitor.k8s.yaml`); phase 1 keeps it. Needs a `.gitattributes` /
  `ruff.toml` exclusion note if prettier would otherwise reformat cdk8s's own YAML
  emission and fight the pinning test — not yet checked against a real prettier run.

**The one real catch: `dependsOn` rationale comments.** Live examples
(`inventree/app`, `docker-ci`, `aiquota`) carry per-entry `#` comments explaining _why_
each dependency exists — "mirrors inventree-sso-providers into the inventree
namespace", "No storage dep (emptyDir, not a CSI PVC)". Across the current
`flux-kustomization.yaml` files that's ~186 comment lines, not a rare occurrence.
cdk8s's YAML emission (`Yaml.format_objects`, same as plain `yaml.dump`) does not
preserve comments — there's no hook for "emit this list entry with a trailing
comment." First real instance, decided rather than hypothetical: PR #7103 added
`litellm/app`'s `monitoring-crds` dependency with the comment
`# the ServiceMonitor/PodMonitor CRD`; the generated version drops it — `monitoring-crds`
reads as self-explanatory without it, matching "accept the loss where a dependency is
self-explanatory from its name alone." The Python source still documents the reason
(`cluster/generate_manifests.py`, as an ordinary comment on the `FluxDependency(...)`
call) for whoever edits the generator next — it just doesn't reach the YAML. A
dependency that genuinely needs its rationale visible _in the manifest_ (not just the
generator source) still needs an answer — carry it as a `reason` kwarg the shared
construct renders as something else, since `dependsOn` list items have no
comment-equivalent field — deferred until one actually shows up; flagged under § Open
questions.

"One big YAML per Flux Kustomization" (the user's framing) is right as the common case;
nothing here requires exactly one file if a directory's cdk8s program produces multiple
independent `Chart`s — `litellm/app` emits two, `litellm.k8s.yaml` and
`litellm-servicemonitor.k8s.yaml`, both into the same directory now that PR #7103 folded
the ServiceMonitor's own Kustomization away (§ First cutover).

## The other real catch: Flux's `$imagepolicy` marker

`litellm/app/deployment.yaml`'s image line carries
`# {"$imagepolicy": "flux-system:tana-litellm-proxy"}` — the inline comment Flux's
`ImageUpdateAutomation` scans for and rewrites on every new build (confirmed live:
`cluster/k8s/flux-image-automation-forgejo/tana-litellm-proxy-image.yaml` defines the
matching `ImagePolicy`). Same root problem as the `dependsOn`-comment catch above, but
worse: a YAML emitter dropping this comment doesn't just lose documentation, it silently
stops image automation for that Deployment — nobody notices until the image stops
updating. `deployment.yaml` also carries ~15 lines of rationale comments (why
`topologySpreadConstraints` is `ScheduleAnyway` not `DoNotSchedule`, tied to the
2026-08-09 outage; why `LITELLM_SALT_KEY` must never rotate; per-secret purpose notes)
that are individually less severe to lose but add up.

**Resolution for this cutover: any resource carrying an `$imagepolicy` marker stays
hand-written**, alongside SOPS secrets, as a named exception to "one directory, fully
generated" (§ Phase 1). `litellm/app` is otherwise fully generated —
`kustomization.yaml`'s `resources:` list is just `[deployment.yaml, litellm.k8s.yaml]`.
`ProxySpec`/`LiteLLMProxy` in `cluster/litellm_constructs.py` no longer build a
Deployment at all (dead fields deleted, not left dangling) — extending the generator to
also own `deployment.yaml` needs a real answer to the marker-comment problem first, not
before.

## First cutover: `cluster/k8s/litellm/app` — done

Landed: `litellm.k8s.yaml` (ConfigMap, Service, ServiceAccount, HTTPRoute, the
forgejo-images ExternalSecret) and `litellm-servicemonitor.k8s.yaml` (ServiceMonitor) are
generated and committed under `cluster/k8s/litellm/app`, replacing the prior hand-written
per-resource files there and in the now-retired `litellm/servicemonitor/` directory.
`flux-kustomization.yaml` and `kustomization.yaml` are generated too, via the shared
`FluxKustomization`/`kustomize_kustomization` helpers in `cluster/flux_constructs.py`.
`configMapGenerator` is gone from `kustomization.yaml`; `deployment.yaml` is the one
exception (§ above). `cdk8s-manifests-experiment.yml` and its `cluster-manifests`
publish-branch job are deleted — the pinning test is an ordinary `py_test`
(`//cluster:test_generate_manifests`) that `bazel-ci` already covers.

**Landing this took two passes**, not one: the first cutover generated into a separate
`litellm/servicemonitor/` directory (mirroring the pre-existing hand-written split).
Rebasing onto `devel` picked up PR #7103 — a human PR, landed independently and
concurrently, that folded `litellm-servicemonitor` (and six other monitor-only
Kustomizations across the cluster) into their owning components, for unrelated reasons
(fewer artifacts, shorter reconcile chains). The generator moved to match: one `App`,
two `Chart`s, both outputting into `litellm/app/`. Worth recording as a real data point
for § "Does this mix well": an independent structural change to the _hand-written_ side
of the cluster, landing concurrently with the _generated_ side's own first cutover,
needed the same reconciliation a rebase always needs — not a special case because one
side was generated.

**Operational note for the next directory**: this session's local `bb run`/`bazel build`
could not fetch some unrelated external Bazel archives from `github.com` (hit on two
unrelated repos across two separate attempts — `protoc-gen-validate`, `rules_perl` —
needed only to analyze the `//devinfra`/`//cluster` packages at all, not caused by this
change) while `bbr`'s remote runner fetched them fine. `bbr run` doesn't sync a target's
arbitrary file writes back to the local checkout the way `bbr build`/`bbr test` sync
declared outputs — so the working fallback was a throwaway venv (`pip install` the exact
versions pinned in `requirements_bazel.txt` at the time: `cdk8s==2.70.103
cdk8s-plus-33==2.5.56 jsii==1.140.0 constructs==10.8.1` — re-check the current pins,
these drift) to run `python3 -m cluster.generate_manifests` directly and commit its
output, then verify with `bbr test //cluster:test_generate_manifests` — which passed
against Bazel's own hermetic toolchain both times, confirming the pip-generated files
are exactly what Bazel would have produced. Try `bb run` first; fall back to this only if
it hits the same class of fetch failure.

## Explicitly deferred (not decided, not scheduled)

Recorded so they don't get re-litigated as if phase 1 requires deciding them now:

- Generating the _entire_ cluster tree with cdk8s.
- Moving Flux's authoritative manifests into their own branch (`cluster-manifests` or
  similar), so generated output stops living on `devel`.
- Building the authoritative manifests in CI instead of committing regenerated output on
  every generator change.

Any of these would change where the pinning test in phase 1 points (from "the committed
file in `cluster/k8s`" to something built later), so they're easier to evaluate once
phase 1's actual pattern has run for a while, not before.

## Open questions

- ~~Exact `.gitattributes`/`ruff.toml`/prettier treatment for `*.k8s.yaml`~~ — resolved:
  `litellm.k8s.yaml` and `litellm-servicemonitor.k8s.yaml` pass `prettier` and
  `kubeconform (cluster)` unmodified as committed. No exclusion needed, at least for this
  shape of output.
- `//cluster:generate_manifests` now hardcodes its two output directories (no
  `--output-dir` flag) — matches phase 1's "write directly to `cluster/k8s`", but isn't
  yet a general per-directory regeneration entrypoint. Revisit when a third directory
  converts and the hardcoding actually needs generalizing, rather than guessing the
  right shape from two data points.
- How to carry a `dependsOn` rationale comment through generation when one is genuinely
  needed _in the manifest itself_ — see § "A fully-converted directory generates all
  three files". The one real instance so far (`monitoring-crds`) was resolved by
  dropping it as self-explanatory, with the reason kept in the generator's Python source
  instead. Still open for a case where that's not good enough.
- How to let a fully-generated directory still carry an `$imagepolicy`-marked (or
  otherwise comment-load-bearing) resource without falling back to "the whole directory
  stays hand-written" — see § "The other real catch". Only matters once a converted
  directory's Deployment needs image automation; `litellm/app`'s stays hand-written for
  now.
