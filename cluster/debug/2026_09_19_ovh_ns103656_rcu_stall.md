# `ovh-ns103656` worker hang with CPU 7 RCU timer warning — 2026-09-19

**Status:** recovered after an OVH service intervention; the original trigger remains
unresolved. The IPMI session request and both Manager hard-reboot tasks failed, but the
host subsequently rebooted and rejoined Kubernetes after the intervention. Its exact
actions are not recorded here. The evidence does not distinguish a kernel, firmware,
hardware, or other cause.

## Summary

The Talos worker stopped reporting to Kubernetes. Its kernel log showed an RCU stall
warning on CPU 7 with the same `timer-softirq` count in two warnings 88 seconds apart.
Kubelet health checks timed out, followed by CRI/containerd health-check timeouts. This
is evidence of a CPU-local timer/softirq path failing to make progress, but it does not
identify why. See the [Linux RCU stall detector documentation](https://docs.kernel.org/RCU/stallwarn.html):
an unchanged timer-softirq count is a reason to suspect timer handling, not proof of a
specific hardware or kernel defect. Following an OVH service intervention, the host
booted with a new boot ID and returned Ready. A separate BPF verifier warning occurred
while Cilium loaded a program during that boot; Cilium subsequently reported healthy.
Neither recovery nor the BPF warning identifies the original stall's cause.

on other workers, not this node; the earlier Mimir compaction burst was on
`ovh-ns103711`. There is no evidence attributing this incident to Mimir.

## Console and diagnostic limits

- The Talos API stopped responding before the reboot, so no pre-stall support bundle or
  live stack trace was collected. After the intervention, direct Talos API access
  returned and the post-boot `talosctl dmesg` was collected; no support bundle was
  captured. A node-exporter sample was available at 04:13, but a later port-forward to
  its pod could not be established; its stale Kubernetes `Running` status was not proof
  that the pod was still responding.
- OVH's IPMI self-test passed its HTTP, authentication, and ping checks. A fresh browser
  SoL session still failed with `Unable to establish IPMI v2 / RMCP+ session`. SSH SoL
  reached OVH's gateway and identified the service, but showed no host serial output.
- A later OVH Manager **Tasks** view showed two `IPMI access request` errors (18 Sep
  22:00:53 and 22:01:37; displayed timezone not shown). Both reported that OVH could not
  instantiate an `ipmi/javaKvmSession` because its `ipmitool ... mc info` command exited
  with status 1. The view also showed the two reboot errors at 22:37:41 and 22:40:55:
  `Internal error while hard rebooting`. These task details expose no lower-level BMC
  error. Other IPMI self-test checks showed green results, but that does not establish
  that the actual session or reboot command succeeded. The IPMI task output contained
  internal address and credential fields; they are intentionally omitted here.
- The image configuration includes `console=tty0` and `console=ttyS0,115200n8`
  ([OVH Talos image configuration](../cluster/terraform/main/ovh-nodes.tf#L116)). This
  routes new kernel output to serial; attaching later does not replay earlier boot or
  kernel messages. Talos is API-managed and has no normal shell or SSH session ([Talos
  FAQ](https://docs.siderolabs.com/talos/v1.12/troubleshooting/faqs)).
- The BMC System Event Log (SEL) was not obtained. OVH Manager's intervention history
  is a separate service record, not the SEL. OVH documents the distinction between
  customer-launched tasks and data-center technical interventions ([service logs and
  intervention history](https://docs.ovhcloud.com/en/guides/account-and-service-management/account-information/security-specifications-dedicated-servers));
  its [IPMI guide](https://docs.ovhcloud.com/en/guides/bare-metal-cloud/dedicated-servers/ipmi)
  documents KVM, SoL, IPMI testing, and IPMI reboot, but does not document an SEL viewer
  in Manager.

`ns103656.ip-147-135-39.us`, covering approximately 2026-09-19 01:20–02:15 UTC; request
any CPU, timer, thermal, power, or memory/ECC findings, and request the service report

After the failed reboot tasks, the OVH server-details API returned `state: ok` and
`monitoring: false`. The service-state field is not evidence that the host OS is
responsive. `monitoring: false` means OVH's optional ICMP monitoring is disabled; the
setting was not changed ([OVH monitoring documentation](https://docs.ovhcloud.com/en/guides/account-and-service-management/account-information/security-specifications-dedicated-servers)).

## Context and next checks

`ovh-ns103656` was a former KS-5 control-plane node, but by this incident it had been
removed from etcd and was a worker; the three etcd voters were on NVMe-backed control
planes. The earlier HDD/etcd latency incidents are documented separately in
[the storage lesson](../cluster/docs/lessons_learned/2026_06_19_etcd_hdd_io_contention.md).
That history is not proof of this incident's cause.

The separate Talos upgrade canary `ovh-ns103711` was Ready and cordoned. Its PDB-aware
drain was blocked; no pods were evicted. That cordon did not take `ovh-ns103656` down.
At the final snapshot, Kubernetes still showed PVC-backed pods on `ovh-ns103656` as
Running despite deletion timestamps, so those API phases were stale. A reboot would
interrupt workloads on the host but would not itself delete their PVCs. Neither OVH
task produced an observed reboot, and no Talos upgrade was performed.

The host and Cilium recovered, but workload convergence was still in progress at the
last check. Recheck the remaining application pods and verify the OVH intervention
report, local-disk boot selection, and SEL response. Avoid another Manager reboot until
OVH explains the failed IPMI session and reboot tasks. If the stall recurs, capture the
full kernel warning and per-CPU timer/softirq counters while the node is still
reachable. A similar generic BPF verifier invariant warning was noted after a different
Kimsufi worker reboot ([separate incident note](../cluster/debug/2026-05-31-kimsufi-worker-1-notready/README.md#reboot));
that does not connect either warning to this node's earlier RCU stall. The separate
evaluation of OVH monitoring and interventions is tracked in
[issue #7278](https://github.com/agentydragon/ducktape/issues/7278).
