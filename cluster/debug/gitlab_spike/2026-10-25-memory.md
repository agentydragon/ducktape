# GitLab component memory, 2026-10-25

## Measurement boundaries

Memory is the Kubernetes Metrics API's per-container working-set measurement,
summed by component and namespace, in GiB (2³⁰ bytes). This is observed usage,
not resource requests, limits, process RSS, or a guaranteed idle floor. PostgreSQL
includes its Barman sidecars; webservice includes Workhorse. Shared SeaweedFS and
the separate Runner namespace are excluded.

Independent component medians need not sum exactly to the median namespace total.
Background jobs continue in quiet windows. Fresh processes, cache state and replica
changes limit causal comparisons; use the separate loaded benchmark result for
its original workload, not as a matched baseline for a quiet deployment.

## One Puma worker per Pod

PR #12047 merged as `bef51ac5521faa201fb5d6363cc4e12910ff27a8`, setting
`gitlab.webservice.workerProcesses: 1`. Two app Pods and four threads per worker
give two request worker processes and eight request threads across the deployment.
The Puma parent and auxiliary processes remain.

The observation starts with a pre-rollout snapshot whose webservice metric timestamps
are 22:24:13 and 22:24:18 UTC. Post-rollout sampling requires exactly two ready app
Pods with `WORKER_PROCESSES=1`, and Helm Ready at its current generation. Startup
surge Pods are excluded from the comparison. No load benchmark is run in this window.

### Rollout observations

The first replacement, `6cd7fd8955-clkf4` on `ovh-ns103656`, was created at
22:24:33 UTC. Its logs confirmed one worker and four threads. Liveness checks killed
the Rails container during initialization at 22:27:34, 22:30:34 and 22:33:34.
Process snapshots found the Ruby parent waiting in `folio_wait_bit_common`; logs
continued to advance through Rails and API initialization. Node memory usage was
46% in one snapshot. These observations support startup filesystem I/O being a
contributor; they do not fully attribute the elapsed time or prove a worker-count
regression. This node did not host either old app Pod.

Helm release v7 failed on the Deployment's progress deadline at 22:34:36 and rolled
back successfully at 22:34:43, retaining the two ready old app Pods. Its automatic
retry created `6cd7fd8955-7zbqq` on the same node and also restarted during
initialization. PR #12049 proposes a native startup probe with a bounded five-minute
budget before normal liveness checks begin. It does not speed up initialization.

**Post-change memory effect is not yet measured:** as of this observation the
one-worker rollout is incomplete. Do not count an initializing surge Pod as a
successful replacement or report its lower memory as savings.
