# GitLab component memory, 2026-10-25

## Measurement boundaries

Memory is the Kubernetes Metrics API's per-container working-set measurement,
summed by component and namespace, in GiB (2³⁰ bytes). This is observed usage,
not resource requests, limits, process RSS, or a guaranteed idle floor. PostgreSQL
includes its Barman sidecars; webservice includes Workhorse. Shared SeaweedFS and
the separate Runner namespace are excluded.

Independent component medians need not sum exactly to the median namespace total.
Background jobs continue in quiet windows. Fresh processes, cache state and replica
changes limit causal comparisons; use the separate loaded benchmark result for
its original workload, not as a matched baseline for a quiet deployment.

## One Puma worker per Pod

PR #12047 merged as `bef51ac5521faa201fb5d6363cc4e12910ff27a8`, setting
`gitlab.webservice.workerProcesses: 1`. Two app Pods and four threads per worker
give two request worker processes and eight request threads across the deployment.
The Puma parent and auxiliary processes remain.

The observation starts with a pre-rollout snapshot whose webservice metric timestamps
are 22:24:13 and 22:24:18 UTC. Post-rollout sampling requires exactly two ready app
Pods with `WORKER_PROCESSES=1`, and Helm Ready at its current generation. Startup
surge Pods are excluded from the comparison. No load benchmark is run in this window.

### Rollout observations

The first replacement, `6cd7fd8955-clkf4` on `ovh-ns103656`, was created at
22:24:33 UTC. Its logs confirmed one worker and four threads. Liveness checks killed
the Rails container during initialization at 22:27:34, 22:30:34 and 22:33:34.
Process snapshots found the Ruby parent waiting in `folio_wait_bit_common`; logs
continued to advance through Rails and API initialization. Node memory usage was
46% in one snapshot. These observations support startup filesystem I/O being a
contributor; they do not fully attribute the elapsed time or prove a worker-count
regression. This node did not host either old app Pod.

Helm release v7 failed on the Deployment's progress deadline at 22:34:36 and rolled
back successfully at 22:34:43, retaining the two ready old app Pods. Its automatic
retry created `6cd7fd8955-7zbqq` on the same node and also restarted during
initialization. PR #12049 merged as `4a79f62ab31cbc3ac46a9a5956e9a2a1cb06bb06`,
adding a native startup probe with a bounded five-minute budget before normal
liveness checks begin. It does not speed up initialization.

The final Helm upgrade, release v14, completed at **23:26:46 UTC**. Flux subsequently
reported Ready and Healthy. Both remaining app Pods run one Puma worker and four
request threads, confirmed by environment, native startup logs and the process list.

| Pod suffix        | Node           | Created  | Ready    | Rails restarts |
| ----------------- | -------------- | -------- | -------- | -------------: |

| `d74cd56bc-9h8vz` | `ovh-ns102453` | 23:25:19 | 23:26:44 |              0 |

The first Pod's initial attempt was also killed by the **startup probe**, at
23:22:04. Its retry started at 23:22:35 and reached Ready in 2m44s. The second Pod
reached Ready 85 seconds after creation. This demonstrates eventual rollout,
not reliable cold startup within five minutes. No further probe budget was raised;
the slow-start attribution remains open.

### Observed memory effect

Twelve captures at approximately 25-second intervals span **23:58:50 UTC on
October 25 to 00:03:27 UTC on October 26**. Underlying metric timestamps span
23:58:11–00:03:14. Both replacements were already over half an hour old at the
start. Replica counts remained unchanged for every component; both app Pods
remained Ready, with restart counts one and zero unchanged across observation.

- **Webservice:** 6.613 → 4.714 GiB, a reduction of **1.899 GiB (28.7%)**, or
  approximately **0.95 GiB per Pod**. After-sample range: 4.709–4.729 GiB combined.
- **Namespace:** 11.757 → 9.895 GiB, a reduction of **1.862 GiB (15.8%)**.
  After-sample range: 9.873–9.920 GiB.
- **Sidekiq:** 3.200 → 3.205 GiB with two concurrency-ten Pods; effectively unchanged
  over these quiet windows. Other component changes were small.

No load benchmark or profiler ran during this sampling window. These observations
show a lower quiet-period footprint with one worker; fresh process/cache state and
elapsed time prevent attributing every byte to the worker setting. They do not
establish throughput or latency equivalence to the two-worker benchmark. The
original 15.31 GiB loaded result remains a separate measurement.

### Remaining Puma process overhead

After rollout, `/proc/*/smaps_rollup` snapshots on both Pods found one parent,
one request worker, a metrics server and a logger. Approximate per-Pod PSS was
**1.05–1.06 GiB for the Puma parent**, **1.12–1.13 GiB for its worker**, and
**0.06 GiB for metrics/logging combined**. PSS apportions shared pages rather
than counting them fully in both processes. These process snapshots are separate
from container working-set measurements and do not exactly reconcile with them.

One worker per Pod still leaves a large preloaded parent. The reduction therefore
does not remove an entire independent copy of the application's RSS per worker.
[Post-rollout readiness, startup and process evidence](results/2026-10-25-puma-tuning/post-rollout.json)
retains the native observations without heap contents or memory mapping addresses.
