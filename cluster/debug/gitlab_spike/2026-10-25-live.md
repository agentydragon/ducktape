# GitLab replacement spike: live rollout, 2026-10-25

Status: deployed; provisioning, first and repeat OIDC login, CI → OCI → Flux → running
app, paired benchmarks and one controlled Gitaly primary isolation were demonstrated.
**This is evidence for further replacement work, not production migration readiness.**

- Tiny contents writes: GitLab median **0.930 s**, current Forgejo **2.600 s**.
  Tiny pushes: **0.980 s** versus **1.620 s**; no failed operations in 800 samples.
- Full-history clone medians were similar: **33.54 s** versus **34.79 s**.
- Observed server-namespace memory was **15.31 GiB** versus **1.31 GiB** under load.
  Shared object storage and Runner are excluded from both figures.
- A primary partition caused one failed push before promotion; the next push succeeded.
  Its acknowledged commit remained readable during isolation and after all replicas recovered.
- Backup/restore, SSH transport, LFS and disposable membership revocation remain unproved.
  Initial database seeding required manual recovery; first sign-out was visibly slow.
  Times below are UTC.

## Performance comparison method

Run the existing, unmodified GitLab and Forgejo benchmark scripts against the live
spike and current production Forgejo, using the same pinned client image and worker.
Use five paired batches, alternating product order, each with 20 samples per operation.
Report medians and tails, failures, batch variation, versions, placement and resource
usage. Retain raw CSVs and timings; exclude credentials and raw authenticated logs.

This compares candidate GitLab with local HDD Gitaly replication against current
Forgejo storage, as approved. It does not isolate storage media or filesystem effects.
Keep historical results separate from current paired results.

Historical references:

- [July comparison](../git_storage_latency_and_ha.md): GitLab/Praefect on SeaweedFS
  SSD versus Forgejo on SeaweedFS SSD. The July GitLab HDD rows also use network
  SeaweedFS, not local HDD volumes.
- [October canary](../piraeus_migration/benchmarks/README.md): single-writer Forgejo
  local HDD, Piraeus one/two-copy HDD and SeaweedFS controls. These are different
  deployment shapes and measurement dates, not a current HA head-to-head.

## Paired API/Git results

Measured 07:44:47–08:00:43 UTC, five alternating pairs, 100 samples per operation
and product. All 600 API responses were successful and all 200 Git pushes exited
successfully. The scripts emit a synthetic HTTP status of 200 for successful Git
pushes; that column is not an observed HTTP response for the Git operations.

| Operation      | Forgejo median / p95 (s) | GitLab median / p95 (s) | Forgejo / GitLab median |
| -------------- | -----------------------: | ----------------------: | ----------------------: |
| Version        |            0.359 / 0.435 |           0.054 / 0.074 |                   6.60x |
| Contents read  |            0.501 / 0.606 |           0.119 / 0.170 |                   4.22x |
| Contents write |            2.600 / 4.677 |           0.930 / 1.528 |                   2.80x |
| Tiny Git push  |            1.620 / 2.350 |           0.980 / 1.620 |                   1.65x |

[Raw batches and summary](results/2026-10-25-api-git/) retain the individual
runs; p95 uses nearest rank. GitLab's write-batch medians ranged 0.862–1.076 s;
Forgejo's ranged 2.446–4.259 s. The 100 samples are grouped into five sequential
batches, not 100 independent workload trials. This is a serial, small-file,
warm-path application benchmark, with live production/GitOps background load.
GitLab uses a PAT; the existing Forgejo script uses HTTP Basic account/password
authentication on requests and pushes. API endpoints, payloads and initialization
also differ. The API speedups therefore include authentication and platform
costs; the version request does not measure repository storage. No cache flush
or concurrent-client throughput test was performed. A controller
no-drift check overlapped the second pair. No own CI retry, bulk transfer or
failure injection ran during these paired measurements.

The client was pinned netshoot v0.13, digest
`a20c2531bf35436ed3766cd6cfe89d352b050ccc4d7005ce6400adf97503da1b`, on
`ovh-ns102453`, using each product's internal HTTP service. Forgejo was
15.0.8-rootless, digest
`8f97b55ca162ef3b538c6c78a2a077df9f2143c41d80b2bc6b6920f8d430df34`, with two
application replicas and the existing `seaweedfs-ovh-ssd` RWX repository PVC.
GitLab was 19.5.1-ee with two Webservice replicas and three local-HDD Gitaly
replicas. Sidekiq used the chart's autoscaler rather than a fixed replica count.

Resource samples from 07:51:35 onward, excluding benchmark clients, showed median
server-namespace memory of approximately **15.31 GiB for GitLab versus 1.31 GiB
for Forgejo**, and median sampled CPU of **1.454 versus 0.523 cores**. These
include each namespace's PostgreSQL and Valkey, and GitLab's Toolbox/Praefect/
registry. They exclude shared SeaweedFS and the Runner namespace. Sidekiq scaled
to four replicas during measurement (and five during subsequent cleanup/bulk
transfer); these are observed load samples, not idle resource floors or measured
CPU cost per request. Raw aggregate samples accompany the results.

Both dedicated benchmark accounts had empty inventories before measurement.
Forgejo's inventory was empty after the scripts' cleanup. GitLab's five DELETE
requests scheduled deletion and renamed projects with a `deletion_scheduled`
suffix; they did not immediately remove them. Cleanup verified the five IDs
2–6, dedicated owner, current-run creation times, expected paths and deletion
marks, then used `permanently_remove=true` with each exact full path. The
benchmark account's inventory was subsequently empty. Historical scripts were
kept unmodified; future manual runs need this final verified cleanup step.

## OIDC finding

The human login attempt at 08:03:19 failed with `The request is otherwise
malformed`. Authentik logged `Invalid grant_type for provider` with
`authorization_code`; a read-only database query showed `gitlab-spike|{}`.
The deployed authorization handler checks the requested grant against the
provider's grant list before proceeding. PR #12005 adds the omitted
`grant_types = ["authorization_code"]` to the existing Tofu owner. It merged as
`513e2c0139d97188af09a4607ec9759e21d8e817`; the SSO controller applied at 08:09:00
and a subsequent read showed `{authorization_code}`. The human confirmed that
initial login and a subsequent login both worked. API checks establish one intended
non-admin `agentydragon` account (ID 3), the declared OIDC subject and all four declared
SSH public keys. See [curated API evidence](results/2026-10-25-acceptance/acceptance-api-proof.json).
SSH key presence does not establish SSH transport behavior.

Sign-out eventually completed but appeared slow in the browser. The observed
`POST /users/sign_out` completed in 123 ms at Workhorse (59 ms Rails) at 08:14:58;
`GET /users/sign_in` completed in 236 ms at 08:15:50. The roughly 52-second gap
between requests is unexplained without browser/proxy evidence. No logout fix is
claimed, and a GitLab sign-out does not by itself prove an Authentik session logout.

## Controlled Gitaly primary partition

The guarded harness at `ef7589e55efd888a9bba93a9290a04ca8a001230` (PR #12009,
merged as `7edbbafdfa33a11556be1712e250c50426839d9a`) completed one controlled
partition of `spike/acceptance`'s current Gitaly primary. It used only the
project-scoped Developer credential and preserved existing refs.

On Cilium v1.19.8, the gate observed the same Pod UID, the isolated endpoint
identity, `ready` endpoint state and realized ingress/egress policy. A fresh
primary TCP connection timed out while a healthy peer remained reachable; both
had been reachable before labeling. No push began until those checks passed.

- Original primary: `gitlab-spike-gitaly-default-0`; promoted primary: `default-2`.
- First post-gate push at 08:31:33 failed with HTTP 500; retry at 08:31:36 succeeded
  by 08:31:37. The measured 3.618 s is from first post-gate push attempt to
  acknowledgement, **not total partition outage duration**.
- Acknowledged commit `b9658454a5226be13ca83a82d2f810e366f5d82a` was readable and
  freshly cloned during the partition. `git fsck` succeeded.
- The fault label was removed at 08:31:39. All three replicas converged after six
  polls, reporting checksum `5f11370057658bfdcb90ebfb38495b843c256e63`.
- The same commit remained readable after recovery, a fresh clone and `git fsck`
  passed, and pre-existing refs were unchanged. All three original Gitaly Pods
  remained Ready without replacement. The run completed at 08:32:21.

[Fault evidence](results/2026-10-25-primary-isolation/) retains the probes,
metadata, checksums, refs and push attempts. The synthetic proof branch remains
in the acceptance project. This is one network partition with an acknowledged
write, not a general zero-RPO, power-loss, Praefect quorum or disaster-recovery proof.

## Remaining replacement gates

- Rehearse coordinated GitLab/Praefect and object-store backup/restore. CNPG WAL
  backup configuration alone does not establish application recovery.
- Exercise SSH clone/push, LFS push/fetch and recovery, real repository/data
  migration, AGit and existing Forgejo-specific agent permissions/workflows.
- Add a separately declared disposable membership for drift correction and
  revocation. The only managed membership is the human Owner; it was not altered.
- Make a clean initial deployment reproducible without the guarded manual native
  seeding recovery used in this run.
- Investigate slow sign-out if it recurs; current backend logs do not explain it.
- Resolve or accept the existing experimental Praefect/Kubernetes topology,
  disabled Gitaly cgroup isolation and bootstrap PAT renewal constraints documented
  in the component README. Resource costs need an explicit production decision.

These gaps prevent calling this a completed production Forgejo replacement.
