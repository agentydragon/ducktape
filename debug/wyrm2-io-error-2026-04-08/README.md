# wyrm2 IO Error — 2026-04-08

## Symptom

VM 110 (wyrm2) entered `qmpstatus: io-error` with frozen console. QEMU block
status showed `drive-scsi4: I/O status: nospace`. Happened twice within ~45 min.

## Root Cause

**ZFS Direct I/O write verification failures** on `rpool` (Sabrent SB-RKT5-4TB NVMe).

Two `ereport.fs.zfs.dio_verify_wr` events in `zpool events -v`:

| Time     | `dio_verify_errors` | `zio_err` | `zio_offset`  |
| -------- | ------------------- | --------- | ------------- |
| 19:59:39 | 1                   | 0x5 (EIO) | 0x1d887d55000 |
| 20:41:46 | 2                   | 0x5 (EIO) | 0x20ba7c6a000 |

Both target `zio_objset=0x112` (274 = `rpool/var-lib-vz`), `zio_object=0x105`
(261 = inode of the scsi4 backing file). Stage: `DIO_CHECKSUM_VERIFY` — ZFS
wrote data, read it back, checksum didn't match.

## Why QEMU Says "nospace"

QEMU's default `werror` policy is `enospc` — pause on ENOSPC, report other
errors. But the `I/O status` field in `info block` shows `nospace` for **any**
write error that causes a pause, not just ENOSPC. The actual errno from the
host was EIO (5), propagated by ZFS DIO verify failure.

## Phase 2 Investigation Results

### PCIe: Clean

- Link: Gen5 x4 (32GT/s) — full spec, no degradation
- AER counters: **all zero** (`TOTAL_ERR_COR 0`, `TOTAL_ERR_FATAL 0`,
  `TOTAL_ERR_NONFATAL 0`). The `CorrErr+` flag in `DevSta` is sticky from boot
  init, not indicative of runtime errors.
- Root port (00:01.2): `CorrErr-`, clean
- `LaneErrStat: 0` on both device and root port
- `ECRCChkCap+ ECRCChkEn-` — ECRC not enabled, but with zero AER errors this
  is not a concern

### NVMe SMART: Clean

- 0 media errors, 0 error log entries, 100% available spare, 4% used, 57°C
- SMART self-assessment: PASSED
- **Self-test unsupported** — Phison PS5026-E26 controller doesn't implement
  NVMe self-test log (`Invalid Field in Command`)

### fio Verify Tests: Passed

- **DIO single-job (4G, O_DIRECT, 128K bs, crc32c verify)**: `err=0`, 32768
  write+read verify cycles, zero errors
- **Buffered single-job**: also passed
- **DIO stress (4 jobs, shared file)**: verify errors, but these are **false
  positives** — fio warns `multiple writers may overwrite blocks that belong to
other jobs`. Not real corruption.
- **No new `dio_verify_wr` events** generated by any fio test

### ZFS DIO Config

- ZFS 2.4.1-pve1 (OpenZFS 2.4.1, DIO introduced in 2.3)
- `zfs_dio_enabled = 1`, `zfs_dio_strict = 0`
- `direct = standard` on `rpool/var-lib-vz`
- `zfs_dio_write_verify_events_per_second = 20`

### ZFS Scrub

Started, in progress. No errors found so far.

## Unrelated: Python Segfaults

15+ Python segfaults on April 5 (boot day), 20:15–21:31, during Nix
builds. All crash in `_PyCode_ConstantKey` (code object constant interning) at
`mov rax, [r12+0x78]` where `r12=0xe7` (garbage `ob_type` pointer). System
Debian Python 3.13.5-2. `7 callbacks suppressed` = even more rate-limited.
**Verdict: CPython 3.13.5 bug**, not hardware. Unrelated to ZFS DIO.

## Assessment

Root cause is **unclear**. Two competing hypotheses remain:

1. **ZFS DIO bug** — DIO is new (OpenZFS 2.3.0, Jan 2025, ~15 months old),
   has known open issues under concurrent I/O ([openzfs/zfs#16695](https://github.com/openzfs/zfs/issues/16695)),
   and all hardware indicators are clean.
2. **Real hardware corruption** — DIO verify is correctly catching silent data
   corruption (NVMe, PCIe, or memory). The clean SMART/AER/fio results don't
   fully rule this out — fio exercises a different codepath than ZFS's internal
   DIO verify.

We have not observed the problem with DIO disabled (but we also haven't run
long enough to confirm the converse).

## Action Taken

Disabled ZFS DIO on the affected dataset as a trial:

```bash
zfs set direct=disabled rpool/var-lib-vz
```

This is managed by Ansible (`ansible/atlas.yaml`, tag `zfs`).

Routes writes through the ARC instead of Direct I/O. The
`DIO_CHECKSUM_VERIFY` stage won't fire. If the drive is genuinely corrupting
data, scrubs will catch it on read.

## Monitor

- Scrub result: `zpool status rpool | grep scan`
- Watch for recurrence: `zpool events -v | grep dio_verify`
- If errors recur with DIO disabled, hardware is the more likely cause
