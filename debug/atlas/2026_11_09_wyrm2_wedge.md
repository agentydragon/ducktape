# Wyrm2 wedge, 2026-11-09

Times are PST (UTC-08:00). The user rebooted Atlas to recover wyrm2. The
evidence establishes a guest/VM execution failure after a period of memory and
I/O pressure; it does not identify what stopped execution or prove that memory
pressure caused the wedge.

## Existing protection

- The previous boot and current generation have `systemd-oomd` and a
  `user.slice` pressure policy of 80%. The previous boot's oomd journal contains
  startup messages but no kills. Current `oomctl` shows a 30-second duration,
  80% per-user-slice limits, and no swap-monitored cgroups. The same systemd
  260.5 oomd unit and empty `oomd.conf` are present in the previous boot's
  initial system generation. Later configuration changes during that boot were
  not independently reconstructed.
- Pressure limits use the fraction of time all tasks in a monitored cgroup are
  stalled, averaged over ten seconds and above the limit for the configured
  duration. Historical user-slice PSI is unavailable; we cannot establish
  whether the threshold was crossed or why no kill occurred.
- `ManagedOOMSwap` is not enabled by `systemd.oomd.enableUserSlices`. The
  default swap policy acts only when both system memory and swap use exceed
  90%, and selects eligible descendants with swap use above 5% of total swap.
  Merely enabling it therefore does not prove it would have fired during this
  incident. Enabling it can kill an entire scope, including interactive work;
  inspect candidate scopes and evaluate in dry-run mode before choosing policy.
- VM 110's Proxmox configuration has no virtual watchdog. Inside the guest,
  systemd's runtime watchdog is disabled and the exposed `iTCO_wdt` is
  inactive. `kernel.sysrq=16` permits only sync via keyboard-triggered SysRq;
  privileged writes to `/proc/sysrq-trigger` have different rules.

## Next investigation and safeguards

1. Export per-user and system cgroup memory, swap and PSI, or keep a bounded
   local process/cgroup history. Alert on sustained PSI and swap pressure while
   preserving the relevant top cgroups. Current metrics cannot attribute the
   swapped pages to a process.
2. Evaluate a swap-aware oomd policy in dry-run and consider a lower user-slice
   pressure threshold based on observed workload, including the blast radius
   of killing a terminal or desktop scope. This mitigates pressure; it is not
   an established fix for the VM freeze.
3. If it recurs, before reboot capture Atlas's VM status and per-thread QEMU
   CPU/state and kernel stacks, plus guest task/memory stacks if the guest still
   responds. Record whether QMP and the guest agent respond. A tested watchdog
   could shorten recovery, but an automatic reset can destroy volatile evidence
   and cannot be assumed to work if QEMU itself is stuck.
