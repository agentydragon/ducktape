Bazel Python Typing Ecosystem State

A decision report on whether Ducktape should replace its Bazel-integrated mypy checker with Pyrefly, Pyright, pytype, Pyre, or ty.

Evidence snapshot: 2026-09-13 Ducktape baseline: origin/devel at d3a4de32a Validation: Bazel/BuildBuddy RBE probes plus source review
Decision Landscape Ducktape probes House style Trade-offs Evaluation plan Sources

Decision in one page

Recommendation: keep mypy as the required checker; do not switch globally today.

Ducktape already has the strongest production-shaped integration: an official Bazel aspect, explicit target dependencies, RBE-compatible execution, centralized configuration, and a working override/plugin model. The upstream rules_mypy runner update is worth taking independently; it removes the local fork without changing the checker decision.

Pyrefly is the only alternative that currently merits a serious side-by-side experiment. Its official Bazel rules integrate as a toolchain and aspect, and the mechanical adoption probe worked. However, two of six representative targets failed immediately on existing Docker and mautrix typing patterns. That is promising infrastructure, not switch-ready compatibility.

Best current CI choice
Mypy + upstream rules

Highest compatibility and lowest migration risk. Land the already-validated upstream runner cleanup.

Best alternative to investigate
Pyrefly

Native-looking Bazel shape and likely speed upside, but the rules are experimental and diagnostics are not yet compatible with Ducktape.

Best editor companion
Pyright

The existing LSP is useful for Nix/stdlib code. It is not currently a credible hermetic Bazel CI replacement.

What would justify revisiting the switch?

A full-repository Pyrefly run with target-equivalent dependency resolution, a stable config/suppression migration, and measured cold/warm RBE results. The decision should be based on compatible findings and changed-target latency, not a vendor speed claim or a small clean sample.

Candidate landscape

“Bazel support” here means more than being able to invoke a binary from a Bazel action. A useful replacement must understand the target graph, consume the Python provider information and declared dependencies, participate in output groups, run hermetically on RBE, and preserve enough of Ducktape’s existing configuration and typing semantics.

What happened in Ducktape

The alternate-aspect probes ran through bbr build against BuildBuddy RBE. They used --config=nolint and requested only the candidate’s output group so the result isolates the candidate checker rather than mixing it with Ducktape’s existing default aspects.

Mypy baseline and upstream runner

The existing mypy wiring passed a 13-target representative build. The same family of targets also passed with the upstream rules_mypy 0.41.0 runner in the focused cleanup change. This establishes a working baseline for the comparison.

Result: compatible with current target graph and house configuration.

Baseline evidence: 13-target BuildBuddy invocation. Upstream-runner evidence: focused representative targets and //util:kubernetes.

Important local context: the current fork sets cache=False because its cache merge/symlink path has been troublesome. That is a real infrastructure downside, but it is being addressed by the upstream runner change rather than by changing checkers.

Pyrefly: integration works

The official rules were added as a temporary Bzlmod/toolchain/aspect probe. The toolchain registered, the aspect traversed Ducktape Python targets, and the type-check output group behaved as expected.

bbr build --config=nolint --aspects=...pyrefly_aspect --output_groups=pyrefly TARGETS
Passes: //util:kubernetes, //finance/augur/fit:scoring, //skills/freecad/examples:render_dxf, //x/genome_analyzer:genome_analyzer.

Pass evidence: first two targets and second two targets.

Pyrefly: current typing incompatibilities

//x/inop/runners:containerized_claude failed on a return from Docker’s dynamic client: Pyrefly inferred Model | Unknown where Ducktape declares Container. This may be a stub precision or checker-compatibility issue; it is not an aspect wiring failure.

//x/ember:matrix_client failed with ten not-async diagnostics where mautrix stubs expose AsyncGenerator values that the code awaits. Ducktape’s existing mypy configuration has a targeted mypy-mautrix override, and the current mypy path accepts this target.

Representative result: 4/6 passed; 2/6 failed on already-known third-party/dynamic-library edges.

Failure evidence: Docker client diagnostic and mautrix diagnostics.

Pyright: blocked before target analysis

The available community rules were added through a temporary Bzlmod/git override because the repository has no release. The module extension failed while loading its checked-in pnpm lockfile: Ducktape’s pinned aspect_rules_js 3.4.1 requires lockfile version 9 or newer, while the ruleset supplies version 6.

fail: npm_translate_lock requires lock_version at least 9.0, but found 6.0
Result: no Pyright target was analyzed. Fixing the lockfile would only clear the first blocker.

Evidence: BuildBuddy module-loading failure.

The aspect source itself only passes ctx.rule.files.srcs to Pyright. It does not use the target’s Python provider/dependency graph, which is incompatible with Ducktape’s explicit-deps and hermetic-import expectations.

What was not “tested” as a false green

For pytype, Pyre, ty, and standalone/basedpyright, the blocker is upstream integration rather than a failed type check: no maintained Bazel aspect or hermetic Bazel package was found to add to Ducktape. A hand-written shell wrapper would test a new adapter that does not yet exist, not adoption of the ecosystem’s supported Bazel path. Those candidates are therefore recorded as runner/build-system gaps, not as passing checkers.

Fit with Ducktape’s house style

The important local contract is target-scoped, explicit, hermetic checking. Ducktape uses one Python library per source, explicit deps, Bazel-managed third-party packages, centralized checker configuration, and RBE-backed aspects. A candidate that only understands a filesystem project is operationally worse even if its standalone CLI is attractive.

Pyrefly’s own documentation is explicit that the Bazel integration does not consume pyrefly.toml; the aspect is configured separately. That can be clean, but it means a mypy-to-Pyrefly migration cannot simply preserve the root config file as the source of truth.[S6] Pyrefly documents a mypy configuration migration path for its CLI, but the mapping is a conceptual migration, not proof of Bazel-aspect parity.[S7]

Where alternatives are worse than mypy today

DimensionCurrent mypy positionAlternative downsideHow to measure or resolve it
Compatibility Known Ducktape patterns are already covered by targeted overrides, including mautrix and dynamic Docker APIs. Pyrefly rejects both patterns in a small six-target sample. Pyright’s available aspect does not even import the target graph. Build a diagnostic mapping for a broad target sample. Treat each suppression as a reviewed compatibility decision, not a blanket disable.
Configuration continuity Root mypy.ini, Bazel aspect settings, and the custom CLI are already understood by the repository. Pyrefly’s Bazel settings live outside pyrefly.toml; Pyright requires config/extra-path generation; runner-only tools need a new source of truth. Prototype one generated, checked-in or reproducible config contract before considering migration.
Plugin and stub ecosystem Mypy’s plugin and override mechanisms are imperfect but exercised in this codebase. No tested equivalent for Ducktape’s pydantic/sqlalchemy plugin setup and mautrix workaround was established for the alternatives. Inventory plugin-dependent targets and test them explicitly. Do not infer parity from clean stdlib targets.
Operational maturity Official rules are released, Bzlmod-aware, and already part of the CI architecture. rules_pyrefly is experimental; rules_pyright is unreleased and currently incompatible with the pinned JS lockfile; the others have no maintained Bazel path. Require a maintained release, reproducible toolchain, and a clear owner before making it a required check.
Performance Mypy’s known local cost includes cache behavior and a conservative cache=False setting. Pyrefly and ty may be faster, but public speed claims are not Ducktape measurements. A faster checker that adds config or false-positive maintenance can be a net loss. Compare cold and warm RBE actions, changed-target latency, remote-cache hit rate, and developer-visible diagnostics on the same target set.
Semantic continuity Mypy is the checker against which existing annotations, ignores, overrides, and review expectations have evolved. pytype’s inference-first/lenient model is deliberately different; Pyrefly/Pyright/ty diagnostics and narrowing behavior will differ even when both are “correct.” Define a compatibility policy: what counts as a required finding, an accepted difference, or a code change.

Recommended path

  1. Land the upstream mypy runner cleanup. It is an independently useful maintenance change and removes the local cache/symlink patch without taking on checker migration risk. The focused validation is already green; PR #6817 is the relevant change.
  2. Keep Pyrefly opt-in. Retain a temporary or experimental Bazel aspect configuration, but do not add it to the required default aspect set. Expand from the six-target probe to targets selected by typing risk: third-party stubs, pydantic/sqlalchemy, Docker clients, async code, and generated code.
  3. Resolve the semantic failures one by one. Determine whether the Docker diagnostic is a stub issue, a Pyrefly inference difference, or a real annotation defect. For mautrix, compare available stubs and decide whether a narrow Pyrefly suppression is acceptable. Preserve the existing mypy check while doing this.
  4. Measure the actual economics. On equivalent target sets, record cold/warm RBE action counts, wall time, changed-target latency, cache behavior, and diagnostic volume. Include the cost of maintaining two configs during the experiment.
  5. Revisit Pyright only if its Bazel integration changes materially. The minimum bar is a maintained release whose aspect consumes Python providers and deps, has a reproducible config story, and works with Ducktape’s current Bzlmod/JS pins.

Bottom line

It is worth investigating Pyrefly as a faster second checker. It is not yet worth replacing mypy in Ducktape CI. The likely near-term win is upstreaming the mypy runner fix and using Pyrefly as an evidence-generating sidecar until its target compatibility and configuration story catch up.

Scope and limitations

This report evaluates the current publicly available Bazel paths and a representative Ducktape probe, not every checker feature or a full-repository benchmark. The Pyrefly runs intentionally isolated its output group from Ducktape’s existing default aspects. The Pyright result is a real adoption failure at module loading, and source inspection found a second provider/dependency limitation; it is not evidence that the Pyright checker itself is poor.

“No maintained aspect found” means no credible current path surfaced in this review. It does not prove that no private, experimental, or newly published integration exists. The ecosystem moves quickly, especially for Pyrefly and ty; re-check release maturity before acting on a future migration proposal.
