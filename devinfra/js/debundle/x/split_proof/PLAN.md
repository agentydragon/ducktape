# Plan

The goal is to turn the production bundle in `gaffer-private` into runnable, readable modules following its authored spec, with a machine-checked guarantee that the split behaves like the original.

## Acceptance contract

Build the splitter with a proof about its **constructor**: for every original program and authored spec that meet a supported rule's preconditions, applying the rule produces the requested placement and preserves the requested observations. Check the proof when building the splitter. A split run checks the preconditions on its particular input and applies the rule. Checking two finished programs for equivalence can validate that one split; it does not discharge this construction obligation.

Given the original module graph and a proposed placement, the splitter certifies the output module graph or refuses. A certification states the [target theorem](#target): each source unit sits where the placement puts it, the entry exports the same public names bound to the same live cells (including the effects of generated imports and exports), and in every modeled world allowed by the strict contract, all observable modeled endings agree, including normal completion and throws and their effects. A proof of normal completions alone does not authorize publication, even for a reordered split. Applying the result to JavaScript relies on the [trusted parts](#trusted-and-tested); it is not a theorem for arbitrary JavaScript.

No public constructor rule currently establishes the full source/output and strict-observation bridge, so the publishing splitter refuses with `no_constructed_rule`. The production acceptance run uses the private bundle, its dependencies and the reviewed placement. Record the certified guarantee for the complete split, which authored boundaries it realizes, and the result of running the emitted application through its browser smoke test. Until it certifies, record the first reproducible blocker on that input. Keep the bundle, selectors and run artifacts in the private repository.

### Build the Lean placement spec from the existing spec

Keep the pinned original spec as the baseline. Derive the private Lean spec from its selectors, owner assignments and module order. Start with certified dependency-closed regions, then certify their unions through the ordinary splitter. A union can introduce initializer reversals that neither region exercised on its own.

When an authored placement changes observable behavior, save the smallest input and unchanged placement that exhibit the difference, and skip that extraction. An unsupported construct or a resource limit leaves the placement undecided. Track those cases for language modeling, proofs and optimization. Record any proposed change to ownership or order as an explicit diff from the original spec for review, and replay the resulting placement at emission and from disk.

**Acceptance priorities.** Replay the named spec on the pinned bundle with current Rust. Record the engine revision and the outcome for each requested pull, including selector or build failures. For refused pulls, minimize the dependency-closed source and the requested placement while retaining the scheduling change that triggered the refusal. If two pulls pass individually and fail together, keep the pair as the case under review.

- If the original and candidate differ observably under the intended contract, retain the counterexample and revise the placement or leave the affected units together. The stack-derived key in the host replay above is one such counterexample.
- If the placement can be justified, identify the missing inference in the checker that refused it. Add the rule with its proof where applicable, a positive replay and a nearby unsafe control. Agreement on sampled Node or browser inputs alone leaves the proof obligation open.
- If the evidence is inconclusive, record the missing observation, semantic assumption or proof. Keep the pull unresolved until that question is answered.

For emitted candidates, retain the applied graph, JS and entry exports. Run the ordinary Lean disk check and browser smoke test. If Rust emits different module glue from the ASTs Lean derives, track that mismatch separately from the semantic status of the requested move.

Keep the stack-sensitive move as a negative control for exact host-state equivalence. [Chromium regression](https://github.com/agentydragon/ducktape/pull/19261). A location-preserving candidate must retain line and column as well as module URL, and reproduce the complete observed key and consumer behavior. Normalizing locations would require an explicit, separately reported observation contract covering the consumer's reads. Continue certifying other exact dependency-closed selections in parallel.

**Proposed V1 stack contract.** The caller may request a proof under a shared stack string. For every string `s`, run the original and emitted programs with every supported built-in error stack read returning that same `s`. Prove the requested outcome guarantee in that model and name this assumption in the certificate. The string is arbitrary but fixed across sites and repeated reads: two stacks that differ in a real runtime compare equal in this model. No line map is needed. The default certificate still uses exact observations.

V1 requires evidence of two facts at the read: the receiver was allocated by the realm's intrinsic `%Error%`, and property lookup reaches the host's supported built-in stack behavior on that receiver. An alias of the intrinsic can satisfy the first condition. A shadowed constructor named `Error`, an object made with `Object.create(Error.prototype)`, or a borrowed built-in getter on a lookalike cannot. An actual Error with its own replacement getter still runs that getter. Preserve receiver evaluation, constructor effects and exceptions; if a proxy or formatting hook has unmodeled behavior, refuse certification. Until the model can establish both facts, the shared-string rule cannot apply.

Substitute the string at the supported read so branches, property keys and later host calls use it. For example, a moved `registry[new Error().stack] = 1` should write `1` to `registry[s]` on both sides when those conditions hold; changing the write to `2` must still fail. TODO: consider logical frames and source positions if consumers need to distinguish stacks from different sites.

**Open deployment question.** For a relative import, consider naming the source and output layouts, their effective module URLs and the host's resolution rules as certificate premises. Check that the two graphs resolve to corresponding modules with the required live bindings and initialization effects. Even if both URLs load the same module, code reading `import.meta.url` can distinguish their strings. The stack contract leaves that observation alone. A future Bun profile would need its own evidence for resolution and loading.

## Target

The target is one total Lean function over CoreJS. Its soundness theorem has this shape (schematic):

```lean
split request X S = .ok (Y, A) →
  Permitted request A ∧                   -- only assumptions permitted by the strict contract
  Places S X Y ∧                          -- each source unit appears once, in the module S names
  SameExports X Y ∧                       -- same entry names, bound to the same live cells
  ∀ w, Satisfies w A → StrictEquivalent w X Y
```

`X` is the lowering of the original module graph. The lowering of the printed output must match the constructed `Y`. The public equivalence compares all supported observable endings, including throws and their effects; [`NormalEquivalent`](lean/EsmSplit/CoreJS/LinkedBehavior.lean) alone is insufficient. [`SameExports`](lean/EsmSplit/CoreJS/LinkedBehavior.lean) states the linking guarantee. Placement, linking and behavior must all hold for the constructed graph. A model diagnostic or a comparison of sampled JavaScript executions is not this certificate.

The planner may use unproved heuristics to propose operations. Write `Contract` for the conjunction above. The construction obligation is (schematically):

```lean
∀ request X S ops A, admit request X S = .ok (ops, A) →
  Contract request X S (applyOps X ops) A
```

The compiled splitter checks the proposed operations' preconditions and applies them. Prove once, when **building the splitter**, that the accepted operations compose to give this result. For example, the proof for an order-preserving rule must derive preservation of the linked execution order from the rule and its preconditions. Assuming that a comparison of the two finished schedules succeeds would only prove the comparison sound.

There is a separate check at the printer boundary. The proof above relates `X` to the constructed `Y`. The production CLI stages the printed files, reparses them, and checks that their lowering matches **that same `Y`** before publication. This detects, for example, a printer that emits the wrong export name. It does not establish semantic equivalence between `X` and an arbitrary reparsed program. With the current unverified printer this check belongs at split time; no Lean compiler or new equivalence proof is needed there. See [Trusted and tested](#trusted-and-tested) for the assumptions behind the JavaScript claim.

For example, if the spec says to move function `F` to module `M`, check that its free references still resolve to the right live bindings. If a required check fails, the target CLI exits with status 1, identifies the requested move and the unproved condition, and leaves any existing output untouched. It must not silently omit the move or substitute a weaker guarantee. Refusal means the splitter could not certify this request; it need not prove that the requested move changes behavior.

The public contract fixes strict observations and does not offer a weaker outcome guarantee or host/deployment premise override. Changed function source is harmless only if the proof shows the difference is unobservable, including through other code that receives the function. An unmodeled read is not evidence of unobservability. The separately proposed shared-stack-string contract is research, not a public certificate: it would evaluate each supported intrinsic Error stack read with the same arbitrary string on both sides, while preserving its use in a branch, write or host call.

A move proved only for normal completion is not sufficient for publication. In `const o = { a: undefined }; console.log("printed"); const w = o.a.b;`, moving the throwing read ahead of the log changes the effects before the throw ([historical experiment](experiments/README.md)). The proof must preserve those observable effects as well as successful results. CoreJS is the formal boundary; the theorem does not claim general JavaScript semantics or a trace of an unfinished run.

### Trusted and tested

The theorem starts and ends at CoreJS. These parts connect it to JavaScript. They are tested, not proved:

- Acorn's parse and eslint-scope's annotations.
- One lowering from annotated ESTree to CoreJS, written in Lean. It lowers the original graph and the reparsed output.
- CoreJS semantics and the world model for the supported fragment, including the host function table (`worldFunction` in [`Value.lean`](lean/EsmSplit/CoreJS/Value.lean)).
- Lean's kernel, which checks every proof when the tool is built, and Lean's compiler, which builds the checker that a split run executes.

The Node comparison suites ([`model/README.md`](model/README.md)) exercise the same lowering and interpreter as certification. The emitter and printer are not trusted: publication reparses the printed files and checks that they lower to `Y`.

### Decided

- **One lowering, in Lean.** The same Lean code lowers annotated ESTree for certification, for the `corejs` interpreter and for the Node comparison suites.
- **One guarantee.** Callers do not choose a proof technique or level. The verdict reports the evidence and premises it used.
- **No unchecked output.** Every written module graph is certified. Diagnostics report and write no modules.
- **No Lean at split time.** A certified split runs only compiled code. Host premises are data in a fixed vocabulary; adding a kind of premise is a code change, proved once when the tool is built.
- **The planner stays unproved.** Heuristics such as `Effects.lean` propose candidates. Their output counts as evidence only after a proved check accepts it ([footprint soundness](docs/footprint_soundness.md)).
- **A proved rule for a narrow fragment is worth landing.** It widens what the one checker accepts.
- **No new precision rule goes into the unproved footprint analysis** unless a measurement shows it is blocking. Fixing a wrong rule is always in scope, and its cost on the large bundle is measured before it is adopted.
- **The world is a parameter.** Real bundles reach unknown code: without P3, 1,751 of the large bundle's 9,707 units touch the world. The theorem holds for every world that satisfies the listed premises. A world reads and changes only what it is given.
- **The standard library is part of the world.** Each standard function gets a stated class of behaviour, such as "a function of its primitive arguments", "reads its receiver" or "may call its argument". That table is a tested assumption about the engine ([`docs/lessons_learned.md`](docs/lessons_learned.md) § The first slice of a model).
- **What is refused** ([`SUPPORT.md`](SUPPORT.md)): a top-level `await`, a top-level `using`, a direct `eval` anywhere, a name declared twice in one list. A `Proxy` is never covered by premise P3.
- **Premise P3 is not assumed for real inputs** (finding F7, 2026-11-21). Code of the program that the world runs can add a getter or a `toString` to an object the world holds, and the Claude bundles do it. Without P3 the analysis is sound for that, and the cost is small: 3 to 6% more units touch the world on three production bundles, and peeling barely moves ([`generator_findings`](translation/debug/generator_findings/README.md)). The cases and fuzzers still set P3, to test the analysis under it.

### Open decisions for the owner

- How the four input files with a direct `eval("require")` are admitted: a check of the string, or an audited premise.
- Whether a reviewed vendor table is worth its review cost. Alone it does not change which modules peel.
- Whether debundle's Rust gate stays as an extraction diagnostic once Lean certifies the production split. Readable names move into the checked split ([renames](#renames-inside-the-checked-split)); until then debundle emits its tree unproved and `translate` referees it.
- Whether the vendor chunk becomes part of the program in the model. It removes most unknown code, and the model then has to run what the vendor code runs at start-up, regular expressions included.

**Dynamic-guard theorem target.** Instrument the compiled probe run to produce both its result and `ProbeTrace`. Define `ProbeTrace.onlyPremised` to mean that the trace contains no `World.step` or `talk`, and that every `globalTypeof` and `hostRef` observation is in the collected premises. The intended general theorem is:

```lean
theorem ProbeRun.replayPremised
    {premises : HostPremises} {p : Program} {fuel : Nat}
    {probeState : State (premises.specialize World.probe)}
    {trace : ProbeTrace}
    (probeRun : ProbeRun.run premises fuel p = .ok probeState trace)
    (onlyPremised : ProbeTrace.onlyPremised premises trace) :
    ∀ w, premises.Satisfied w →
      runProgram (premises.specialize w) fuel p =
        .ok () (replaceWorld (premises.specialize w) probeState)
```

The checker compares both complete probe states and public exports before constructing `EquivalentFor`, `SameExports`, and the decoded `ASTEquivalent` result. The trace condition is the intended executable guard.

### Proof track

**N4. Widen the slice that moves code.** `moves_preserve` is proved; what `MayMove` covers is 69% of the large bundle's units. The active [footprint soundness work](docs/footprint_soundness.md) establishes a compositional contract for checked Effects output, starting with binding-only statements and keeping unsupported analysis rules outside the proved slice.

- _Opaque-code frame proof:_ [`OpaqueFrame.lean`](lean/EsmSplit/CoreJS/OpaqueFrame.lean) proves conversation framing from per-request conditions and commutation with allocation-only declarations in both directions. [`Reachability.lean`](lean/EsmSplit/CoreJS/Reachability.lean) now defines distinct object and binding nodes, rooted in handed objects and supplied bindings, following binding values, properties, accessors, prototypes and closure captures (including `this` and opaque captured cells). A closed envelope contains this least reachable set and excludes the protected region and initializer read bindings. [`Request/Frame.lean`](lean/EsmSplit/CoreJS/Request/Frame.lean) derives framing for the actual binding read, initialization, assignment and own-key requests from that invariant. It preserves the envelope on normal, thrown and unknown outcomes, including handing out an object and publishing an alias through another binding. When every request the world can issue preserves one fixed envelope, the full conversation and the world-backed statement preserve it too. A caught request exception can pass an accessible object handle back to the world before the next turn. Kernel-checked examples cover separated mutation, caught TDZ errors, immutable writes, forged handles and hidden captures.
- [Object allocation requests](lean/EsmSplit/CoreJS/Request/Allocation.lean) preserve the protected region and read bindings. The reachable-object envelope can grow by the newly allocated address. An explicit prototype comes from a supplied handle. Default construction requires the intrinsic Object.prototype in the envelope. A callback captures the supplied binding cells and inherits from Function.prototype. A constructible function also allocates an own prototype inheriting from Object.prototype. The envelope grows by the two fresh addresses and contains both sides of the constructor/prototype cycle. In the Excalidraw editor, unit 99 names only `Uint32Array` and `f6`, and the closure initialized at 98 has no free names. The frame for unit 99 must also cover callbacks and handles already handed to the world.
- _Prototype lookup:_ [`Request/Property.lean`](lean/EsmSplit/CoreJS/Request/Property.lean) frames prototype search even when replacing the protected region changes the total object count. The first matching property is on a path of distinct objects in the envelope, so either heap has enough search fuel. The actual `in` request uses this proof, and a property read uses it when getter calls also preserve the frame.
- _Move-rule target:_ for any world, fuel, linked state `s`, allocating pivot `p`, prefix `pre`, crossed units `crossed`, suffix `post`, and final state `t`, prove the same successful final states for `pre ++ crossed ++ [p] ++ post` and `pre ++ [p] ++ crossed ++ post`. The pivot must be `Local (p.id + 1) R`; the linked state must satisfy `Access [] A`, where `Away (p.id + 1) R A` excludes the pivot region and every initializer read cell. Every unit in `pre ++ crossed` must run in a different region, have its captured environment inside `A`, and preserve `Access [] A` while framing that region and `R`. Thus every successive swap starts inside the envelope, including callbacks through previously handed closures; direct free-name disjointness alone is insufficient. Only normal completion is claimed. [`runUnits_pivot_normal`](lean/EsmSplit/CoreJS/LinkedPivot.lean) already gives this result from `FramedUnits`.
- _Schedule composition target:_ let `units : Nat → LinkedUnit` be the linked units and `ready` the state **after** linking and function initialization. A prefix-aware Bool relation `allows ready pre i j` is sound when, for every fuel `n` and distinct in-range `i`, `j` absent from the distinct in-range `pre`, acceptance implies a predicate `I : State W → Prop` with:
  1. every successful `runUnits n (pre.map units) ready` ends in `I`;
  2. `CommuteOn I (unitStep n (units i)) (unitStep n (units j))` and the reverse `CommuteOn I` both hold.

  `I` may depend on the world, fuel, linked state, prefix and pair; the compiled Bool must not inspect the world's private state. Given a trace from the original order to the requested permutation, where each step swaps adjacent `i, j` after its actual `pre` and `allows ready pre i j = true`, prove that `runUnits` from `ready` has exactly the same successful final states in both schedules, for every fuel. Each trace step is checked in its current intermediate order, including prefixes produced by earlier swaps. Lift this result through [`moves_preserve_run_of_order`](lean/EsmSplit/CoreJS/Move.lean) to the `Ends` equivalence of `moves_preserve_of_sound`, under the same `Valid` and `FootprintsOfSyntax` premises and for every world. A compiled strategy checks the permutation, trace and per-step Bools, and transports checks on the probe linked state to each world's linked state; it returns only this proven CoreJS guarantee.

  Existing `MovesSound` relations lift into this contract with `I := fun _ => True`, so `MayMove` and a prefix-aware opaque rule compose by Bool disjunction at each swap. For the opaque arm, establish the access invariant after linking and throughout that swap's actual prefix, then use both frame commutations; do not assume the invariant survives the allocating pivot or arbitrary later units. A pairwise inversion check alone does not specify which intermediate prefixes to certify. The trace can be computed by the strategy; no Lean elaboration is needed when `split` runs. This is a target statement, not yet a proved theorem.

### 6. Imports and several chunks (18 entries: 12 multi-chunk, 4 `ImportDeclaration`, 2 specifier selectors)

Model it: `import { x } from "…"` as a hoisted definition of `x` plus a foreign module that evaluates first, so that `OrderOk` covers the order and a module that awaits at its top level is refused or handled.
- The 4 `ImportDeclaration` entries need three things of the adapter: literal values in its dump (`lowersplit` reads an import's source from `lit`; `dump` writes it), the modules written beside the chunk, where its relative imports resolve, and `import` statements left in the entry when debundle's spec moves one. A probe with the first two: `return_object_provider_import` is accepted and prints the chunk's output, `chunk_renames/named_imports` agrees, `chunk_rename_peeled_import` is rejected for an `import` outside the entry, `pruned_import_keeps_its_load_order` fails `OrderOk`.
- Model several chunks as one bundle each, with import edges between them. `Plan.visit` and `OrderOk` run over the union.
- Oracle for the evaluation order: `es_order/check.mjs` (500 random import graphs against Node). Add cross-chunk graphs.
- Largest step. Do it last.
