# Hosted Firecracker snapshot TSC restore failure

## Physical attempts and ownership

[PR #15493 CI attempt 2](https://app.buildbuddy.io/invocation/d1131cb0-8e38-509f-8b02-eaca85afba23) failed before its VM test result. The first physical attempt cold-booted, then its outer Linux 5.15 Firecracker guest panicked in scheduler load accounting before BuildBuddy could reach `fc.sock` to pause it. That attempt did not create the snapshot later loaded by the retry. The scheduler panic has a separate [canonical investigation](2026_11_02_scheduler_kernel_panic.md) and [tracking issue #14952](https://github.com/agentydragon/ducktape/issues/14952); its likely Linux defect and kernel-identity evidence should not be attributed to snapshot restore.

The second physical attempt had the same Bazel action digest `88a417ef177c880cea19732b91e1b66506cf12f00c5ae5ca9fe1f2704164a2b6` on `gke-prod-dtib7-spot-executor-c2-66369769-k94w`. Its retained execution response reports Firecracker 1.16.2 and a failed `PUT /snapshot/load`: `Could not set TSC scaling within the snapshot: Invalid argument (os error 22)`. The log shows matching Intel vendor IDs for host and snapshot, then the error; it does not include either CPU model or saved/current TSC frequency. [Issue #15581](https://github.com/agentydragon/ducktape/issues/15581) records a second C2-worker TSC restore occurrence on 10 November. Neither event proves the snapshot was produced on a different CPU model.

## Producer-side compatibility boundary

At [BuildBuddy source `1491988059`](https://github.com/buildbuddy-io/buildbuddy/blob/1491988059aa96853015dc07a164584bd1a8b48b/enterprise/server/remote_execution/containers/firecracker/firecracker.go), `getCPUID()` deliberately puts vendor and family into `VMConfiguration.host_cpuid` but omits model. `vmConfigurationHash()` contributes that configuration to the snapshot key. The [schema](https://github.com/buildbuddy-io/buildbuddy/blob/1491988059aa96853015dc07a164584bd1a8b48b/proto/firecracker.proto) has a CPU-model field and `VMMetadata.last_executed_task`; the [snapshot loader](https://github.com/buildbuddy-io/buildbuddy/blob/1491988059aa96853015dc07a164584bd1a8b48b/enterprise/server/remote_execution/snaploader/snaploader.go) stores VM configuration and metadata in its internal ActionResult manifest. The failed execution's public ActionResult exposes the consuming executor and scheduling CPU set, but no selected snapshot key or ID, creator task or worker CPU model, or saved/current TSC values. The first attempt's ActionResult was no longer in the cache when revisited on 12 November, although its VM log and physical-attempt record remain in the issue/report.

The root [`.bbrc`](../../../.bbrc) selects `kvm-clock` through `run-under` _inside_ the guest after restore. It cannot repair a TSC-scaling error raised by Firecracker before guest execution. A client-supplied snapshot key cannot safely encode the provider's actual CPU/TSC identity, and disabling remote reads would alter reuse and refresh behavior without a measured benefit. The smallest provider-side discriminator is to expose the selected snapshot key/ID and manifest's preceding task, producer and consumer vendor/family/model plus saved/current TSC frequencies or ratio, and the restore decision. BuildBuddy can then reject incompatible snapshots before loading them or fall back to a cold boot. This is a compatibility request, not a claim that cross-model reuse caused these incidents.

Kernel replacement is independent. [Upstream issue #13523](https://github.com/buildbuddy-io/buildbuddy/issues/13523) reports Linux 6.1 enabled for another organization, not verified for ours; the explicit [guest-kernel selector PR #13858](https://github.com/buildbuddy-io/buildbuddy/pull/13858) remains open. A provider-supported newer kernel should be verified by the actual guest identity and fresh, uncached VM executions, inspecting every physical retry for panics. No local snapshot policy, test coverage, or kernel pin was changed for this investigation.
