# Proposal: include active nested Bazel modules in CI selection

**Status:** design proposal for [issue #6636](https://github.com/agentydragon/ducktape/issues/6636), checked against `devel` at `4de7559104` on 2026-10-22. This does not implement CI changes. The issue is open but names the former shell selector and a `website` path absent from the current root override list; no overlapping open PR was found.

## Finding

PR CI keeps a root-workspace `bazel-diff` fast path, then runs `bazel test` and `bazel build` with the selected root labels. Pushes and graph-wide changes use `tests(//...)` / `//...` ([`bazel_ci.py:124-203, 211-264`](../ci/bazel_ci.py)). The seven nested module paths listed in [`.bazelignore:34-42`](../../.bazelignore) are also root `local_path_override`s ([`MODULE.bazel:132-165`](../../MODULE.bazel)). Root external-label dependency hashes can already select some root consumer tests; the certain gap is that root patterns do not themselves select module-owned labels, including checks with no root consumer.

The existing declarations do not make a CI policy: `.bazelignore` only excludes paths from root traversal, while `image_targets.json` and `artifact_targets.json` describe release artifacts and omit some modules/scopes. In particular, an image catalog entry does not say whether an ignored module is still active, or what to do when a module has no tests.

## Minimal design

Add one small `NESTED_MODULE_CHECKS` policy in `devinfra/ci/bazel_ci.py`, keyed by the module names already declared in root `MODULE.bazel`. Each entry has an explicit `active` or `excluded` status, a reason for exclusions, and exact test/build labels. Keep module paths out of this table: derive them from the root `local_path_override(module_name=..., path=...)` declarations. Their current literal form is visible at [`MODULE.bazel:132-165`](../../MODULE.bazel).

Use Python's standard `ast.parse` on the current Python-compatible `MODULE.bazel`; accept only direct top-level `local_path_override` calls with literal string `module_name` and `path` keywords. Reject parse errors, `include()` (which could hide overrides in another file), nested/dynamic calls, duplicate keywords, or other `local_path_override` argument forms with a line-numbered unsupported-declaration error; never evaluate the file. Allow unrelated parse-compatible root module calls. Before selection, validate that every root local override has exactly one policy status, every active policy identity has a matching root override, each normalized path stays inside the checkout and contains a `MODULE.bazel` with the same module name, and every check label uses that module's canonical root repo mapping or an intentional root consumer label. This catches a new local module that lacks a policy decision without duplicating identity/path pairs.

For ordinary PRs, preserve root `bazel-diff` and resolve changed paths against both revisions: use the base revision's override map for deleted/old rename paths and the head revision's map for added/new rename paths. The selected checks are the union of active head owners, de-duplicated with the existing root selection. Keep separate test and build patterns so build-only labels are not treated as test requests. Add module test labels to the test invocation and test-count query; add module build labels to the build invocation. An empty root affected set must not exit early if an active module owns a changed path.

For pushes and the existing graph-wide PR cases, append every active module's test/build scopes to the existing root full sweep. Keep the current root fast path for ordinary root-only changes. Run all labels from the existing root workspace with the same `--config=rbe --config=ci`, normal tag/platform filters, and invocation IDs; never change directory into a module or launch a second workflow. No-test modules still contribute their declared build targets. Unknown active ownership or an invalid policy/label fails closed rather than silently producing an empty selection.

If a base-only owner is absent from the head's local overrides and policy, treat it as a retirement candidate. Require the root `MODULE.bazel` removal and the normal graph-wide head run to verify surviving root consumers; do not demand that deleted module labels still load. For example, moving `third_party/activitywatch` while retaining `ducktape_activitywatch` maps the old path through base and new path through head, then runs its head checks once. Removing the Manifold module completely is clean only when its root override/dependency, policy entry, and root consumers are also removed; the surviving root full run checks the resulting graph.

## Execution boundaries and relationship to publication

This extends the existing GitHub Actions → BuildBuddy RBE invocation and its target evidence; it adds no GitHub API/service dependency or separate paid workflow. Public Haku checks use only the checked-in shared module and public console targets. Private `haku-state` work remains in its cluster. The additional module builds/tests cost CI time, so the first version deliberately runs whole supported scopes for only changed active modules, with no per-module hash cache or cross-run optimization.

Publication proposal B remains independent. B may use its existing safe fallback when a nested artifact digest is absent; C must not wait for B or change publication conditions. C's extra targets may appear in the normal BuildBuddy invocation evidence, but publication correctness does not depend on C selection.

## Small implementation slices and acceptance

1. Add the policy and literal override reader/validator; exercise literal multiline calls, duplicate/dynamic declarations, a path move, and policy/override mismatches with a few selector-focused fixtures.
2. Add owner selection and separate test/build patterns. Cover a source-only ActivityWatch importer edit, one Haku shared-file edit, a multi-module edit, a root graph-wide input, and a head-only new/removed path. Prove selection from changed paths without building the world locally.
3. In a separate small slice, register the existing Haku Python test source as `//haku/console:shared_tool_calls_test` (no new test body). Then verify on a normal PR that selected labels appear in the test/build BuildBuddy invocations and that existing CI filters still apply.

Acceptance is: each active source-only example selects its row's exact supported checks; root-only edits keep the existing fast path; full runs include active module scopes; inactive modules are not auto-enabled; retirement and rename cases resolve as described; and an unexplained active module cannot silently pass with no checks.

The open evidence question is whether future active modules need additional labels beyond these inspected rows. Resolve that by reviewing their BUILD targets and supported artifacts when adding their policy entry, not by broadening discovery to every ignored directory.
