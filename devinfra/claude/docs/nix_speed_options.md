# Faster Nix Package Installation Options

Analysis of approaches to speed up nix package installation in Claude Code web sessions.

## The Problem

Nix's cold-start is slow (~120s) because:

1. **Evaluation requires nixpkgs** - To compute a store path, nix must evaluate the package expression
2. **First run fetches nixpkgs metadata** (~50MB, takes 60-120s)
3. **Binary cache only helps after evaluation** - You need the store path first

Current workaround: `binary_tools.py` downloads binaries directly (~2s), but this duplicates version definitions with `.envrc`/flake.nix.

## Options Considered

### Option 1: Pre-computed Store Paths

**How it works:**

- CI evaluates flake, records store paths in a JSON file
- Session hook reads JSON, runs `nix copy --from https://cache.nixos.org $path`

**Pros:** No evaluation at runtime, uses official cache
**Cons:** Still needs nix installed, store paths change with nixpkgs bumps

```json
// tools/store-paths.json (generated by CI)
{
  "x86_64-linux": {
    "opentofu": "/nix/store/abc123-opentofu-1.9.0",
    "tflint": "/nix/store/def456-tflint-0.53.0"
  }
}
```

### Option 2: Pre-built Nix Store Tarball (Recommended)

**How it works:**

- flake.nix defines tools (single source of truth)
- CI builds, garbage-collects, and exports minimal store closure
- Publish tarball to GitHub releases
- Session hook downloads and unpacks to /nix/store

**Pros:**

- Single source of truth (flake.nix)
- No nix installation needed at runtime (just unpack + symlink)
- Hermetic - identical versions across local dev and Claude Code web
- Small tarball for standalone tools (~30-50MB)

**Cons:**

- CI complexity to build/publish tarball
- Architecture-specific (need x86_64, maybe aarch64)
- Must republish when updating versions

**CI workflow:**

```yaml
- nix build .#opentofu .#tflint
- nix copy --to file://./nix-export $(nix path-info -r .#opentofu .#tflint)
- tar czf nix-tools-x86_64-linux.tar.gz -C ./nix-export .
- gh release upload nix-tools-v1 nix-tools-x86_64-linux.tar.gz
```

**Session hook:**

```python
download("https://github.com/.../nix-tools-x86_64-linux.tar.gz")
tarfile.extractall("/nix/store")
symlink("/nix/store/abc123-opentofu-1.9.0/bin/tofu", "~/.local/bin/tofu")
```

### Option 3: Generate binary_tools.py from Flake

**How it works:**

- flake.nix is source of truth
- Script extracts version/URL info from flake and generates binary_tools.py
- Keep current binary download approach, just automate the version sync

**Pros:** Minimal changes, keeps fast binary downloads
**Cons:** Code generation complexity, still two "systems"

```bash
# Extract info from flake
VERSION=$(nix eval --raw .#opentofu.version)
URL=$(nix eval --raw .#opentofu.src.url)
# Generate binary_tools.py entries
```

### Option 4: Shared versions.toml

**How it works:**

- Define versions in a shared TOML file
- Both .envrc and binary_tools.py read from it

**Pros:** Simple, no nix CI needed
**Cons:** Manual URL maintenance, not truly "nix-native"

```toml
# tools/versions.toml
[opentofu]
version = "1.9.0"
url_template = "https://github.com/opentofu/opentofu/releases/download/v{version}/tofu_{version}_linux_{arch}.zip"
sha256.x86_64 = "..."
sha256.aarch64 = "..."
```

## Why Nix Doesn't Have a Package Index

The store path is a hash of the entire derivation tree (inputs, dependencies, build flags). You can't know it without evaluation. This is by design - it's what makes nix reproducible.

Efforts to improve this:

- **Lazy trees** ([PR #6530](https://github.com/NixOS/nix/pull/6530)) - Avoids copying nixpkgs to store, but still requires evaluation
- **FlakeHub resolved paths** - Pre-computed store path lookup, but proprietary

## Recommendation

For the current use case (2-3 standalone CLI tools):

1. **Short term:** Keep binary_tools.py - it works, it's fast
2. **If version sync becomes painful:** Option 2 (pre-built tarball) provides true single source of truth with minimal runtime overhead

The tarball approach is worth implementing if:

- More tools are added
- Version drift between local/.envrc and Claude Code web becomes a problem
- You want guaranteed reproducibility across environments
