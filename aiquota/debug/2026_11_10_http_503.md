# Intermittent HTTP 503, 2026-11-10

AIQuota recovered after an automatic Kubernetes restart. The observed restart
and collection sequence explains an observed readiness `503` and is a plausible
explanation for the user's uncaptured `503`; it does not prove the cause of that
exact request. The reason health probes missed their deadlines is unknown.
No live deployment, resource, probe, or application change was made during the
investigation. The candidate mitigation below changes declarative configuration.

## Observed chain

Times below are UTC. Pod `cli-proxy-api/aiquota-api-6d5584f446-sjgc9` runs on
`ovh-ns103711`, image `devel-20261108190457-e72d5d1`, digest
`sha256:cc933428e163edddb0046ab306f0b383be3f493a2856cd3b3beef0fcafcaadb1`.

- Kubelet recorded `/healthz` timeouts awaiting headers with a one-second
  deadline. The last was `08:28:46`; the same event records that liveness failure
  caused the container restart. There were seven restarts over approximately
  twenty hours, with six retained `Killing` events explicitly naming liveness.
- The old process continued logging successful HTTP responses during the
  slowdown. Before `08:28`, health responses appeared at `:05.298`, `:25.298`,
  and `:45.298` each minute. In the incident minute they appeared at `:06.553`
  and `:27.403`; no `:45` response followed. Readiness responses shifted from
  `:00.030`/`:10.030` cadence to `:23.990`, `:38.300`, and `:44.794`.
  These are response-log times, not measured request durations.
- Uvicorn logged shutdown at `08:28:47.065` and waiting for open connections at
  `08:28:52.439`. The container exited `137` at `08:29:16`, reason `Error`,
  rather than `OOMKilled`. The replacement started at `08:29:20`.
- At `08:29:43`, public `/` returned `303 /auth/login`. At `08:29:51`, public
  `/healthz` returned `200 {"status":"ok"}` and `/readyz` returned
  `503 {"status":"collecting"}`. The first successful provider collection and
  ClickHouse write completed at approximately `08:29:54`; EndpointSlice readiness
  returned at `08:30:01`. Both public probes returned `200` at `08:32:53`.

The user's original failing request was not captured. The observed readiness
`503` is application-generated; an Envoy no-backend `503` during restart is
consistent with this chain but was not directly reproduced.

## Ownership and source boundary

`cluster/cdk8s/aiquota.py` owns the singleton Deployment, probes, Service, and
HTTPRoute. Flux `ducktape-flux/aiquota` was Ready and the HTTPRoute had Accepted
and ResolvedRefs conditions. The Service selector selected the running pod.

`aiquota/server_main.py:main` starts one Uvicorn process. In `aiquota/api.py`,
`create_app` starts quota collection, history collection, and presentation timers
in the same event loop serving requests. `/healthz` is an async constant response;
it does not acquire the provider lock or call external services. `/readyz` waits
for the first persisted snapshot when ClickHouse is configured.

Provider requests and ClickHouse writes use awaited HTTPX async operations.
The deployed ConfigMap uses CLIProxyAPI management for Claude/Codex and
environment tokens for the two billing providers, bypassing the synchronous
credential-file paths. JSON/Pydantic conversion, hashing/base64 capture,
presentation construction, client construction, and access logging still perform
synchronous work. No observed stack identifies one as the incident cause.

The deployed Authlib code awaits discovery GET, token POST, and JWKS GET;
`joserfc` imports public keys and verifies JWTs synchronously. Starlette session
middleware uses cookie JSON/base64/signing and has no external storage. HTTPX
client construction synchronously loads CA certificates. A bounded `cProfile`
in a separate process inside the current container measured three warmed client
constructions at `0.103s` total (`0.101s` loading CA certificates). A cold profile
was `2.147s`, dominated by import/compilation, but the application had already
constructed provider HTTP clients before the incident. Neither profile proves
what the terminated process was doing.

## Hypotheses checked

- Sustained CPU throttling is unsupported: preincident two-minute CPU rates
  were approximately `6–12m` with negligible throttling. A `229m` sample was
  replacement startup, against its `250m` limit. Memory was `83–94Mi` against
  `256Mi`; the node had approximately `12Gi` available after recovery.
- Node I/O pressure coincided: three-minute I/O full-stall rate reached `23.2%`
  around `08:28`, while disk `sdb` was approximately `74%` busy. This does not
  establish which process or syscall delayed the response.
- The current browser OAuth flow coincided with slowdown, but retained Loki
  logs falsify login as a required trigger. Only two `/auth/login` responses
  and one callback occurred over this pod's lifetime. Earlier restart increments
  were observed at `16:46`, `19:18`, `22:54`, `00:43`, `03:23`, and `05:57`;
  the earlier login was `23:07:06`, between the `22:54` and `00:43` counter
  increments, more than an hour before the next restart.
- The last successful persisted snapshot before the incident was `08:25:11`,
  approximately three minutes before the browser activity.
- After recovery `/proc/1/wchan` was `do_epoll_wait`; the old process is gone.
  Talos kubelet logs were readable, but kernel logs were denied with
  `PermissionDenied: no request forwarding`.

## Remaining visibility and next diagnostic

Retained access logs have no request-start timestamp or duration. There is no
event-loop heartbeat, Python stack capture, or syscall trace for the stalled
process. Existing metrics establish failed deadlines and restart consequences;
they do not justify a particular resource, timeout, storage, or application patch.

During recurrence, capture all Python thread stacks and native thread wait state
while comparing event-loop progress with direct health-request latency. This
distinguishes synchronous Python/C work, blocking log/file I/O, and a network
path delay. An opt-in diagnostic could pair a loop heartbeat with bounded
`faulthandler` stack dumps; a Python-only watchdog can itself be delayed by a
held GIL, and periodic native watchdog rearming has overhead. A loop-lag metric
alone would confirm delay without identifying the blocker. Instrumentation and
its deployment require a separate reviewed change; none was added here.

## Candidate availability mitigation

Raise only AIQuota's liveness timeout from one to five seconds, retaining its
twenty-second period and three-failure threshold. One-second probe timeouts
coincided with successful health response logs drifting from their prior cadence
while the process continued serving requests. Request start times are unknown,
so this drift does not measure request duration. A five-second deadline allows
more time for responses, but this change may not prevent recurrence and does not
identify or repair the underlying stall.

Assuming a responsive kubelet and ordinary request timeouts, a permanent wedge
triggers restart approximately `40 + timeout` to `60 + timeout` seconds after
onset: `41–61s` before this change and `45–65s` afterwards. The pod's thirty-second
termination grace can add thirty seconds until SIGKILL; replacement startup and
initial collection add further downtime. Kernel uninterruptible sleep can prevent
prompt process exit even after SIGKILL. Readiness and resource limits are unchanged.

Roll back by removing `timeout_seconds=5` from the liveness probe in
`cluster/cdk8s/aiquota.py` and regenerating manifests. After deployment, inspect
probe failure counters and restart history separately from provider freshness.
