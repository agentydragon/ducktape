# `haku-dispatch` — parked dispatch-plane deployment

This directory is the canonical deployment package for the retired Haku dispatch
plane. The z.ai lane was retired in August 2026 and the package is parked by the
suspended `cluster/k8s/haku-dispatch.yaml` registration. The application code is in
`haku/x/dispatch/`; this cluster wiring is not runnable as-is until the worker-zone
and provider wiring is deliberately restored.

The in-cluster half of the former Haku dispatch plane: the dispatcher service, the shared
second-layer **workers-LiteLLM**, and the CNPG database they share. Application code:
<../README.md>. Zone perimeters (where the workers actually run):
<../../zones/README.md>. Design + roadmap:
<../../../archive/2026_08_multi_agent.md>.

Everything here is ducktape-reviewed — Haku can reach the dispatcher's API but has no
write path to any of these manifests.

## Layout

The Flux Kustomization and its resource/config files are all in this directory:
`namespace.yaml`, the CNPG database resources, dispatcher resources, workers-LiteLLM
resources, and their ConfigMap generator inputs. The `litellm/` subdirectory contains
only the Bazel generator and parity test for `workers-litellm-config.yaml`.

## Two-layer LiteLLM and the key chain

Provider keys must never be readable by Haku. The chain has three hops, and containment
comes from **reachability**, not secrecy:

- The **workers-LiteLLM** (`litellm-deployment.yaml`) runs here, chained to the main
  LiteLLM (`cluster/k8s/litellm/`). It holds the **zone keys** as upstream credentials —
  only this deployment mounts them. Its config is generated by
  `litellm/generate_workers_litellm.py` (imports the main generator's GLM list, so the
  two stay in lockstep) and parity-tested.
- The dispatcher mints a **per-job virtual key** on the workers-LiteLLM at Job creation,
  allowlisted to the zone's models with a budget + TTL. That is the only LLM credential a
  worker holds.
- `cnp-workers-litellm.yaml` admits **only zone-namespace pods and the
  dispatcher** to the workers-LiteLLM — never Haku. So a per-job key leaked through worker
  output is worthless anywhere Haku could reach it, and per-job keys can't be minted on
  the cluster-wide-reachable main LiteLLM for the same reason.

The dispatcher's **classifier** calls go to the configured Anthropic-compatible backend with a
scoped virtual key. The dispatcher holds no raw provider key at all.

> **Deviation (Flux layering):** the zone-key Terraform lives **downstream** of the
> serving LiteLLM (`cluster/k8s/litellm/keys-tf/` `dependsOn` the litellm app), because the
> TF provider needs a live LiteLLM to mint keys against. Putting it in the app's secrets
> dependency deadlocks the rollout.

## Database

One CNPG cluster (`postgres-cluster.yaml`, OVH-HA) hosts both the `dispatcher` database
and the workers-LiteLLM's `litellm_workers` key database — the repo's first CNPG
`Database` CRs. `db-role-secrets.yaml` defines managed roles: `dispatcher` (owns its
tables) and **`haku_reader`**, a member of `pg_read_all_data` whose password is reflected
into `haku-sandbox`. That role is Haku's read path (no GET API). Its `pg_read_all_data`
does span `litellm_workers`, but that DB stores only sha256-hashed virtual keys and spend
logs — `store_model_in_db: false` keeps provider credentials out of the database entirely.

## Dispatcher deployment notes

- All secrets arrive via `secretKeyRef` (pod specs are Haku-visible through
  `cluster-diagnostics-reader`; no secret value is ever inline).
- The reviewed **Job template** (`job-template.yaml`) and **zone wiring**
  (`zones.yaml`) are `configMapGenerator`-mounted, not live manifests
  (kubeconform-excluded, `cluster-manifest-ignored`). The image tag in the Job template
  tracks a Flux `ImagePolicy` marker.
- `rbac-zone-zai.yaml` is the dispatcher's write grant **into** the zai zone:
  `jobs` + the same-named per-job `secrets`, nothing else (no `pods/log`, no `exec`). One
  copy per zone namespace.
- Optional `dispatcher-classifier-context` Secret (SOPS, `sops -e -i` only — never
  plaintext) sharpens the classifier with private specifics; absent = base policy.

## Retirement record

The retirement was performed in two PRs. First, #3982 changed the two namespace
Kustomizations to `deletionPolicy: Delete` and was merged only after the policy
change could reconcile. The follow-up then moved this dispatch tree, the z.ai
zone, and the shared zone proxy under `cluster/k8s/x/` and removed their active
root registrations. This package move keeps the retired plane's reviewed
deployment closure beside its application code while leaving it suspended.
