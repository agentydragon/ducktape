Bazel target and wiring audit

A prioritized review of unused wrappers, ownership boundaries, naming drift and lint-driven dependencies. Findings are proposed work, not changes applied to the build.

Snapshot: e964b0b3fb699a129e0b86a3beb93337f83ac144 · inspected 2 November 2026 UTC · machine-readable evidence

What to do first

Start with A and B: stable consumers depend on experimental package locations. Then batch the independently reviewable unused wrappers (C–F) after confirming consumers. G–I simplify concrete indirection and names; J–L need design and coverage work.

Absence of an in-repository label is a lead, not proof of dead code. Macro-created edges, direct CLI invocations, non-Bazel consumers, generated labels and downstream workspaces can all matter. No data, migration, schema, test or lint coverage is proposed for deletion merely because a wrapper appears unused.

Method and limits

  • Inspected a clean checkout of the exact commit above, repository BUILD/Starlark conventions, CI target selection, and tracked references including hidden workflow files. The user’s working tree was not modified.
  • A successful remote Bazel query listed evaluated filegroup rules across //.... A source inventory also parsed literal top-level BUILD declarations; macros, selects, generated rules, load-time expressions and non-Bazel callers require additional review.
  • A repository-wide depth-one reverse-dependency query confirmed that the eight wrapper targets in C–F and M have no incoming rule edges in this evaluated workspace. The query also confirms ten generated visual tests consume each Agentplane visual bundle wrapper. External callers remain outside the query. //... includes top-level checks and tools with no incoming dependency, so zero reverse edges alone never proves a target is dead.
  • Do not remove visual harness filegroups just because their labels are absent from BUILD files: agentplane_visual_test references them in its Starlark macro. Likewise, whole-program lint source groups are active inputs, and generated output groups or single-file views can be needed for $(rootpath).
  • These are selected high-signal cases, not an exhaustive proof that all other targets are correct. Priorities express review value and expected blast radius, not measured build-time savings. No code change, build or behavior test was performed for a proposed refactor.
