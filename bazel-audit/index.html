What to do first

Start with A and B: stable consumers depend on experimental package locations. Review the remaining unused-wrapper candidates D, F, and M after confirming their consumers. J, K, and L need design and coverage work.

Absence of an in-repository label is a lead, not proof of dead code. Macro-created edges, direct CLI invocations, non-Bazel consumers, generated labels and downstream workspaces can all matter. No data, migration, schema, test or lint coverage is proposed for deletion merely because a wrapper appears unused.

AHighOwnership

Move Augur’s deployed model contracts out of x/

The production API configuration imports provider configuration and models from finance/augur/x/models, and the calibration layer imports a private-equity model there. finance/augur/api/config.py:32 finance/augur/api/BUILD.bazel:67 finance/augur/calibration/BUILD.bazel:94. The repository describes x/ as experimental, with no stable API.

Refactor: Decide which model/config modules constitute the supported deployment contract and graduate that coherent slice to an owned package; move imports, BUILD labels, fixtures and deployment configuration together. Keep genuinely experimental models under x/.

Verify: Build affected libraries and images and exercise real configured provider startup; a path move must preserve config and stored-data compatibility.

BHighOwnership

Decouple Haku’s schema build from an experimental service implementation

//haku/console/mcp:export_tool_schemas imports Gmail and Calendar implementations under //x/google_mcp_server; the generated catalogs feed the Haku frontend. haku/console/mcp/BUILD.bazel:7 haku/console/mcp/export_tool_schemas.py:13 haku/console/mcp/BUILD.bazel:30. This is build-time schema coupling; it does not mean Haku runs those servers in-process.

Refactor: Choose a stable owner for the server contracts: graduate the Google service or extract producer-owned schema/model targets consumed by both server and exporter. Preserve generation from authoritative tool definitions; do not replace it with a copied schema roster.

Verify: Regenerate both catalogs and validate the frontend renderers and producer contract together.

JMediumLint wiring

Untangle checker-only provider dependencies from runtime libraries

Five skills/eval_infra libraries each declare Anthropic, Claude and OpenAI provider packages with comments saying that the core stub’s imports require them for mypy. skills/eval_infra/BUILD.bazel:31. Similar entries appear in the Haku agent-framework package. haku/runtime/x/agent_framework/BUILD.bazel:20. These are real checker inputs today; deleting them can break type checking and may alter runtime closures.

Refactor: Investigate the pinned agent-framework stub/import graph and whether its distribution can expose correct optional typing dependencies. Prefer an upstream or narrowly scoped stub/typing fix so each production target declares actual runtime dependencies. Measure package and image closure before choosing a repository-level abstraction.

Verify: Reproduce mypy failure without these deps, verify all affected targets under default lint, and compare runtime/image closures. No removal is justified until that test passes.

KMediumLint wiring

Make whole-program ESLint inputs auditable across package boundaries

Agentplane enumerates 11 child source groups and separately lists generated declarations and npm inputs for the type-aware ESLint program. agentplane/app/frontend/BUILD.bazel:26 agentplane/app/frontend/BUILD.bazel:52. The lint macro needs source files at original paths and uses no_copy_to_bin; it is a real lint check, not a disposable target. devinfra/js/typed_eslint.bzl:16.

Refactor: Investigate generating or validating the source/declaration closure from a single authoritative frontend package registration, including newly added Bazel subpackages. Preserve source paths, generated declarations, and the distinct whole-program analysis; avoid introducing a second unchecked roster.

Verify: Add a focused coverage check that fails for an omitted nested source package and run the typed ESLint target.

util/testing/frontend_visual.py lives alongside a frontend_visual/ Bazel package. Refactor: Consider moving the Python module and its assets into a coherently named non-colliding package, or rename one side; update Python imports, Bazel labels, runfile lookups and visual macros together. Treat this as an ownership cleanup with a broad blast radius, not a reason to delete asset wiring.

Verify: Run representative visual tests on RBE and verify screenshots and browser asset resolution.

Method and limits

  • Inspected a clean checkout of the exact commit above, repository BUILD/Starlark conventions, CI target selection, and tracked references including hidden workflow files. The user’s working tree was not modified.
  • A successful remote Bazel query listed evaluated filegroup rules across //.... A source inventory also parsed literal top-level BUILD declarations; macros, selects, generated rules, load-time expressions and non-Bazel callers require additional review.
  • A repository-wide depth-one reverse-dependency query found no incoming rule edges for the remaining wrapper candidates D, F and M in the audited snapshot. The query also confirms ten generated visual tests consume each Agentplane visual bundle wrapper. External callers remain outside the query. //... includes top-level checks and tools with no incoming dependency, so zero reverse edges alone never proves a target is dead.
  • Do not remove visual harness filegroups just because their labels are absent from BUILD files: agentplane_visual_test references them in its Starlark macro. Likewise, whole-program lint source groups are active inputs, and generated output groups or single-file views can be needed for $(rootpath).
  • These are selected high-signal cases, not an exhaustive proof that all other targets are correct. Priorities express review value and expected blast radius, not measured build-time savings. The remaining recommendations have not been implemented or validated by this audit.
