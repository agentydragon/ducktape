Zero retries has an observed recovery tradeoff

Five remote-execution failures occurred among 58 verified zero-retry attempts (8.6%). Three were Firecracker VM pause socket refusals; one was an executor OOM; one was transport EOF with a server-shutdown GOAWAY. All five surfaced as remote UNAVAILABLE. Four later workflow attempts succeeded on the identical tested source, still using zero retries; the OOM rerun was canceled.

This is an observed failure cost alongside the intended cancellation mitigation. It does not prove five avoidable failures or that default retries would have recovered them automatically. Pinned Bazel 9.2 retry classifier treats UNAVAILABLE as transient; zero removes that opportunity. The five default-policy attempts are not a matched control. No production policy is changed by this report.

Do not make blanket zero retries permanent on the strength of the cancellation probe alone. The recovery tradeoff is now observed; realized canceled-work savings are still unquantified. Keep the policy decision separate from the three cleanup-failed attempts (two remote executions) and four source/test failures.

Sources, clocks and limits

The collection recursively split all-workflow run queries below GitHub’s 1,000-result cap: 2,279 distinct runs, with all attempts’ job detail for 975 core runs / 2,618 jobs. Core scope is CI, trusted-fork CI, pre-commit and artifact workflows. No all-workflow runner-occupancy or account-capacity census was collected. Run membership uses creation time; job outcomes were read during the later sweep. Attempts and distinct heads are separate units.

Assigned-completed duration statistics require a positive runner ID and valid ordered timestamps. Cancellations are excluded from success/failure denominators and retained in outcome tables. Percentiles use nearest rank; GitHub timestamps resolve one second. The two temporal bins have different workloads and source histories. Effective policy is established from actual Bazel options, rather than assigned by creation time.

Same-repository PR feedback is a latest-head survivor proxy: earliest matching core workflow creation to completion of the latest successful native jobs for all three required contexts. It is not push-to-green or full auto-merge readiness. Fork heads are excluded from that linkage because their workflow head metadata can name the base. Changed-path classes use exact head/event-base comparisons where available; unknowns remain explicit.

Live rules still require bazel-ci / Test & Build, Pre-commit checks and Build artifacts + imports check, with zero required approvals and no strict up-to-date/thread-resolution requirement. Drafts, conflicts and extra approval for unattributed changes can still block merge. The legacy branch-protection endpoint returned 404; the active branch-rules endpoint supplies these requirements.

Remote queue, process/worker time, CPU, artifact overlap and required-check wall time are different units. Shared/cached executions and synthetic cancellation timestamps cannot prove physical worker shutdown or reclaimed compute. Agent-visible API availability, webhook/inbox/harness receipt and full-policy readiness remain unmeasured. Raw logs, profiles, worker identities and credentials stay local; public evidence contains reviewed aggregates, source/action links and artifact hashes.
