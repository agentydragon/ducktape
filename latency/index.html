1. API-only fixture image

Add an API-only image binary/layers beside agentplane/app/BUILD.bazel without frontend:bundle or service_worker_js; point only the API-only k3s fixture at it. Production retains the full image. Query f7a6c3e7 proves 14 reverse-dependent tests before manual filtering; current CI runs 11. agentplane/app/main.py gates asset reads on Electric, which the fixture omits. This cuts execution triggers as well as bytes.

Impact model: Forecast conditional on a production-bundle-only edit that currently invalidates k3s: retain roughly 2–5 minutes of browser/component work instead of also waiting for a 4–7 minute cluster tail. Range 120–360s; plausible lower bound zero. The pure frontend harness example selects no k3s already; that is a counterexample to treating all UI edits alike.

Acceptance and falsification: Replay a production SPA edit through bazel-diff before/after; verify all 11 fixture TestRunner input digests stay equal while frontend checks change. Run API-only lifecycle and full-image browser coverage. Falsified if a remaining real dependency still changes the fixture image or its manifests.

2. Deterministic, feature-scoped fixture rendering

Move database, app/OIDC, bcrypt and MCP credential generation into per-action runtime inputs/placeholders; split the five-output render rule by backend/MCP/VM feature. The current shared rule emits random fields into every variant. New RBE experiment 82a877b1 found 17/22/17 differing paths for identical base/MCP/VM inputs; controlled outputs matched completely.

Impact model: Forecast 60–300s on an edit that reruns the renderer but leaves a consumed variant semantically unchanged; potentially up to the whole 434s cluster critical path, less retained gates. It saves zero on changes to the actual service config/images. Current population frequency is unmeasured; determinism is not a promise that all chart changes become cache hits.

Acceptance and falsification: Implement real placeholders with correct shared references and per-stack secrets; do not ship fixed test credentials. Render each variant twice in separate processes, change MCP-only config, and prove base/VM digests and unaffected test verdicts reuse. The experiment controlled randomness at the test boundary; production placeholder code remains to implement.

3. Separate image bytecode and consumed layers

Split whole-image compileall into runtime, dependency and app-source bytecode; keep static assets out. Emit only consumed image layers, or hide implementation-only roots from broad selection. The shared-layer helper still creates discarded per-binary interpreter archives and an umbrella that roots them. A real query verified these targets; nine call sites exist.

Impact model: One current mixed frontend case has 78.39s in app_bytecode, 33.99s in the package tar and 18.68s in its descriptor on the reported dependency chain. Forecast 30–90s for app/static invalidations by reusing stable bytecode/package outputs; cold all-input builds may save nothing. Up to nine duplicate interpreter tars disappear from a cold full sweep, but their elapsed savings were not measured. Do not add these upper bounds together.

Acceptance and falsification: Compare a UI-only and one-file Python edit using aquery/profile and image digests. Verify hash-mode .pyc, co_filename, exact interpreter version, ownership and startup. All public image targets must still build their consumed layers transitively; do not mark public coverage manual.

Acceptance and falsification: Replay util → git-hooks/ducktape and claude-api → aiquota → statusline, ZIP-only changes and missing outputs. Preserve source-built overrides for all selected consumers and both assets of multiasset releases. Compare final required-gate time, not just the Nix job.

5. Make superseded remote builds actually quiesce

The current signal/child-ID fix is present and its explicit cancellation RPC succeeds, yet three sampled cancelled jobs still submit their own new actions afterward. Extend the cancellation lifecycle to stop the originating outer/inner build and verify no new work appears; use a bounded cleanup supervisor if GitHub’s signal grace is insufficient. Do not simply repeat the landed trap change.

Impact model: Observed own-action tails end 211–267s after GitHub cancellation. The post-cancel action-wall intervals sum to 2,113 / 257 / 943 seconds in those three samples; these overlap and are not CPU or feedback time. NEW identifies originating work, but later consumers may share it, so not all continuation is avoidable waste. It is not extra GitHub occupancy. Forecast 0–30s of burst feedback benefit only if freed resources matter; direct RBE queues are usually subsecond. Exact avoidable worker-seconds and server visibility limits are in the follow-up evidence.

Acceptance and falsification: Reproduce cancellation while an inner build is actively submitting actions, inspect outer and child IDs, and prove no NEW executions start after the stop deadline while a replacement passes. An HTTP-success CancelExecutions response is insufficient. Hosted service semantics/acknowledgment are an explicit external boundary; no production cancellation change was tested.

6. Clone an immutable unpacked image seed into fresh actions

Prototype a digest-keyed, trusted seed of pinned containerd content/snapshots; clone it copy-on-write into each fresh RBE action, then import changed service layers. Preserve fresh cluster/database/identity state. Current importer streams deduplicated OCI blobs per image but still repeats unpack filesystem work in each action.

Impact model: Latest observed Pod imports are about 71–110s and the VM’s image imports about 207s; the older three-run model-free profile was 34–89s. Forecast 30–100s end-to-end on cold affected stacks after seed clone/check cost. This is a sizing estimate, not a measured speedup. A plain prebuilt tar avoids framing but leaves unpack, and a warm verdict already saves the entire action.

Acceptance and falsification: Start with immutable PostgreSQL/operator/harness layers on one fixed source. Key kernel/containerd/k3s/snapshotter/features and layer digests, validate GC roots/leases, and exclude PR code, credentials and mutable Kubernetes state from the seed. Compare clone+import+first usable Session, cold and warm. Stop if transfer/unpack cost merely moves or platform support is unavailable.

Impact model: Current example: VM process 432s versus next Pod process 285s. Even eliminating the VM action entirely saves at most about 148s of that inner finish path. Most of its pre-case time is imports/readiness: stack Ready at 276s from fixture start. Forecast 40–140s for a combined better I/O/guest-acceleration result, with zero plausible if provisioning/queue costs cancel gains. KVM alone cannot remove image import.

Acceptance and falsification: Hold images and scenario/case set constant; measure pool queue, input fetch, node/import/Ready, first turn and total action. Preserve KubeVirt, Kyverno relay, PVC/image-volume and identity coverage. Keep one emulation compatibility path if needed. More memory alone does not establish faster CPU or disk.

14. Group compatible scenarios into a few isolated stacks

Prototype 2–4 cacheable Pod scenario groups with a stack per action, preserving PR isolation; keep destructive storage/lifecycle and VM separate. Current ten Pod actions each start/import a full stack. This differs from one shared multi-PR cluster, which is not recommended.

Impact model: Ten → three stacks avoids seven setups. At current Pod startup/import magnitudes, about 300–700 worker-seconds is a plausible setup saving, not a wall-clock sum. Forecast 0–60s gate saving; a longer serial group can instead regress latency. It is secondary to smaller dependency closures because grouping broadens invalidation and rerun scope.

Acceptance and falsification: Compare a single-scenario edit and a broad service edit; preserve all harness/case variants, explicit unique ownership and cleanup. Reject if the slowest group is later than the baseline or cache misses cost more than setup reuse.

Reject if net required-gate time or occupied runner time worsens. Combining Nix commands previously saved no useful evaluation time and is not revived here.

What the heavier tests really cost

Current source: ten Pod scenarios plus one VM scenario run automatically when selected and are verdict-cacheable. Each action starts a fresh k3s/containerd, imports its fixture and runs real Pods/services. The standalone model-free lifecycle workflow is still manual; it is not the new PR cost. Three additional VM scenarios are now manual, although historical migration runs in this window executed all four VM variants.

Real cluster, deliberately reduced platform

Pinned k3s, kubelet, kube-proxy, flannel host-gw, CoreDNS, local-path PVCs, ImageVolume, real TokenReview/controllers, one PostgreSQL 18 Deployment with service-owned DBs, and Go control-plane services. The app/API and current-source Python Actions remain. No Electric/browser, Cilium, CNPG operator, Gateway API, cert-manager, ESO or monitoring stack. MCP adds Dex and two MCP fixtures; VM adds KubeVirt/Kyverno and a small guest.

Each action requests four estimated compute units and 50GB disk, bridge networking, recycle-runner=false. Pod overlay snapshots are tmpfs; content stays on disk. VM snapshots stay on disk. Outer BuildBuddy runner recycling is separate and already enabled.

The expensive path is inside the action

OCI layouts → per-image tar streams with distinct blobs sent once → containerd content store and unpack → manifests → Deployments Ready → scenario. No Docker-load tarball or external runtime image pull is required for supplied layouts. Current --no-unpack would only skip import unpack; first use still needs usable snapshots. The upstream import implementation supports that distinction.

Historical native CPU profile found filesystem apply/writes dominant, not Python tar CPU. An input closure of 6.06GB is not 6.06GB downloaded on each run: current measured input fetch is usually subsecond to a few seconds. Benefit comes from fewer invalidations, build prerequisites and unpack writes, not an invented bytes/bandwidth conversion.

Which larger changes are worth considering?

Prefer immutable image seeds to shared multi-PR clusters

A persistent multi-PR cluster removes startup on paper but namespaces do not isolate CRDs, cluster RBAC/controllers, node/host mounts, storage provisioners or arbitrary PR code. It adds state pollution, credential exposure, noisy-neighbor behavior and dishonest action-cache inputs. Fresh per-action clones of trusted immutable content preserve the existing isolation boundary. A fully booted k3s snapshot has more potential but must regenerate certs/identity/network/leases, recover databases and handle clocks. Start with content/snapshot seeds and prove BuildBuddy support first; BuildBuddy documents outer-runner snapshotting, which does not itself prove an inner k3s seed is supported.

Choose tiers by the behavior they exercise

Use real API-server/etcd envtest for admission, watches, RBAC/TokenReview and reconcilers that need no Pods. Keep k3s for kubelet/CNI/DNS/image volumes/PVCs/sidecars and real Sandbox paths; keep KubeVirt/Kyverno for VM paths. DCR registration is the clean component candidate. Do not replace lifecycle/storage/streaming end-to-end coverage just to remove a costly test. A bundled control-plane Pod can reduce Pod scheduling/probe overhead, but still imports the same binaries and must preserve distinct service credentials; one union ServiceAccount would change the security contract.

Actions Go first; app/BFF deletion is a separate decision

agentplane/plans/action_service_go_port.md has most Go implementation stages landed and caller/testing/staging/Python retirement still in flight at the pinned source. The fixture still selects Python Actions there; newer in-flight heads are separately measured. The generated-facade track removes handwritten route/client/model mirrors but deliberately keeps app origin/login/CSRF/token exchange and app-owned composition/state.

The older October 21 model-free inventory is 938,776,320 distinct blob bytes (895.3MiB): 410.7MiB Python group, 313MiB Go services, 24.9MiB Goose, 68MiB runner/tools and 78.8MiB PostgreSQL. 382.1MiB is exclusive to the Python images, 42.7% of distinct stored bytes. Removing Actions alone cannot claim those bytes while app remains. Removing both requires replacement bytes and state/auth ownership; the plan’s 9–14% action saving is only a proportional model, not an empirical Go-port result.

Possible end states are: thin app BFF (least migration; retains Python), Go BFF (moves runtime but keeps the owner), or static browser plus service facades and explicit credential/state owners (largest change). App Thread names/archive state and browser sessions are user data, not disposable relay state. Removing a database from Dispatcher does not eliminate PostgreSQL from app, Actions, History, egress and Notifications. The fixture already omits the CNPG operator.

Alternatives with counterevidence or insufficient upside
  • ctr --local: previous paired means 230.3s vs 232.8s action, 79.4 vs 83.2s import; opposite worker directions. No useful speedup established.
  • Parallel VM/core imports: previously slower under I/O contention; no custom import scheduler recommended. Deployments already start concurrently, even though kubectl waits are printed serially.
  • --no-unpack: moves work to first use unless there is real snapshot reuse. Require first usable Session, not a shorter importer number.
  • Another generic Go rewrite: the earlier LLM ingress port did not establish lifecycle speedup. Measure exclusive bytes and selected CPU first.
  • Go stripping/compression or lazy/erofs/stargz images: experimental candidates after inspecting exact current link/debug modes and snapshotter/ImageVolume compatibility; no measured removable-byte result, so not counted as a quantified quick win.
  • All-in-one control-plane Pod: existing unscheduled spike; upper opportunity is part of the ~26–53s readiness phase, not all image bytes or all startup.
  • More GitHub slots: can address the observed 36s queue p90, not executing 4–7 minute cluster actions. More RBE capacity has little support from the inspected subsecond queues.

Limits that affect decisions

  • Outer remote request → test is measured, but VM queue vs boot vs setup is not fully exposed. Warm repo sync does not prove analysis-cache reuse.
  • Archived logs/profiles represent exact tested merge/source revisions; the inspected devel source is separately pinned. Actions/fixture transitions and VM-manual changes occur within this window.
  • 48-hour occupancy outside the core workflows is incomplete; other repositories, the account concurrency limit, and historical GitHub incidents were not censused. Completed occupancy is a lower bound.
  • Transient session DNS/TLS/API failures were bounded/retried and do not prove a CI service outage. Exact invocation HTTPS access recovered; two real query checks and the renderer experiment ran on RBE.
  • All forecast ranges are conditional and overlapping. No current optimization was rolled out, no population before/after speedup measured, and no raw logs, profiles, credentials, identities or inbox contents are published.
