  1. Use the current VM chain as the next gate. The three scheduling/parsing changes are merged. The earlier complete sweep did not establish a repeated overall gain; current warm VM evidence still includes substantial environment readiness, real harness work and cleanup.
  2. Follow the executor boundary before changing Python dependencies. The full profile locates about 18 s of inclusive import work. Follow the outer VM workspace boundary

The inspected BuildBuddy implementation stamps execution start before the runner's Run call. Initial Firecracker creation or snapshot restore, plus ext4 workspace preparation and guest command setup, can occur inside that interval. A paused runner taken from its in-memory pool restores earlier. Both observed warm actions report task number 1 and prior snapshot metadata, supporting the initial-runner restore path under the inspected code. The hosted server revision is unknown, so this is source-grounded attribution of possible work, not a per-stage latency measurement.

The exact mainline Action and Command omit enable-vfs; the inspected parser defaults it to false. Enabling VFS is not an equivalent persistence experiment: Firecracker plus FUSE is marked non-recyclable, and it changes snapshot compatibility. Keep this alternative's tradeoff explicit rather than crediting avoided workspace copying while assuming the current retained K3s stack. The next discriminating evidence is the exact executor trace for Create/LoadSnapshot, ext4 workspace build/attach/mount and guest Exec; those hosted spans are not exposed by the collected execution API response. The response's vmexec dial metrics cover only 9.48 s in the first profile and 0.012 s in the repeat.

The fresh mainline scenario chain is already concurrent. Claude's 203.3 s lane includes 123.2 s waiting for environment readiness, 19.7 s opening the session, 36.2 s for its turn, and 22.3 s of Sandbox cleanup. The OOM lane finishes about four seconds earlier, so improving Claude alone soon exposes another gate. Removing all 51.6 s before the first span would be only 14% of this VM action, before accounting for other CI targets. Reaching 25–50% requires another independent reduction in the shared boot or setup path while retaining fresh guests, OOM recovery, supervision and journal/shutdown proofs.

The current readiness wait is also supported by producer records: approximately 23 s to Pod scheduling, 43 s to workload readiness, 47 s to guest kernel output, 85 s to prepared workspace, 112 s to the supervision pass marker and 123 s to runner-connected. These offsets cross console and condition emitters and are approximate. The readiness predicate requires a live Gateway Lease for the current Pod and runtime boot identity; it is not just a subscription lifetime. The raw first-state/Lease timestamp is missing, so the final roughly 11 s after supervision cannot be claimed as removable polling time.

The merged-source failure was at shutdown

This full sweep ran all three VM scenarios successfully. Claude's runtime stopped, its workspace unmounted, then journal-flush did not finish. QEMU was terminated at the 30 s grace boundary, without state-unmount or the required shutdown receipt. The copied journal verifies structurally.

We lack the stalled process stack. Guest journal-flush, virtiofs and the host daemon remain possible causes; there is no proof this was caused by the root split. Suppressing the receipt or the journal would hide the failure.

Shared setup, cleanup and resource cost

The seven successful warm targets in the pilot already overlap image imports with installation and manifest work. Deployment controllers reconcile concurrently even when readiness watches are called in sequence; parallel watches would not remove the wait for the last actual readiness transition.

The critical VM target spent 71.49 s in setup and 37.61 s in cleanup. Fixture namespace deletion took 15.53 s, monitoring deletion 5.80 s and resource closure 7.61 s. Existing cleanup already batches fixture namespaces. The remaining safe overlap has an ideal bound of 5.80 s on that path, about 1.4% of the 419.11 s critical path, and requires additional delete/join error handling. No shared cleanup patch is proposed.

MCP Delegation had a 44 s namespace deletion in that pilot: the fixture received SIGTERM, exhausted its 30 s grace and was killed. That fixture-specific shutdown behavior is separate from the shared cleanup mechanism; no reduction is claimed without a validated repair.

All three combined VM runs were cold. Filtered baseline-transition logs show that each attached an older 2b3619f103… baseline while expecting 8e5387507b…; two old markers were clean and the third dirty. The fingerprint fence correctly rebuilt infrastructure. Why those older snapshots were selected is unmeasured: concurrent old/new source versions sharing the pin-derived family is a plausible explanation, not a proven provider defect. Why 16 outer compute units are not being promoted

A small RBE capacity probe with the same isolation/resource settings exposed 11 CPUs/about 20 GB at eight requested units and 19 CPUs/about 40 GB at 16 units. Neither showed in-VM cgroup throttling. The full VM control averaged 3.6–4.3 CPUs and peaked below 8 GB in selected runs, which does not prove an eight-CPU bottleneck. Host-side burst scheduling remains unknown.

The probe did not run QEMU. Moving to 16 units doubles the requested CPU/memory reservation and changes the snapshot family. There is no measured runtime benefit to offset those costs. BuildBuddy's resource-unit documentation describes each compute unit as one CPU and 2.5 GB; guest-visible CPUs are a separate observation.

The ten-target pilot covered seven k3s suites, both bridge shards, 16 browser shards and window-browser: 26 physical test executions. All seven k3s suites, both bridge shards and 16 browser shards passed, while window-browser exceeded its 300 s deadline after five of six items.
