Why cache propagation remains disabled

January's symlink merger and external-dependency fork experiments were followed by cache=False after disk exhaustion (31a5df2327). #6817 later adopted the upstream runner while retaining that setting. Bazel's whole-action cache remains enabled; the disabled feature is propagation of mypy's internal cache between actions.

The current experiment produced 16 SQLite shards plus three support files, about 16.6–18.9MB per baseline action. The upstream merger keeps the first file with a given name, which cannot merge the entries of identically named SQLite shards from different dependencies. Open ZIP-delta PR #138 also excludes inherited filenames even when subsequently modified. Deterministic archive headers do not normalize embedded mypy timestamps. These are cache-reuse and design concerns; no false-green cache defect was demonstrated.

Remaining candidates that preserve the aspect

  • Narrow irrelevant action inputs. The indexing mypy graph includes runtime templates such as agent_instructions.j2. Upstream PR #141 addresses excess inputs. Any adaptation must preserve py.typed, stubs, configuration/plugin inputs and the checker's runtime dependencies. This would avoid unnecessary invalidation; savings are unmeasured.
  • Avoid discarded cache writes. Using /dev/null when cache propagation is disabled reduced the four individual checks' CPU totals by approximately 3% and 10% in the two pairs. Batch timings did not consistently improve. This can preserve the aspect interface; an unprofiled comparison is needed before claiming a small performance improvement.
  • Keep cache reuse as a separate investigation. Re-enabling cache=True, hardlinking whole files or applying the ZIP proposal unchanged is not supported by this evidence. Logical cache-entry merging, changed-entry export and dependency/options/plugin invalidation need validation against the current format.

Remote continuation: historical diagnosis (advanced by #9873 above)

The landed #9369 grouping fix is working for hosted slots: all 40 sampled superseded Bazel jobs cancelled, median 16s / p90 17s after the newer workflow was created (max 22s). But three sampled inner builds finished 18s, 132s and 340s after GitHub cancellation. The latter two executed 3,920 and 4,499 worker-process seconds after the GitHub job ended (132s continuation; 340s continuation).

These are remote-resource costs, not additional occupied GitHub minutes. Saved net compute could be smaller if obsolete execution warms useful cache entries. A cancellation adapter must preserve interruption handling and correctly address the outer execution plus descendants; validate both remote termination and a healthy replacement run. Do not equate a cancelled GitHub check with terminated remote work.

The pinned CLI 5.0.466 registers SIGINT/SIGTERM and calls CancelExecutions while its invocation-running guard is set. After log EOF it clears that guard and waits for completion; a signal in this later phase does not call the remote cancel. The composite uses a bb remote | tee pipeline without a forwarding trap. Neither fact identifies the historical cause: signal delivery, phase and RPC outcome were not recorded. Pinned cancellation implementation.

Bounded probe: inconclusive. A new isolated 60-second remote sleep completed normally at 22:06:49 UTC. The local tee exposed its start marker only after its end marker; SIGTERM at 22:06:59 hit the CLI after remote cleanup. This did not exercise live remote cancellation. All probe processes exited. The smallest valid follow-up must use API-confirmed live step state to time the signal, and then verify descendants terminate. That inconclusive probe selected no production change; the later API-timed probes above support merged #9873.

Evidence, clocks and remaining limits

Agent-visible feedback is only partly observable

For one follow-up job, GitHub reports start at 21:53:27 UTC and completion at 21:55:42. A query at 21:54:11 observed it running; the job-log endpoint returned 404 at 21:54:12. At 21:58:35 it was terminal, and the job log and BuildBuddy critical-path log were accessible by 21:58:40. A transient TLS handshake timeout interrupted the planned 20s polling. These are coarse bounds, not a measured 3-minute delivery delay.

Queryable terminal result and accessible diagnostics: n=1, first-access time interval-censored. Notification webhook acceptance/delivery, subscription inbox read and agent harness receipt: n=0. GitHub completion timestamps and buffered console lines cannot substitute for those clocks.

Reproducibility and data handling

  • GitHub Actions run queries were split into subwindows below the 1,000-result cap; paginated jobs include all attempts. Three skill-collector snapshots were analyzed with the packaged evidence recipes. Sweep start/end timestamps are in evidence; this is not an atomic snapshot.
  • GitHub carried forward six completed jobs into rerun metadata with new IDs/creation times but the same runner, start and end. Deduplication by run/name/runner/start/end removes double occupancy and negative synthetic queues. No negative queue was silently clamped to zero.
  • Profiles, critical paths, execution metadata, job logs, exact-head checks and current rules were reviewed. Small summaries are published; raw logs, credentials and API payloads remain local. Source and tested merge revisions are distinct.
  • No controlled population-wide before/after result, push-to-ready clock, notification delivery distribution, complete 24-hour occupancy, or cross-repository capacity attribution is available. The results identify concrete waste and critical paths without claiming those missing measurements.
