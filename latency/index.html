What changes the decision

  1. Prioritize the long tail inside the Pod batch. Storage still runs exclusively first; idle/resume then starts first among concurrent cases. The number of slots, cases and resource reservations stay fixed.
  2. Keep bounded MCP case concurrency on one stack. The three independent cases get separate resources and names. OAuth cases remain sequential on the same deployment, preserving the stateful coverage that the earlier three-stack split lost.

VM boot and teardown: the evidence boundary

The merged-source failure was at shutdown

This full sweep ran all three VM scenarios successfully. Claude's runtime stopped, its workspace unmounted, then journal-flush did not finish. QEMU was terminated at the 30 s grace boundary, without state-unmount or the required shutdown receipt. The copied journal verifies structurally.

We lack the stalled process stack. Guest journal-flush, virtiofs and the host daemon remain possible causes; there is no proof this was caused by the root split. Suppressing the receipt or the journal would hide the failure.

Boot has substantial real work

In that run, workload readiness preceded runtime connection by 48–65 s across the guests. The OOM guest's own monotonic boot evidence reached userspace at 9.3 s, udev at 22.9 s, workspace mount at 30.3 s and Runtime active at 37.0 s. These guest timestamps are not directly subtractable from host UTC.

A fresh pinned-source control passed in 603 s, but its broad slowdown and cold 51.9 s guest-root import make it unsuitable as a matched before/after result. Driver-observed readiness was 154–180 s. No safely removable polling interval was established.

Before the first traced manifest load, the combined controls expose another blind interval: 77 s in control and 51 s in candidate after physical action start. That 25.7 s change is much larger than the 4.9 s parser difference. The prior plain collect-only probe took 28.1 s, and Python importtime measured 9.65 s of import self time; those earlier probes do not explain the full gap. REAPI and OTel timestamps come from different clock emitters, with no offset bound captured. Profile the action launcher, Python startup, collection and pre-span fixture-input loading before calling this import cost or crediting it to the new patches. The next probe should start stdlib cProfile before importing test_vm, preserve the full suite and save pstats to undeclared outputs; measure any launcher residual separately.

No VM runtime patch is proposed from this lane. KVM remains outside this session's options. Obtain a blocked task/virtiofs stack on recurrence and optimize a demonstrated operation, while retaining the native lifecycle proofs.

Shared setup, cleanup and resource cost

The seven successful warm targets in the pilot already overlap image imports with installation and manifest work. Deployment controllers reconcile concurrently even when readiness watches are called in sequence; parallel watches would not remove the wait for the last actual readiness transition.

The critical VM target spent 71.49 s in setup and 37.61 s in cleanup. Fixture namespace deletion took 15.53 s, monitoring deletion 5.80 s and resource closure 7.61 s. Existing cleanup already batches fixture namespaces. The remaining safe overlap has an ideal bound of 5.80 s on that path, about 1.4% of the 419.11 s critical path, and requires additional delete/join error handling. No shared cleanup patch is proposed.

MCP Delegation had a 44 s namespace deletion in that pilot: the fixture received SIGTERM, exhausted its 30 s grace and was killed. That fixture-specific shutdown behavior is separate from the shared cleanup mechanism; no reduction is claimed without a validated repair.

All three combined VM runs were cold. Filtered baseline-transition logs show that each attached an older 2b3619f103… baseline while expecting 8e5387507b…; two old markers were clean and the third dirty. The fingerprint fence correctly rebuilt infrastructure. Why those older snapshots were selected is unmeasured: concurrent old/new source versions sharing the pin-derived family is a plausible explanation, not a proven provider defect. Why 16 outer compute units are not being promoted

A small RBE capacity probe with the same isolation/resource settings exposed 11 CPUs/about 20 GB at eight requested units and 19 CPUs/about 40 GB at 16 units. Neither showed in-VM cgroup throttling. The full VM control averaged 3.6–4.3 CPUs and peaked below 8 GB in selected runs, which does not prove an eight-CPU bottleneck. Host-side burst scheduling remains unknown.

The probe did not run QEMU. Moving to 16 units doubles the requested CPU/memory reservation and changes the snapshot family. There is no measured runtime benefit to offset those costs. BuildBuddy's resource-unit documentation describes each compute unit as one CPU and 2.5 GB; guest-visible CPUs are a separate observation.

The near-full pilot failed; it is not a passing whole-gate benchmark

The ten-target pilot covered seven k3s suites, both bridge shards, 16 browser shards and window-browser: 26 physical test executions. All seven k3s suites, both bridge shards and 16 browser shards passed, while window-browser exceeded its 300 s deadline after five of six items. Its first browser context started around 145 s into the action, after a 41 s Postgres image load; the fifth item was still progressing near the deadline. How to read and reproduce this snapshot

  • Source: inspected devel 3d60fc34d66c284d55dfe89eb78858ebc8aeeb87. The source prototypes have their own commits/PR heads; effective local trees and patches are recorded separately from BuildBuddy's checkout metadata.
  • Mainline context: CI/devel literal //... invocations created since 19:55 UTC and returned by an update-time-bounded API query through 21:54 UTC. Non-atomic capture: 17 completed, onepartial. This is not a complete moving census of every possible recently updated run.
  • Controlled execution: normal --config=ci and remote action-cache acceptance,--nocache_test_results. Fresh test execution does not imply a cold retained stack. Cold imports, warm receipts, physical retries and failures are accounted separately.
  • Durations: critical-path wall time, worker occupancy, CPU, memory and aggregate transfer durations are different quantities. Per-file download-duration sums are not an input-fetch wall phase. Overlapping spans are not added into a false critical path.
  • Coverage: all original cases, fresh app/database/certificate/workspace boundaries, both harnesses, native supervision, OOM recovery and teardown evidence stay required. No live PostgreSQL persistence or scanning-policy change is included.
  • Evidence: selected measurements and source/window manifest. Raw logs, full API payloads and process identities stay out of the publication.

Decision threshold: a target-level win earns a narrow source PR; it is not promoted to a 25–50% complete-CI saving without matched full-path evidence. VM, Pod and dispatcher can exchange the final position as cache/source/worker conditions change.
