2. Cancellation competes for the same GitHub runner capacity

Ordinary PR CI admits each run independently. A separate trusted workflow_run controller cancels old heads, but it also needs an ubuntu-latest runner. Its assigned jobs take about 14 seconds; its observed assignment waits are median 63m16s / p90 70m20s (15 assigned jobs). Fifty-eight controller jobs were still queued in the earlier incident extraction. This is admission/cancellation feedback, not slow cancellation code.

Twenty-four completed Bazel jobs used 368.35 runner-minutes after a newer distinct head's CI run existed, within 03:00–04:35. That is equivalent to 3.88 continuously occupied runner slots over this window. This is a measured opportunity bound, not the effect of a deployed cancellation fix: cancellation takes time and teardown must release downstream actions. Still-running jobs are excluded, as are intervals outside the window.

A multi-second live sample found 18 assigned current jobs, dominated by Bazel and image builds, while ready independent jobs queued. Public documentation gives standard limits by plan, but this account's authenticated API returned plan: null. Its effective account cap is not established; neither a guessed 20-slot plan nor an unobserved BuildBuddy org quota is needed to establish the KVM saturation and long GitHub assignment waits. Eleven other recently pushed owner repositories had no recently created in-progress workflows in the bounded check.

What is established, and the remaining visibility boundary

  • Exact capacity: one registered self-hosted KVM worker, one task slot and a growing local queue are directly observed. Hosted BuildBuddy fleet size, org CPU quota and GitHub account allowance remain unexposed.
  • Current slot occupant: its identity and internal wait were not available from the accessible execution records. Automatic approval review rejected an interactive root/autologin console as too broad for read-only diagnosis. Read-only journal/container/process commands were proposed; no approval was received and no console connection was opened. No worker restart or cancellation was attempted.
  • Failure amplification: existing 59,005 service spans, driver spans and failed-case logs establish repeated turn deadlines and HTTP 502s. They do not expose the underlying LLM reverse-proxy transport error. Preserve the server’s warning/error fields in the failed test outputs or collect that producer log on the same input; do not declare a provider outage or a SVID root cause from these status codes.
  • Feedback availability: GitHub statuses supply creation clocks, not first queryability or delivery. Running GitHub job log retrieval returned 404 while BuildBuddy logs were accessible. No webhook acceptance, inbox delivery, agent-read or harness receipt timestamps were available. No agent delivery percentile is claimed.

Job pages use filter=all and checked totals; active records and open-head checks are separate non-atomic observations. No live epoch clocks become zero-duration measurements.
  • Scope: this incident displaces lower-priority optimization experiments. Ordinary successful actions still include useful test execution; no stress workload removal or coverage reduction is claimed. Raw API payloads, logs, profiles, process identities and model request bodies remain local.

The reuse model: stable services, fresh workloads, verified release

Use a versioned infrastructure recipe for compatible services and pinned images. Check actual identity, configuration, health and cleanliness at attach. Build current application inputs and fresh databases/certificates/mock state. Release a clean environment only after all owned mutable resources are gone; rebuild owned dirty or incompatible state cold.

  1. Family: recipe version + infrastructure pins/configuration; avoid a new family for every application edit. Effective platform/resource/VM settings still affect matching.
  2. Attach: prove ownership and health; mark leased/dirty before handing it out. A restored process may be dead or have stale connections.
  3. Test: current code and isolated state. Migration-from-empty, restart, supervision and recovery scenarios retain their fresh-start coverage.
  4. Release: stop clients, remove owned databases/roles/slots/credentials, then atomically mark clean. Failed cleanup prevents reuse.

This selector explains designs; it does not change repository or executor settings.

Local fixtures should call the same setup/reset/cleanup code with retention off by default and fixture-owned temporary state. BuildBuddy permission and invalidation belong in an adapter. Current Docker/browser tests still run on RBE; local-host validation and any policy change are separate. Self-hosted OCI/Docker can retain a paused container on one executor; Firecracker snapshotting needs additional host capabilities and executor configuration.

Prepare lazily; version layout changes; add a warmer only for a measured need

A normal cold test can prepare a family. Test setup boots or attaches, test teardown proves cleanliness, and BuildBuddy decides whether to save afterward. A service-layout or lifecycle change gets a new compatibility recipe version and all consumers change together.
