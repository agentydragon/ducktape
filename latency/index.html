What would move the needle

Fix the dependency graph, then the VM execution architecture.

  1. Separate the changing supervision fixture from the immutable guest root. The observed serial root path is 150–277s on affected heads. The passing prototype preserves the guest, native supervisor proof and all three scenarios; the paired input-change build below tests its marginal cost. Benefit applies when these inputs invalidate, not to every head.
  2. Run the existing VM suite on a KVM-capable RBE lane. Its three guests already boot concurrently. They spend 88–101s reaching actual Runtime/Gateway readiness under QEMU TCG. A matched hardware-backed run is the strongest next large experiment. Current hosted executors expose no /dev/kvm; a suitable pool needs provider support or separately provisioned executors. No speedup is yet measured for KVM.
  3. Use selective case distribution after the VM path improves; reject blanket three-way sharding. The new experiment ran all 14 Pod, three Dispatcher and five MCP test items, but used 1.6–2.4× selected worker cost and split an intentionally sequential OAuth pair. Its raw ~19% three-target improvement is not a normal full-CI effect. The cheaper idle-case reorder can save overlapping wait but is a small component.
No fleet-wide 25% or 50% win is established. The report separates proven dependency removal, measured probes, and conditional budgets. Optimizing only the last test would quickly expose another branch. Provider retries and GitHub queues are separate tails.

Process DAGs · guarantees behind the elapsed time

The dominant VM wait is real boot work. The long Pod wait is intentional.

VM: three genuinely concurrent guests

Current driver phases: 37.10s before first span, setup 75.36s, case 178.75s, diagnostics 2.85s and cleanup 28.16s, with 3.61s setup-to-case and 2.31s trailing work. Guest-root import is 38.22s inside setup. Cleanup’s baseline-clean child is 24.43s; it is not setup.

The three scenario spans overlap: Claude 177.85s, Codex OOM 173.89s, ordinary Codex 157.70s. Guest readiness takes 88.09–100.88s and includes the current Pod/boot-bound Gateway lease, not just Pod Ready. The native journal independently shows two vCPUs and a 14.85s private systemd supervision proof on one selected guest.

Pod: an idle contract stranded at the tail

The exclusive storage case takes 24.86s, followed by 13 cases under two slots. The case makespan is 228.24s with 367.06s total case work. The 84.21s idle-resume case is queued late and finishes alone.

Moving it immediately after the exclusive case models 196.45s makespan (−31.79s) with the same two slots. The API and CRD enforce at least one minute of idleness. Preserve the real controller suspension, old-Pod removal, authenticated resume, new Pod and retained history. A shorter CI timer is invalid.

The source-backed next VM architecture experiment keeps the current cases and changes execution hardware. Merging the two Codex scenarios is a coverage decision: the ordinary guest tests the default 256MiB executor budget, fresh boot, certificate, supervised setup and history; OOM uses 96MiB and proves same-process/session recovery. Moving only a shell probe would not preserve that matrix, and deleting a branch that already ends earlier predicts no direct elapsed saving without a measured contention effect.

Why the other obvious shortcuts do not establish a large win

Ordinary and OOM commands pass through actual harness/tool/session boundaries. The OOM baseline, exhaustion and same-session follow-up are sequential by design (32.10s,17.88s,8.41s in the current trace). Combining them into one synthetic shell loses recovery coverage. The two harness cases inside existing paired tests are already concurrent. Dispatcher cases mutate shared replicas/controller state; parallel cells must own separate deployments. Pod protocol-only cases already borrow compatible runners and verify immutable Sandbox and Pod identity; lifecycle cases cannot use that pool.

Preparing more immutable application inputs may remove part of the remaining 40–80s setup, but retaining live app/DB/credential state requires a new isolation/reset contract. Existing k3s/PKI/KubeVirt retention is already implemented. A previous live-Postgres experiment demonstrated no benefit. Neither fact rules out a separately designed immutable empty-database clone, but it is not an established 25% gain.
