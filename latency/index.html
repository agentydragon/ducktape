The reuse model: stable services, fresh workloads, verified release

Use a versioned infrastructure recipe for compatible services and pinned images. Check actual identity, configuration, health and cleanliness at attach. Build current application inputs and fresh databases/certificates/mock state. Release a clean environment only after all owned mutable resources are gone; rebuild owned dirty or incompatible state cold.

  1. Family: recipe version + infrastructure pins/configuration; avoid a new family for every application edit. Effective platform/resource/VM settings still affect matching.
  2. Attach: prove ownership and health; mark leased/dirty before handing it out. A restored process may be dead or have stale connections.
  3. Test: current code and isolated state. Migration-from-empty, restart, supervision and recovery scenarios retain their fresh-start coverage.
  4. Release: stop clients, remove owned databases/roles/slots/credentials, then atomically mark clean. Failed cleanup prevents reuse.

This selector explains designs; it does not change repository or executor settings.

Local fixtures should call the same setup/reset/cleanup code with retention off by default and fixture-owned temporary state. BuildBuddy permission and invalidation belong in an adapter. Current Docker/browser tests still run on RBE; local-host validation and any policy change are separate. Self-hosted OCI/Docker can retain a paused container on one executor; Firecracker snapshotting needs additional host capabilities and executor configuration.

Prepare lazily; version layout changes; add a warmer only for a measured need

A normal cold test can prepare a family. Test setup boots or attaches, test teardown proves cleanliness, and BuildBuddy decides whether to save afterward. A service-layout or lifecycle change gets a new compatibility recipe version and all consumers change together. Validate cold, warm and another compatible consumer; an action-cache pass cannot prove warming.

What the pinned selector really supports

The pinned bazel-diff v47.0.0 uses bazel query --proto:instantiation_stack by default. It content-hashes main-repository macro/rule Starlark appearing in instantiation stacks and propagates dependency digests; pinned E2E tests cover changed macro bodies with identical emitted attributes and cross-file macro/rule edits. This supports investigating audited BUILD-loaded leaf macros. Pinned hash implementation · Behavioral coverage.

It does not justify removing the fallback globally: the package-level subinclude fallback switches off when any rule has a stack, leaving a mixed-graph coverage question; external source hashes are excluded; module extensions, toolchain/configuration changes and undeclared workspace readers need separate proof. Keep unknown roots broad. Validate actual transitive helper/constants/load and mixed-stack fixtures with the pinned executable before changing policy. Mixed-graph boundary.

Root //... also excludes nested modules in .bazelignore; their own validation remains a separate pre-existing coverage boundary. Neither a full root sweep nor narrower root selection establishes nested-module coverage.
