More Pod slots hit a memory-reservation limit.

On the existing four-unit worker, two slots passed all 13 cases in 262.3s. Three slots took 498.8s and failed three cases; two explicitly reported Kubernetes Insufficient memory, and another never reached bootstrap. The target failed. Its 5.7 GiB action memory peak is not proof of a physical out-of-memory kill: the scheduler refused declared memory requests.

Each environment Pod requests 1 GiB for the runtime, 512 MiB for its executor, plus a 32 MiB sidecar. Six Pods alone exceed 9 GiB; the 11 fixed app Deployments add 1,664 MiB before PKI and Kubernetes. The four-unit worker reported 9,724 MiB total RAM. Node allocatable and a simultaneous aggregate request census were not captured, so these source requests corroborate the scheduler diagnosis without inventing an exact admission threshold.

The original 2/3/4/4/3/2 plan stopped after that capacity failure. The revised experiment holds capacity at eight units for 2/3/4 slots, then repeats the highest passing candidate and the two-slot control.
