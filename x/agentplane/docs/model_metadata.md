# Harness model-metadata under LiteLLM route names

Scope: Claude Code 2.1.252 and Codex 0.152.0 (the `MODULE.bazel` pins, lines 753-777) launched by Agentplane against LiteLLM 1.90.2 (`cluster/k8s/litellm/app/deployment.yaml:69`) with the cheap-experiments key. Binary evidence comes from `strings` of the pinned tarballs and from the `openai/codex` source at tag `rust-v0.152.0` (file paths below are in that tree). Live evidence comes from the `hooks` capture scenario of [`../capture/`](../capture/) run against LiteLLM for both harnesses on 2026-09-03; the captures stay outside Git, as every probe run does.

## Headline

- **Claude Code already recognises the route.** It normalises by substring (`includes("claude-haiku-4-5")`), so `anthropic-api/ant-messages/claude-haiku-4-5-20251001` resolves to canonical `claude-haiku-4-5` with the right window, pricing, thinking and effort gating. The capture proves it end to end. Nothing needs changing for Haiku; the only degraded case is the codex-lane `chatgpt/ant-messages/gpt-5.6-*` names, which contain no Claude family token (already handled by `CLAUDE_CODE_MAX_CONTEXT_TOKENS` in `nix/home/claude_code/gateway.nix:24-45`).
- **Codex does not recognise the route**, and says so on the wire: the capture contains `warning: Model metadata for `chatgpt/oai-responses/gpt-5.6-luna` not found. Defaulting to fallback metadata; this can degrade performance and cause issues.` Cause: Codex matches slugs by longest prefix, then retries after stripping exactly **one** `namespace/` segment; a two-segment prefix is rejected by design. A single-segment name (`anything/gpt-5.6-luna`) would be recognised.
- **Recognition is not free for Codex.** The real `gpt-5.6-luna` entry turns on code mode (`tool_mode: code_mode_only`), websockets preference, responses-lite, verbosity, freeform `apply_patch`, and `default_reasoning_summary: none`. Several of those are unlikely to survive LiteLLM, and code mode changes the item stream the Agentplane Codex adapter translates. "Make Codex understand it is GPT-5.6" therefore needs a decision about which of those features to want, not only a naming fix.
- **LiteLLM can alias without touching key allowlists**: `router_settings.model_group_alias` is consulted during the key's model-access check, and supports `hidden: true`. Per-key `aliases` (which the ncecere provider does expose) are applied only _after_ the access check, so the alias name would also have to be allowlisted. Team `model_aliases` are checked during auth but are marked deprecated upstream.

## 1. LiteLLM route names and aliasing

### Naming scheme

- `cluster/k8s/litellm/app/model_rosters.py:3-42` — `{provider}/{shape}/{model}` (#4823). Provider first because key allowlists match `model_name` prefixes (`anthropic-api/ant-messages/*`, `tf/gitops/litellm-keys/main.tf:371,405,460`); `/` chosen because model slugs are dash-heavy and `/` is LiteLLM's own idiom (lines 29-36). `exposed_name()` at line 68.
- Pinned in three places: `model_rosters.py` rosters, literal locals in `tf/gitops/litellm-keys/main.tf:59-160`, and generated entries in `proxy-config.yaml` (Haiku at 310-316, Luna Responses at 238-248 with the measured 372k window from `model_rosters.py:85-106`). `test_litellm_config.py:28-69` pins tf allowlists to rosters and asserts every literal allowlist name is served by the proxy.
- cheap-experiments key: `main.tf:180-188`, models `local.cheap_experiments_models` (`main.tf:115-160`), which includes exactly the two names Agentplane uses (157, 159). Staging runner pods read it via `main.tf:209-221` → `cluster/k8s/agentplane-staging/app/sandboxtemplate-agentplane-runner.yaml:68,73` (`ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`).
- No `router_settings` block exists in `proxy-config.yaml` today; `litellm_settings` is only `drop_params` + callbacks (`proxy-config.yaml:544-550`).

### How the existing consumers handle names

- `haku-console-claude`: `haku/console/config.py:306-311` sets `ANTHROPIC_MODEL=<anthropic-max20/ant-messages/...>` and `ANTHROPIC_DEFAULT_HAIKU_MODEL=<route>`, optionally `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`. Same pattern in `nix/home/claude_code/gateway.nix:31-45`, whose comment (lines 24-29) already records that non-Claude route names (`chatgpt/ant-messages/gpt-5.6-luna`, Gemini) make Claude Code assume 200k and need `CLAUDE_CODE_MAX_CONTEXT_TOKENS`.
- `codex-pod` / agent-workspaces: `cluster/k8s/agents/agent-sandbox/workspace-image/codex-config.toml:9-11` uses `model = "chatgpt/oai-responses/gpt-5.6-sol"` with a custom `model_providers.litellm` — same two-segment shape, so the same fallback metadata as Agentplane (inferred from the matching logic below, not captured).
- Laptop gateways (`codex-clients`, `gemini-clients`, `tana-clients` teams, `main.tf:355-465`) rely on team-level `router_settings.fallbacks` (`model: "*"`) so that Claude Code's hard-coded background model slugs (`claude-haiku-4-5-20251001` etc.) get routed somewhere instead of 403ing. That is the only aliasing-like mechanism in use today, and it is a fallback, not a rename.

### What LiteLLM 1.90.2 supports (file paths are in the `litellm` package of that release)

- Model-access check `_can_object_call_model` (`auth_checks.py:3004-3073`): builds `potential_models = [model]`, appends `litellm.model_alias_map[model]` or `llm_router._get_model_from_alias(model)` if the request name is a `router_settings.model_group_alias` key, and allows if **either** the alias or the underlying model passes `_check_model_access_helper` (wildcards via `is_model_allowed_by_pattern`, `auth_checks.py:4485-4566`). So a router alias `claude-haiku-4-5-20251001 → anthropic-api/ant-messages/claude-haiku-4-5-20251001` is accepted by any key whose `models` already contains the target — no Terraform change to allowlists.
- `model_group_alias` values may be `{"model": ..., "hidden": true}` (`router.py:9577-9582`, `_get_model_from_alias` at 10779-10796) so the alias need not appear in `/v1/models`.
- Per-key `aliases`: rewritten in `litellm_pre_call_utils.py:1949` (`_update_model_if_key_alias_exists`), which runs in `add_litellm_data_to_request` _after_ auth (order at 1818-1836). Auth's `_check_model_access_helper` (2950-3001) never reads key aliases, so the alias _name_ must itself be in the key's `models` (or match a wildcard). That collides with `test_terraform_key_allowlists_only_name_models_the_proxy_serves` (`test_litellm_config.py:64-69`) unless that test learns about aliases.
- Team `model_aliases`: honoured during auth (`_model_in_team_aliases`, `auth_checks.py:2981,3075-3093`) and rewritten pre-call (`litellm_pre_call_utils.py:1874`), but the docstring there says "model_aliases for team models are deprecated ... only applies to legacy non-team-scoped aliases".
- Terraform provider `ncecere/litellm ~> 2.0` (`main.tf:9-12`, `tf/gitops/litellm-keys/BUILD.bazel:15`): `litellm_key` has `aliases: Map(String)` "Model alias mappings"; `litellm_team` has `model_aliases: Map(String)` and `router_settings { fallbacks, context_window_fallbacks }` — no `model_group_alias` on teams (fetched from `internal/provider/resource_key.go` and `resource_team.go` on `main`; the exact version the Bazel mirror resolved could not be read here — no `.terraform.lock.hcl` is checked in for this module and no provider binary was found on disk). Router-level `model_group_alias` is proxy config (`proxy-config.yaml`), not Terraform.

## 2. Claude Code 2.1.252

All from the bundle's strings; the identifiers are the minified names as they appear in it.

- **Normalisation is substring-based.** `_v(e)` lowercases and walks `includes()` checks in generation order: `"claude-fable-5"`, `"claude-opus-5"`, ..., `"claude-sonnet-5"`, ..., `"claude-haiku-4-5"`, `"claude-3-5-haiku"`, ... returning the canonical id. Provider-specific ids (`us.anthropic.…`, `anthropic.…`) are handled first via `Afe`. Nothing requires the string to start with `claude-`; a prefix path is ignored.
- **Static model table** with the Haiku entry: `{id:"claude-haiku-4-5",family:"haiku",…,provider_ids:{first_party:"claude-haiku-4-5-20251001",…,gateway:"claude-haiku-4-5-20251001"},context:{window:200000,supports_1m_suffix:!0},max_output_tokens:{default:32000,upper:64000},pricing:"haiku_45",capabilities:["context_management"]}`; pricing tier `haiku_45:{input:1,output:5,cache_write_5m:1.25,cache_write_1h:2,cache_read:0.1,…}`. Window computation `Zw(e)`: `[1m]` suffix → 1e6; native-1m models → 1e6; else `CLAUDE_CODE_MAX_CONTEXT_TOKENS` **only if** `Qw(e)` (model does not start with `claude-` _and_ is not a known canonical id); else 200000. So for a recognised model the env override is ignored and the table wins.
- **Unknown-model handling**: `Qw`/`RMe` decide "known"; message `… map it in the modelOverrides setting or update Claude Code; CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1 restores the previous wait-for-the-API behavior`. `modelOverrides` (settings) maps canonical Anthropic id → provider-specific id; `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` fetches `/v1/models?limit=1000` from the gateway and feeds a `runtimeCapabilityLookup` used by `hh(model, capability)` only when the static table has no entry.
- **Feature gating by canonical id**: effort is disabled for `claude-haiku-4-5` (list includes it explicitly; `CLAUDE_CODE_ALWAYS_ENABLE_EFFORT` overrides); interleaved thinking `Ybt` returns false for `claude-haiku-4-5`; extended thinking stays on (`thinking:{type:"enabled",budget_tokens:min(z,maxTokens-1)}`).
- **Alias env vars**: `D5()` returns `ANTHROPIC_DEFAULT_HAIKU_MODEL` verbatim (`Yb` is identity) when set, else the catalog default; same for `dp()`/`Nt()` (sonnet/opus). `K6` maps `haiku|sonnet|opus` to those env vars. `--model haiku` + `ANTHROPIC_DEFAULT_HAIKU_MODEL=<route>` therefore sends the route on the wire and normalises it exactly as today — no metadata gain, only the `haiku` alias label. `ANTHROPIC_DEFAULT_*_MODEL_NAME/_DESCRIPTION/_SUPPORTED_CAPABILITIES` are display/capability overrides for the picker.
- **Provider detection** `Oe()` returns `"gateway"` only for Claude Code's own gateway-auth credential slot; with `ANTHROPIC_BASE_URL`+`ANTHROPIC_AUTH_TOKEN` it is `firstParty` (matches the capture).
- **What Agentplane passes today**: `x/agentplane/native/claude/scenarios.py:115-170` (`--model <route>`, `--effort` when set, `--safe-mode`, `--setting-sources=` etc.) and `:177-185` (env: `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_MAX_RETRIES`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`). No `ANTHROPIC_MODEL`/`ANTHROPIC_DEFAULT_*`. Runner: `x/agentplane/runner/claude.py:50-71`. The harness tests already rely on substring recognition: `x/agentplane/harness_tests/claude/harness.py:13-15` uses `agentplane-test/claude-haiku-4-5-20251001` "the family suffix lets it resolve the model's context window".

## 4. Live check: Codex recognising the model, through LiteLLM

Rai's expectation was that LiteLLM copes with the recognised model's feature set. Checked on
2026-09-03 with the `shell` capture scenario: Codex launched with `model = gpt-5.6-luna` against a
local shim that rewrites the request's `model` to `chatgpt/oai-responses/gpt-5.6-luna` and forwards
everything else untouched to LiteLLM under the cheap-experiments key.

- **The turn completed correctly.** Three upstream requests, all `200`; the model ran both probe
  commands and reported `exit 0` / `exit 23` with the right stdout and stderr; no `warning`
  notification at all.
- **Code mode was on and survived the proxy.** The request carries no `tools` or `instructions`
  keys: the tool set travels as a developer `additional_tools` input item (namespace `functions`
  with the custom `exec` JavaScript tool, `wait`, and `request_user_input`), and the base
  instructions as a developer message. The model answered with `function_call: wait` items and a
  `custom_tool_call: exec` streamed as `response.custom_tool_call_input.delta`; Codex executed
  the script, which called `exec_command` from inside the isolate. So the Agentplane adapter would
  see `custom_tool_call` items instead of `exec_command` function calls once the model is
  recognised.
- **Verbosity and reasoning context went through:** `text: {verbosity: low}` and
  `reasoning: {effort: low, context: all_turns}` were accepted. No reasoning `summary` was
  requested (the real entry defaults to `none`), so no summary deltas came back; the earlier
  fallback-metadata capture had `summary: auto` and streamed them.
- **No websocket attempt** reached the shim: with an API-key provider and an `http://` base URL,
  Codex used plain SSE despite `prefer_websockets`.
- **The context window did not change:** `thread/tokenUsage/updated` still reports 258 400, because
  the real entry's `context_window` is the same 272 000 as the fallback's; only its
  `max_context_window` (872 000) differs, which is what a `model_context_window` override may now
  reach. The route's measured 372 000 needs that override either way.

## 5. Options, ranked

Ranking assumes the goal is "harness applies its real per-model behaviour" with the least blast radius. Verified = observed in binary/source/capture; inferred = follows from that but not executed.

**1. LiteLLM router alias, hidden, targeted per wire (option a).** Add to `cluster/k8s/litellm/app/proxy-config.yaml` a `router_settings.model_group_alias` block, e.g. `gpt-5.6-luna: {model: chatgpt/oai-responses/gpt-5.6-luna, hidden: true}` (and, if wanted for symmetry, `claude-haiku-4-5-20251001 → anthropic-api/ant-messages/claude-haiku-4-5-20251001`), then launch Codex with `model = gpt-5.6-luna`. Verified: `_can_object_call_model` accepts the alias when the target is in the key's `models`, so `tf/gitops/litellm-keys/main.tf` allowlists and the roster tests stay untouched; `hidden` keeps `/v1/models` clean; Codex then longest-prefix-matches the bundled Luna entry. Risks: (i) an alias name is proxy-global — `gpt-5.6-luna` can point at only one of the two wires, so it must be the Responses entry and Claude Code on the codex lane keeps its full `chatgpt/ant-messages/*` route (already fine for it via `CLAUDE_CODE_MAX_CONTEXT_TOKENS`); (ii) the Codex feature set below turns on; (iii) `cheap_experiments_models` in `main.tf` is intentionally exact — the alias does not widen it, but the roster tests should gain a case that every alias target is served; (iv) Haiku needs nothing, so aliasing it is cosmetic (Claude Code would still key `modelUsage` by whatever it is given).

**2. Single-segment route spelling for Codex consumers (option d, narrow).** Codex's namespaced retry accepts `namespace/gpt-5.6-luna` if `namespace` is `[A-Za-z0-9_-]+`. Exposing the Responses entries additionally (or instead) as e.g. `chatgpt-oai-responses/gpt-5.6-luna` would make them recognised with no LiteLLM alias machinery. Verified matching rule (`manager.rs:634-652`, tests 776-820). Costs: a second scheme beside the #4823 one (`model_rosters.py:29-42` chose `/` between all three segments deliberately), roster/tf/test churn across `model_rosters.py`, `proxy-config.yaml`, `main.tf`, `test_litellm_config.py`, `codex-config.toml`, `haku/console` config. A full rename of every route to two segments is the same idea with far more churn and would also need every key allowlist and wildcard (`anthropic-api/ant-messages/*`) re-spelled — not worth it for a Codex-only quirk.

**3. Codex config overrides on fallback metadata (option c).** Keep the route, add `-c model_reasoning_summary=…`, `model_verbosity`, `model_context_window` in `x/agentplane/native/codex/scenarios.py:config()`. Verified the keys exist in 0.152.0; verified the window override is clamped to 272k on fallback metadata, so it cannot express the measured 372k. It cannot enable code mode, freeform apply_patch, reasoning-level validation, or clear the "fallback metadata" warning/model-switch refusal. `model_catalog_json` could (a catalog whose one entry has `slug = <route>` and a curated feature set), and is arguably the most controllable form of "Codex understands the model" because it lets us keep `tool_mode`, websockets and responses-lite off while gaining the rest — but it is undocumented, unexercised here, and a custom catalog disables some features in newer Codex. Treat as a follow-up experiment, not the first move.

**4. `ANTHROPIC_DEFAULT_HAIKU_MODEL` + `--model haiku` (option b).** Verified from the bundle that this only substitutes the env value into the request and normalises it the same way; Claude Code already recognises the route, so there is no metadata to gain. Worth doing only for consistency with `haku/console/config.py:306-311` / `gateway.nix`, or when a route name lacks a Claude family token (codex-lane GPT models), where the real fix remains `CLAUDE_CODE_MAX_CONTEXT_TOKENS` (honoured only for unrecognised names, `Zw`/`Qw`).

### Decision needed before option 1 or 2 lands for Codex

Recognition flips Codex into the GPT-5.6 feature set: code mode (single JS `exec` tool instead of `exec_command`/`write_stdin`), `prefer_websockets`, `use_responses_lite`, `text.verbosity`, freeform `apply_patch`, `default_reasoning_summary: none` (the Agentplane adapter's `ReasoningSummaryTextDelta` stream would go quiet unless `model_reasoning_summary` is set). Whether LiteLLM 1.90.2's Responses passthrough to CLIProxyAPI tolerates websockets/responses-lite is unverified; `features.code_mode*` can be disabled explicitly (`scenarios.py:166-172` already sets `features`), and `model_reasoning_summary` restores summaries. A capture against the aliased name is the cheapest way to see which of these bite.
