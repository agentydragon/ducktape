The app shell

Supersedes the earlier top-nav-row mock: the row goes away entirely in favor of a persistent left sidebar. Threads are the primary thing you browse, grouped by the sandbox that hosts them — the group header already carries that sandbox's identity, state, and thread count, so there's no separate Sandboxes tab; a flat browse-by-sandbox view would just repeat what's already visible one level up. That leaves the sidebar itself down to one list, so it's a plain list, not a tab strip. Pending approvals get their own always-reachable badge, and decided Actions get a dedicated full page (not a sidebar tab — there's real detail to show per entry: caller, group/name, arguments) — the same drawer-plus-separate-history-page shape haku/console's shell_chrome.tsx already uses for its own approval queue.

The sidebar's "+" opens an empty composer, not a wizard: pick an existing Sandbox or "+ New sandbox from preset" (only then does a preset picker appear), pick a model, type a prompt, press Enter — the page then binds to whatever Sandbox/Thread that created. A Sandbox's own page keeps a "+ New thread" of its own reusing the identical component with the Sandbox (and therefore preset) already fixed, per the operator's own framing that a per-Sandbox page should still be able to start a fresh conversation directly. Whether this same empty composer eventually replaces whatever the default landing page is instead of requiring the sidebar click first is an open question, not decided here — see x/agentplane/plans/session_first_navigation.md.

Settings — OAuth clients / MCP servers / Notifications

The gear at the bottom of the sidebar (next to the history clock — see the anatomy above) replaces what used to be three separate routed pages behind the old nav row's "More" menu — one modal, tabbed, instead of three pages to navigate between. Renamed the first tab from "Connections" to "OAuth clients": each row is exactly that — claude.ai, a Codex instance on some machine, any OAuth-connected agent — bound to one caller ServiceAccount, the model in x/agentplane/plans/action_policies.md. Plain enough to be a 3-column table rather than a card list: client, its ServiceAccount as a dropdown (picking a different eligible one there is the whole rebind, no new OAuth round-trip, no separate "Change" step), and Unlink. Still the Connection type in code and API — this only changes the label and the exposed controls, not the domain name used everywhere else.

Behavior notes

  • The pending badge is deliberately not a sidebar tab. It has to stay visible and reachable no matter what the sidebar is showing or whether it's even open (phone) — mixing "browse" and "something needs you" into one panel buries the urgent thing.
  • Precedent: haku/console/frontend/shell_chrome.tsx already ships this exact split for its own MCP tool-call approval queue — an icon-rail trigger opens a non-modal drawer over the content area, with a separate full page for history. This mock follows that shape rather than inventing a new one — including giving history its own page rather than a compact tab list, once it needs to show the same per-entry detail (caller, group/name, arguments) the pending drawer does.
  • The drawer is non-modal — approving/denying doesn't lose your place in the transcript you were reading, unlike a full-page interrupt. Whether a genuinely urgent new arrival also needs a harder interrupt (a toast, a sound) is still open — the drawer covers steady-state access, not necessarily "the moment it arrives."
  • The sidebar is one list, not a tab strip. Sandboxes are folded into the Threads list's group headers (identity, state, thread count) rather than a separate flat browsing view, and Actions history moved to its own full page — between those two, there was nothing left to switch tabs between. Tradeoff, left open: a sandbox with zero threads has no row to appear on here at all; whether that needs its own minimal listing (or is simply fine — a sandbox worth tracking usually has a thread) isn't decided.
  • Per-thread status dot mirrors the composer bar's own worst-axis cascade — green while that thread's harness is attached and running, gray while idle or its sandbox is suspended/deleted, amber when something inside that specific thread needs your approval — so a thread needing attention doesn't require opening it first to find out, and a suspended sandbox's threads read as gray without a separate view to learn why.
  • A thread whose sandbox was deleted stays listed and readable — trajectory.py's Thread/Event store is durable and outlives the Sandbox — but its group header renders struck through with a distinct icon, and the open thread has no folder-link (there's no live SandboxPage left to open) and no composer: read-only history only.
  • The folder icon in the breadcrumb is the one way left to reach a specific SandboxPage directly from a thread whose sandbox still exists — mirroring the reference screenshots' own folder-icon-opens-workspace affordance.
  • "Threads," not "Sessions," to match the codebase's own noun for a conversation — Thread/Event in trajectory.py, ThreadView/ThreadTitle in the frontend already. SessionView/sessionId stay as the code names for the live runner-attached connection; the UI label is what changes.
  • "OAuth clients," not "Linked accounts" or third-party services. Each row is an OAuth-connected agent (claude.ai, a Codex instance on some machine) bound to a single caller ServiceAccount — the model x/agentplane/plans/action_policies.md already specifies. The ServiceAccount is a dropdown on the row itself, not a separate "acts as" line plus a "Change" step; a "Linked" badge is dropped too — a client's presence in this list already says that.
  • Approval JSON gets real syntax highlighting in the actual frontend — an existing library already used elsewhere — not the plain monospace block shown here; this mock only stands in for layout, not rendering fidelity.
  • Archived Threads are hidden by default, same as the Sandbox-level "Show archived" switch this replaces: the switch sits at the bottom of the Threads list, off by default, and each row gets its own Archive (or, once revealed, Unarchive) action — a Sandbox's archived state and a Thread's are now two separate flags at two separate levels, not one inherited from the other.
  • A paginated/searchable "all threads" view is deferred, not designed here: this sidebar is fine for a working set, but finding one old Thread once the list runs past the dozens needs its own answer (probably a full page, the same shape as Action history) — flagging it now so THREAD_LIST_API doesn't get built assuming an unpaginated single call is enough forever.
  • Starting a new thread is one component, reached two ways. The sidebar's "+" opens it unscoped — pick an existing Sandbox or "+ New sandbox from preset" (which reveals a preset picker), a model, then type and press Enter — and a Sandbox's own page keeps a "+ New thread" reusing the identical composer with the Sandbox (and its preset) already fixed, so the per-Sandbox entry point survives the sidebar redesign rather than getting displaced by it. Submitting binds the same page to whatever Sandbox/Thread the submission created — there's no separate "creating…" transition state mocked here.
  • Whether this composer becomes the default landing page instead of something reached by clicking "+" first is intentionally left open — it would make the empty-state and the sidebar's own trigger the same surface, but that's a bigger claim about what / shows than this mock decides.
