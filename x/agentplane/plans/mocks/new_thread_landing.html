Agentplane New-Thread Landing

x/agentplane · UISHELL_NEWTHREAD_LANDING / UISHELL_NEWTHREAD_SANDBOX

One page, three states — not a wizard

The sidebar's "+" (unscoped) and a Sandbox page's own "+ New thread" (pre-scoped) open the same page as an open thread — same composer, same composer-row (status dot, model, and reasoning effort pickers), same layout — just in a state where no Sandbox/Thread is bound yet. That state lets the operator target an existing Sandbox or describe a new one; pressing Enter submits the draft immediately, provisions whatever is missing, and then rebinds the page to the real thread in place. The picker area above the composer is the only thing that changes shape — the composer and its row of controls never move and are never replaced by different components, only reused earlier than they're reused today.

Behavior notes

  • One composer component, three call sites. The sidebar's unscoped "+" (UISHELL_NEWTHREAD_LANDING), a Sandbox page's pre-scoped "+ New thread" (UISHELL_NEWTHREAD_SANDBOX), and an already-bound open thread (session.tsx) render the same component in three states, not three components — a pre-scoped entry starts in State A/B with the segmented control and Sandbox picker hidden and that Sandbox already fixed, exactly the "no sandbox/preset picker" card already sketched in app_shell.html.
  • Provisioning has to be server-owned, not client-sequenced. Closing the browser right after pressing Enter must still leave a thread that shows up running when reopened later — so "wait for the pod, then open the session, then send the first turn" cannot live in a useEffect watching the live stream; it has to run durably on the server, independent of any client connection. openSession's own reachability check (bridge.py's runner_address) already requires state === "running" with a pod IP — today nothing but the frontend performs that wait, which is exactly the gap. A server-side worker (naturally an extension of bridge.py's existing per-sandbox watch, since it already observes each sandbox becoming reachable) needs to own opening the session and sending the first turn once the pod is up. This is a real backend change, not a frontend-only feature — see NEWTHREAD_DURABLE in ../task_dag.md.
  • The client mints the session id up front (same pattern sandbox_page.tsx's createSession already uses — s-${crypto.randomUUID()}) and gets back a stable URL to bind to immediately on submit, before the sandbox or session exist yet — not deferred to State D. Reopening that URL later, from any device, reconnects to the same live stream and shows the same in-progress or by-then-completed thread; there is no separate "in-flight submission" state that a reload can lose.
  • The draft is captured optimistically on Enter, before any network call — so it survives as the pending bubble even if the very first request (creating the Sandbox) fails; a failure surfaces inline in the status stack (replacing the failed step with an error line and a Retry), and the draft stays intact for the operator to retry rather than needing to be retyped.
  • The composer is never disabled, only submission is. While provisioning (State C), the operator can keep typing — there's no reason to lock the text field just because sending is pointless until the thread exists. Enter simply does nothing until then; nothing needs to look grayed out.
  • Model and reasoning effort are the composer-row's controls, not a second form. Both already read state (model) or will (reasoning effort — see REASONING_EFFORT_RUNTIME in ../task_dag.md) that's editable after a thread exists; States A–C show that same control before one does, pre-filled from the picked Sandbox's current session (existing-sandbox path) or the chosen Harness (new-sandbox path). There's deliberately no separate "Model"/"Reasoning effort" field in either the Sandbox picker or the new-sandbox form — that would be a second source of truth to keep in sync with the real composer-row the moment the thread binds.
  • Open question, not decided here: should the existing-Sandbox picker allow picking a suspended one? If so, submitting would need to resume it first — the same provisioning status stack as State C, just starting from a "Resuming sandbox…" step instead of "Sandbox created". Left for later.
