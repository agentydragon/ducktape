03 / PostgreSQL backup options

Beyond the S3 bucket.

Research updated 02 Nov 2026. The inventory above remains the dated snapshot shown at the top of this report.

The live check found 21 of 22 CNPG clusters configured to use the Barman Cloud WAL archiver; configuration alone does not establish that backups are healthy. Base backups and WAL currently go through SeaweedFS S3. The options below compare ways to keep backups while changing that storage path.

01 · Current design

Barman Cloud + SeaweedFS

Storage: S3 buckets on the existing SeaweedFS volumes. Recovery: physical backups and point-in-time recovery (PITR) with archived WAL.

This is integrated with CNPG scheduling, retention and recovery today. Keeping it is the least disruptive option, but retains the object-storage layer.

02 · Native snapshots

CNPG + Piraeus snapshots

Storage: snapshots of PostgreSQL PVCs. Recovery: to a snapshot; PITR between snapshots also needs a separate WAL archive.

CNPG can schedule and restore snapshots. The live cluster check found no VolumeSnapshotClass; setup is needed. CNPG does not provide the same retention policies for snapshots. A snapshot sharing its source pool is not an independent copy against loss of that pool; a separate copy or failure domain needs a design.

03 · CNPG plugin on PVCs

Klio

Storage: Klio can store physical backups and streamed WAL on Piraeus PVCs without an S3 tier. Recovery: CNPG-managed restore and point-in-time recovery (PITR).

Uses CNPG Backup and ScheduledBackup resources, Klio Server and PluginConfiguration resources, and CNPG Cluster recovery. Klio supports retention and deduplicated backup data. Its v0.0.20 server uses separate data, cache and queue PVCs; one server can serve multiple clusters, or we can use separate servers for independent placement. Base backups run from the primary.

Experimental: upstream does not yet recommend production use. Our live PostgreSQL images are version 18, above Klio's documented minimum of 15; full compatibility, failover, slot monitoring, retention and thin-pool reclaim still need validation. See the example below.

04 · Direct filesystem candidate

Traditional Barman server

Storage: filesystem repositories on Piraeus PVCs, potentially one independently sized replicated PVC per database. Recovery: physical backups and PITR with continuous WAL collection.

Barman can use pg_basebackup and stream WAL with pg_receivewal. A pilot could collect WAL alongside the existing archiver. CNPG scheduling and restore from a traditional Barman repository are not established drop-in integrations: design credentials, failover, replication slots, retention, monitoring and CNPG restore before cutover. Many PVCs also introduce scheduling and operational overhead.

05 · Filesystem tool, plugin gap

pgBackRest

Storage: pgBackRest itself supports POSIX filesystem repositories. Recovery: physical backups and PITR are supported by the tool.

The experimental Dalibo and Opera CNPG plugins document object-storage repositories but not filesystem repositories, so neither is currently a direct PVC solution for us.

06 · Reduced recovery scope

Scheduled logical dumps

Storage: dump files on a Piraeus PVC. Recovery: to the latest successful dump, without WAL-based PITR.

Simple to understand for selected databases if the potential loss since the last dump is acceptable. Database-level dumps need separate handling for cluster-wide roles and other global objects.

Suggested next investigation

Evaluate Klio without removing existing backups.

Klio is the closest documented fit for non-S3 backups, PITR and CNPG resources, but is experimental. Evaluate it against one small database while retaining its existing Barman Cloud backups; determine whether both paths can coexist, then verify WAL continuity, failover, retention and CNPG recovery before considering a wider migration. Traditional Barman remains a filesystem-backed alternative with more CNPG integration work.

Piraeus replication improves volume availability; it does not by itself provide backup history or protect against logical deletion and corruption. Repository sizing must include retention, WAL growth, cache and overlapping backups.

Klio example: backup and point-in-time restore manifests

Illustrative resource shape for Klio v0.0.20, not a ready-to-apply deployment. Install the Klio operator and CNPG plugin first; create the server TLS certificate and client CA, a client certificate whose common name is klio@app-db, and the referenced Age encryption key and identity Secrets. Preserve the encryption key and identity for recovery. Names, capacities, schedule and retention are examples, not sizing decisions.

This omits the optional object-store tier: data and WAL remain on PVCs. The three piraeus-hdd-2 claims follow that storage class's placement and replication configuration. A shared Klio server holds several databases' backups in its data PVC; use separate servers for separate backup-data volumes. The Cluster snippet shows the integration shape and is not a replacement for our existing managed cluster spec. Klio streams WAL; do not mark it isWALArchiver.

Storage strategy / researched 01 Nov 2026

S3 on Piraeus: the tradeoffs.

We want smaller independently movable pieces within a bucket, with Piraeus doing replication and movement, and capacity returning to its thin pool as objects disappear. The products below are plausible options; none was found to provide the complete one-S3-shard-per-replicated-PVC model as a ready-made integration.

Pieces smaller than a bucketData from one bucket can live in several independently placed pieces. Ideally each piece is a modest PVC, not a whole bucket or node-sized volume.
Piraeus owns movementA piece is a replicated PVC; moving it means attaching on the destination and letting Piraeus synchronize its replica. Independent object-store replication is an extra layer.
Thin capacity comes backA large PVC is a ceiling, not necessarily allocated physical space. Deleted data must be freed by the store and discarded all the way down to the thin pool; snapshots may retain blocks.
Desired provisioning model

One S3 storage volume, one Piraeus PVC

An S3 service divides buckets into modestly sized storage volumes. When it creates a volume, it asks Kubernetes to provision an individual PVC and starts or assigns a worker to mount and serve that volume. Piraeus replicates the PVC; moving the volume means moving its worker and letting Piraeus handle data placement and synchronization, subject to its placement and autodiskful configuration. Different volumes within the same bucket can therefore live on different nodes, and each PVC has a capacity ceiling without necessarily allocating that ceiling up front.

The S3 service still needs durable object-to-volume metadata and a safe PVC and worker lifecycle. Returning space after object deletion requires its own cleanup plus discard through the filesystem and storage stack; retained snapshots can hold blocks. Removing an empty volume could release its PVC, subject to snapshots. No ready-made S3 implementation of this complete model has been identified in this research. The SeaweedFS operator currently provisions PVCs for volume-server pods; Seaweed's smaller logical volumes are files inside those PVCs.

Baseline · workable compromise

Keep SeaweedFS on bounded PVCs

Our existing object service, with node-specific maximum capacities; a larger HDD node can have a larger ceiling.

Placement & replication
Seaweed places and replicates its own modest logical volumes across volume servers. Those volumes are files inside each server's PVC, not independently replicated Piraeus PVCs. Moving one logical volume is a Seaweed operation.
Reclaim
Deletes generally need volume compaction before space returns to the filesystem; discard or trim must then reach the thin pool. Temporary space and retained snapshots can delay reclaim. Measure this on our deployment.
Fit
Preserves fine-grained object placement and our existing integration, but retains two layers of storage management. Choose the Piraeus replica count and Seaweed replication together to avoid accidental over-replication.

Strongest alternative for distributed S3

Garage

Distributed S3 with content-addressed blocks and configurable storage capacity per node, including unequal nodes.

Placement & replication
Objects are split into blocks distributed and replicated by Garage; one bucket is not tied to one node. Multiple directories, each potentially on its own PVC, can have different configured capacities. Garage assigns and rebalances blocks itself; a block or hash slice is not a PVC that Piraeus independently moves.
Reclaim
Data is stored as filesystem blocks/files. Reclaim depends on Garage freeing unreferenced blocks, filesystem discard/trim and Piraeus passing discard to its thin pool; metadata, retained versions and snapshots may remain. Exact timing and pool recovery are unverified here.
Fit
Good sub-bucket distribution, heterogeneous capacity and a plausible thin-friendly filesystem path. Still has application-level distribution/replication; replicated PVCs underneath can multiply copies. Node and directory rebalance are Garage operations, not Piraeus operations.

Strongest alternative for Piraeus ownership

VersityGW POSIX + Piraeus

An S3 gateway maps buckets and objects to ordinary filesystem directories and files. Piraeus can replicate the filesystem PVC instead of an object cluster replicating those files.

Placement & replication
One gateway root can reside on one replicated PVC. Explicitly mounted per-bucket PVCs are a possible Kubernetes design, but need lifecycle and routing work; either way, a bucket on one filesystem is not automatically divided into independently movable PVC shards. A single-writer claim constrains gateway scheduling and failover.
Reclaim
Deleting files can free filesystem blocks; discard/trim must reach Piraeus. Retained versions, incomplete multipart uploads and temporary files can keep space in use. Verify the entire path.
Fit
Simple storage ownership and promising space reclaim, at the cost of whole-filesystem or whole-bucket placement. Check S3 compatibility, xattrs, IAM, naming and concurrency for our clients; versioning is documented as experimental for the POSIX backend.

Fine-grained, operationally heavy

Ceph RGW + RADOS

Ceph's S3 gateway stores bucket objects in RADOS, which distributes placement groups across storage daemons.

Placement & replication
Placement groups distribute data below the bucket level and Ceph moves and replicates them. They are logical groups within pools, not one PVC each. Ceph OSDs can use block devices, but running them over Piraeus adds another distributed storage system and failure model.
Reclaim
BlueStore manages raw blocks rather than a normal filesystem. Discard or its trim operation must free unused blocks through the backing device; verify behavior and cost on our Piraeus stack rather than assuming immediate reclaim.
Fit
Strong placement machinery but a large operational commitment and overlapping replication. Unattractive solely to replace SeaweedFS on this cluster.

Coarse storage pools

MinIO / AIStor

Distributed S3 with erasure-coded objects across drives in erasure sets and server pools.

Placement & replication
Objects are distributed below bucket level, but a PVC is a drive in an erasure set containing parts of many objects, not a Piraeus-managed shard of a particular bucket. Erasure coding adds its own durability layer. AIStor expansion is by adding server pools; it does not automatically rebalance existing objects.
Reclaim
Filesystem-backed drives can return freed blocks through discard/trim after the service removes data; object versions, multipart data and snapshots may hold space. Verify the specific release and stack.
Fit
Usable object storage but a weaker match for small independently movable Piraeus volumes and uneven node ceilings. Check product edition, licensing and supported topology before considering it.

RustFS

S3-compatible object storage with erasure-coded drives and server pools; its Kubernetes chart supports multiple pools.

Placement & replication
Objects are encoded across drives in an erasure set. PVCs are backing drives, not independent bucket fragments managed by Piraeus. The upstream source describes expansion by adding a pool, with the original pool geometry retained; confirm this against the release chosen for deployment.
Reclaim
Filesystem space can be reused after deletion, subject to object versions and cleanup; discard/trim must propagate to the thin pool. Reclaim behavior is not verified in our cluster.
Fit
Another distributed S3 candidate, but adds its own placement and durability layer. Review release maturity, S3 compatibility and operations before trusting it with backups.

Practical direction. Keep the bounded SeaweedFS deployment unless a change buys us enough to justify migration. If we want distributed S3 without SeaweedFS, evaluate Garage first; if we want Piraeus to own replication and can accept coarser placement, evaluate VersityGW first. These are architectural recommendations, not tested migrations.

What to measure before choosing

An empty thin PVC can be small even with a large advertised ceiling. That does not prove that deletes or movement return capacity.

On a disposable, representative Piraeus volume, measure thin-pool data usage before writes, after writes, after deletion and the store's cleanup, after discard/trim, and after any retained test snapshots are removed. Repeat with replication enabled and record each node separately. Check object versions and multipart uploads, available temporary headroom, failover, S3 features required by our clients, and behavior when the thin pool fills. Compare filesystem and PVC usage with physical thin-pool usage; do not add them together. Linux thin provisioning ↗

What the categories mean

Our own code is grouped together because we can change it. “S3 required” means a confirmed protocol dependency in the current implementation, not that changing code is impossible. An object-storage requirement is distinct from an S3 protocol requirement: where no practical self-hosted non-S3 path is verified, the choice remains open. Filesystem support does not prove that our distributed deployment can safely use one PVC. The bucket inventory retains owners and last-reported sizes; the PostgreSQL backup comparison covers possible backup designs.
