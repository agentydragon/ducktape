What “the archive” means here

The app’s PostgreSQL copy of the runner’s journal, plus derived thread state. It is not a ZIP file or BuildBuddy test artifact. Ingestion records journal entries and the derived receipt state in one database transaction; the bridge performs its receipt lookup and replay-cursor read separately.

When it works

  1. The runner has accepted the command once.
  2. The app already has its receipt and returns it, or the app’s replay cursor is still before that receipt.
  3. On the latter path, native replay supplies the existing receipt; the duplicate command executes no additional work.
  4. The HTTP retry returns the original receipt with 200.

When the race wins

  1. The app looks up the command receipt and finds none.
  2. Ingestion copies the accepted command’s receipt into PostgreSQL.
  3. The bridge reads a replay cursor now at or beyond the receipt.
  4. The runner deduplicates the retried command, so it emits no new admission receipt. Replay starts after the old one.
  5. The receipt wait reaches stream EOF, which maps through FAILED_PRECONDITION to HTTP 409.

Source ordering: RunnerBridge.command. The defect is a missed receipt across two reads, not duplicate command execution.

Definitions, coverage, and remaining uncertainty

What the counts include

BuildBuddy SearchInvocation was fully paginated (49 pages, 48,692 repository invocations of all commands). The full-suite census selects command test, role CI, pattern //...: 601 invocations, all source commits present in inspected devel ancestry, 600 complete. It excludes 120 CI-tagged smoke invocations and thousands of developer/build/query invocations. Search filters invocation update times; target-history filtering uses invocation start time, never cached test start time. The completed selected census is checked against target-history membership.

Target history required 18 pages to cross the window boundary. Mainline target observations include cached results. The 827,928-row tracked history contains 1,566 labels; 120 smoke observations are excluded from full-suite analysis. Per-target denominators differ because targets were added, removed or renamed. A target result is not a pytest case, shard or fresh execution.

Current devinfra/ci/bazel_ci.py enables target tracking for push CI, so the tracker is intentionally incomplete for PRs. GitHub attempts supply the separate PR recovery population. A failure followed by a pass on the same tested SHA is strong evidence of inconsistent behavior; configuration, runner state, cache and external services may still differ. A new-commit pass is weaker evidence. Cancellations, missing results, build failures and sustained red sequences are not silently counted as flakes.

BuildBuddy’s official aggregation implementation uses uncached rows and an adjacent pass–failure–pass heuristic. It omits zero-flake targets, and the daily endpoint also omits zero-flake days. Its returned successfulRuns is absent in this deployment; missing values were not read as zero passes. The tracker implementation assigns the target cache flag per incoming test result, which limits interpretation of mixed cached/executed shards. No global uncached execution rate is inferred from this leaderboard.
