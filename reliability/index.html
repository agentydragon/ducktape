Observed failures and their mechanisms

k3s setup: a real xtables lock conflict

In 8cf4fdfe, all ten MCP cases error in one shared fixture. K3s.start checks then appends a NAT masquerade rule while k3s/kube-proxy can also update iptables. The append exits 4 with “Can’t lock /run/xtables.lock”. Current agentplane/system_tests/k3s/stack.py invokes both commands without -w and treats every nonzero check as a missing rule. The same tested SHA later passes the MCP target from a fresh execution. Ten pytest setup errors are one target/fixture failure.

MCP early wait: source defect, now a merged candidate fix

9ba054ed fails the Codex launcher’s wait_for_turn(wait_seconds=1) expectation; 9a80d2fa explicitly passes the target fresh on the identical tested SHA a31e93dfa297fa3185e6f94bbefe3120c5b515a9. #12189 references this exact incident and changes the authorization/wait budget and propagated-deadline boundary. It merged after the window; current source was reviewed. No post-fix recurrence reduction is measured.

Dispatcher: three distinct failures, one verified same-source recovery

One revision fails an exact caller-set assertion after actions becomes a configured caller: a source/test mismatch. An earlier revision stalls in the deployed ready/admission scenario for its 600s pytest deadline. The recovered 7d08c8f3 fails its cleanup wait for Ready.reason=Stopped after the runner reports Codex executor startup: context deadline exceeded; the traceback’s finally cleanup can obscure the original path. 786f259e passes dispatcher fresh on identical tested SHA 1393bc64da85dc49a8ab37151920625b7e0d77c3.

Existing artifacts include dispatcher-wake state and service/native diagnostics; the retrieved log narrows the failure to runner activation/stop, but does not establish why the executor startup wedged or why stop did not complete. The next missing discriminator is the Codex companion/app-server state at that activation failure and the controller’s stop/finalizer state. Do not rebrand the whole set as one flake or raise its timeout.

VM OOM acceptance: three failures in a new contract

Three PR failures occur in the new OOM containment case: one tool response reports an unknown exec-server session, and two later revisions fail because the executor cgroup path differs before/after OOM. The current agentplane/system_tests/test_vm_sandbox.py still requires the same runner boot, app-server process, native session and surviving cgroup, plus a working follow-up. Later passes exist on other tested revisions; these are not verified same-source recoveries.
