App tests: recurring symptoms, separate mechanisms

Thread window projection

af15a737 and 418a1037 both failed test_thread_window_browser.py:171: after a held older page landed while the reader was scrolled back, appending 35 more items yielded cursor 334 but the rendered projection never reported it within 30 s. The cases ran on SHAs a9190914ed7c and 85d673e5a698. Each failed action was noncached, with one TestRunner execution. The source appends through the fake event source and asserts the view's revision cursor. Both retained browser traces show the view reach cursor 264 after the older-page load and remain there through the 30-second wait; no tail item appears. The open live entity-shape GET has no captured event body, and retained service logs do not record the History write or per-cursor projection. A comparable noncached physical pass (0e35611e, different SHA 01bc3bb7288d) shows 264 → 334 in its DOM trace. The first missing stage is therefore bounded between ReplicationSource.append and rendered view revision, with the copy/History write, Electric row/shape and client apply unresolved. If the durable view-state row reaches 334 but the live shape does not, repair shape delivery or subscription recovery; if the row stays at 264, repair the copy/History projection handoff. Record those stage cursors on failure to choose between them, and preserve the retained-reader assertion. The two failures are recurrence across commits, not same-source recovery.

Reproduction and limits

  • BuildBuddy Flakes API bounds are exact UTC through CLI duration conversion at request time. The four labels returned nine paginated heuristic samples. Target history was independently paginated; all-branch rows include cache results and are not physical exposures.
  • For selected failed targets, exact target summaries, remote TestResult strategies and matching TestRunner execution IDs establish noncached runs and physical attempts. Two VM target failures have two physical attempts each. No complete fresh-run denominator or same-full-SHA passing recovery was found in the tracker/history query; one selected PR retry has a verified same-tree fresh fail-to-pass pair.
  • VM timelines use the failed attempt's retained test-spans.jsonl or vm-phases.jsonl, plus native/test logs. Nested and concurrent spans are wall intervals; they are not summed as CPU time. The two slow VM attempts have different first unresolved operations.
  • GitHub census uses complete day partitions, current exact-head check rollups and merge timestamps. It cannot reconstruct superseded check attempts. A non-green merge is operator friction, not proof of flakiness or intentional bypass.
  • Raw API responses, logs and traces remain in local scratch. This report changes no workflow, retry policy or production test. Desktop/mobile visual validation and publication are separate review steps after this authored report.
